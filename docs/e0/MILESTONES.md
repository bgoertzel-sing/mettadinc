## Overview (§3, p. 18 (PDF p. 19))

> Milestones describe capability and evidence, not calendar time. The first useful release is
> M0–M3: strict certificate boundaries, the full frontend, the graded deterministic core and the
> symbolic backend. Each work package ends with the manifest claims it covers, reproducible commands, structured
> results, negative cases, a replay run and a statement of the remaining unsupported surface. A claim
> is covered when the implementation returns its required status and values with replayable evidence;
> claims outside the running release must return Unsupported.

Coding-agent entry checklist (Purpose and use, p. 1 (PDF p. 2)):

> 1. Read the specification, this guide and the package README of the same date. Run `python3 oracle/verify_mettadinc.py` and `python3 check_fixtures.py`; both must succeed before any work starts, and both must still succeed when it ends.
> 2. Record the Cetta revision and read the repository's build and contribution instructions before editing. Record the registry digest you build against.
> 3. Identify your milestone, its manifest claims, owned files, shared IR interfaces and required negative cases. A change to the registry, a certificate format or canonical serialization is a coordinated change: it updates the registry, the fixtures, the manifest and the checker together, and dependent work waits for it.
> 4. Implement the smallest complete path from source through admission, execution and replay. Never hard-code fixture answers, and never resolve an interface question from a PDF listing when the registry or a fixture answers it.
> 5. Keep the negative acceptance suite of §3.1 passing at every step: each of its fixtures is a small change that must make a successful result fail with a precise status.
> 6. Return reproducible commands, structured results, replay evidence, resource records, the manifest claims covered and the remaining unsupported surface. Performance claims need measurements with unchanged semantics and arithmetic.

## Semantic invariants (§1.2, p. 3 (PDF p. 4)–p. 4 (PDF p. 5))

These hold in every milestone (§3.1: "Every later milestone keeps them, and keeps the suite below passing"). The five regression cases at the end name their claims.

> Types and result schemas must keep the following distinctions visible.
> 1. Claim kinds are distinct types: current adequacy, update compatibility, behavioral (bisimulation) adequacy, trace adequacy, simulation, exact induction, approximate induction and linear realization. Evidence for one never satisfies a consumer of another without a registered theorem; in particular a positive behavioral defect does not refute trace equality.
> 2. Observation equality is `Literal` or `Observer`. A zero current defect under a non-separated value tolerance yields decoders into the zero-distance quotient only, and the result says so.
> 3. A measurement (`Measure*`, `Defects`) is Checked when its interval is computed to the requested precision, whatever the value. A check (`Check*`) compares the interval with `Within`, whose default is $0$. `Output` projects only from Checked results.
> 4. `InduceExact` requires current adequacy and update compatibility with defect zero, and literal congruence of the code fibers, checked on code values whatever the code tolerance (claims C01–C03); it returns a quotient arrow. `InduceApprox` returns a representative machine, its section (default `Center`), radius, arrow defect and a priori bound.
> 5. The horizon `(Steps h)` covers the initial observation and $h$ transitions; its tolerance is $\Phi^{h+1}(1)$.
> 6. A transition law, a tolerance, a checked transfer and a host result bag are different types. A bag becomes a set, multiset or law only under the interpretation the interface declares; a transfer becomes a kernel only through the registered `KernelOf` construction.
> 7. Arrow kinds have distinct types and registered composition laws: functions for quotient arrows and homomorphisms, additive defects for graded arrows and transfers, $(\lambda_L\lambda_K, \rho_L\lambda_K+\lambda_L\rho_K)$ for linear arrows, $(L_2L_1,L_2\eta_1+\eta_2)$ for affine contracts. Composing across kinds without a registered conversion is InvalidInput.
> 8. A signed linear realization is not a machine. A replayed positive candidate bounds the positive dimension from above only.
> 9. Kernel hives and transfer hives are different types with different coherence claims.
> 10. A symbolic carrier is admitted only with its obligations discharged; type-checking its terms is not admission.
> 11. A prior-dependent averaged model is an aggregate, not a quotient.
> 12. Probabilities, tolerances and defects, p-bit pairs, report availability, error bounds, operator norms and costs never convert implicitly; an estimate becomes PLN evidence only by a conversion that preserves its estimand and dependence assumptions (§1.11).
> 13. Exact claims are about admitted models; population claims need their own evidence and status.
> 14. Shared and fresh reads of random or nondeterministic variables are declared, never inferred.
> 15. Unmeasured correspondences in a hive are marked, never filled with zero.
> 16. Every result carries its binding: module digest and subject names, source and target model identities, the checked interface with its value tolerances, and its scope (initial states, reachable-state scope, horizon, discount, policy class). Every operation that consumes a result validates the binding first, and a mismatch is InvalidInput naming the field, in every release.
> 17. One assurance policy assigns every status: Checked only on the grounds `Exact` and `Replayed`, Refuted only on a replayed `Witness`, Conditional on `(TrustedBackend solver version logic obligation-digest)` for an unreplayed backend answer, with `agreed_by` recorded as evidence, on `(Assumption name digest)` for an assumption the source declares, and on `(EstimatedPremise result-digest delta)` for a premise that is an estimate; derived results inherit the union of their premises' assumptions, and consumers accept only what their `Accepts` declaration lists.
> 18. A distance value enters a result only through the registered certificate kinds, whatever algorithm computed it, and an exact measurement needs a lower and an upper certificate that meet; when the distance is a supremum that no registered certificate attains, the answer is Unknown with the interval. Trace-event and policy-tree tests are undiscounted probabilities and bound a behavioral distance at discount one only. On a stochastic machine a trace refutation over observation-based policies needs a policy tree; a word witness never certifies it.
>
> Five regression cases protect these invariants from the start, each with its manifest claims. First,
> states $0,1,2$ with constant observations, encoding $\{0,1\}\,|\,\{2\}$ and update $0\mapsto0$,
> $1\mapsto2$, $2\mapsto2$: the behavioral defect is zero while the update defect is one (H09, H10).
> Second, the posterior summary of the receipt memory: it is not compatible with the union merge, and a
> merge of posteriors as independent evidence double counts shared receipts (P10–P13). Third, the
> forty-bit zero machine: a sampled relevance screen drops the tail bits, and the resulting four-class
> encoding has behavioral defect one (F07). Fourth, the adversarial zero-tail candidate, which passes
> every local check and fails coverage (F05). Fifth, for the first stochastic milestone, the
> seven-state chain, where the behavioral check is refuted by a modal test while the trace check passes
> (S03, S05).

## M0: strict certificate boundaries (§3.1, p. 18 (PDF p. 19) to p. 20 (PDF p. 21))

### Text of the milestone (verbatim)

> The first milestone is a small implementation whose certificate boundaries are strict. It answers
> few requests, and it keeps its guarantees under small adversarial changes of its inputs: a premise
> about the wrong machine, a stream whose content changed, a verdict that rests on a solver answer
> nobody replayed, a code tolerance that hides a literal failure. The fixtures of the package and of
> the application bundles already exercise more forms than a first implementation can make reliable,
> so M0 makes the boundaries strict before any breadth is added. Every later milestone keeps them, and
> keeps the suite below passing.
>
> M0 delivers one mechanism for each boundary, or fixes its interface where a later milestone builds
> it.
> 1. Every certificate is bound to its exact interface. The result envelope carries the binding of the specification's trust model: module digest and subject names, source and target model identities, the checked interface with its value tolerances, and the scope with initial states, reachable-state scope, horizon, discount and policy class. One validation routine runs before any consuming operation uses a premise: `Then` and transfer composition, safety transfer along a simulation, lifting to a keyed store, rebuilds, stream and snapshot reads, and gates. The registry's binding rules run at admission, so a mismatch is InvalidInput naming the field in every release, also for a request that is otherwise Unsupported, and wrong-store lifting and wrong-target safety transfer are rejected before any proof transfer begins.
> 2. One assurance policy assigns every status, on the grounds of the registry's `assurance` entry. Conditional results carry their `TrustedBackend` assumptions and their `agreed_by` evidence to every consumer, derivations take the union of their premises' assumptions, the declarations `(Accepts Checked)` and `(Accepts Checked (Conditional (TrustedBackend cvc5)))` are enforced, and a gate counts a Conditional result that its consumer does not accept as inadequate coverage. Results supported by a solver, results replayed independently and empirical estimates stay distinguishable all the way to the consumer.
> 3. Obligations are built from the admitted source. M0 fixes the obligation generator's interface: its only input is the admitted IR, and every obligation it emits records the digest of that source, so no separately written model of a module stands between the source and its proof obligations; the independent mathematical models of the examples stay as differential checks. It also builds the mutation harness, which edits admitted sources to restore known bugs and requires each affected verdict to change. The generator itself is built in M3, with the symbolic backend, and the access-policy mutation becomes a gate there.
> 4. Preserving a goal's meaning is an explicit obligation. M0 fixes the result types and the rule: informational refinement and informational equivalence, the one-way and two-way adequacy checks between goal observers, are results under those names, and preservation of the meaning is a separate obligation with declared, protected decoders, $d_{\mathrm{new}}(g_{\mathrm{new}}(x))=d_{\mathrm{old}}(g_{\mathrm{old}}(x))$ for every valid record $x$; a goal change counts as a renaming only when both hold. The adequacy checks are the `CheckNow` requests of M0. The interpretation request, `CheckInterpretation` of the Omega memory and goals guide, is built with the deterministic core in M2, once its registry patch is adopted.
> 5. Empirical claims name their populations and selection rules. The envelope's `Estimate` field carries the population, the selection rule, the policy version and the estimand, and a result derived from an estimate is Conditional on it; M0 fixes these records, and the estimators come in M4. A policy change triggers a transport check, which passes only with a declared argument, or a new estimation task; a selection rule that depends on the policy blocks transport.
> 6. The witness forms and induction preconditions are fixed before the compiler's interfaces harden: the literal-congruence obligation of `InduceExact` with its `CongruenceWitness`; the `PolicyTreeWitness` format with its admissibility check, and Unsupported answers for policy-class trace requests until its replay exists; and the distance certificates of §1.7, with Unknown for a Precision-0 measurement whose certificates do not meet.
>
> On the computational side M0 covers the core requests these boundaries touch, on enumerated
> deterministic modules: `MeasureNow`, `CheckNow`, `CheckUpdates`, `InduceExact`,
> `CheckAbstractionMap` and `Then`, with the manifest claims E05, E08, E09, H08, H10, H12 and
> C01–C03. Every other request returns Unsupported or, when a binding rule fails, InvalidInput.
>
> The negative acceptance suite is M0's acceptance. Each entry names the document whose bundle holds
> the fixture and the status an implementation must return. An entry whose request needs a later
> milestone is answered Unsupported until that milestone, except that binding failures are
> InvalidInput from M0 on; from its milestone on it must return the status given.
> 1. An index of the live-memory guide [livememory] declared with the item statistic of a machine that has fewer queries than the store's item machine, as in `(Keyed EngineAsItems (Of Items) (Item EngineStat))` where `EngineStat` is a statistic of `EngineTime`, is InvalidInput naming the mismatch. ### Algorithms (§1.9, verbatim) **[assigned to milestones]**

- *Crisp current and update checks*, those of a representation whose code tolerance is the discrete equality, are functional-dependency tests—does the code determine each query, does it determine each successor's code—implemented as hash group-bys with exact comparison, linear in $n$ plus $m$. Under a two-valued metric code tolerance the same group-bys run on the classes of the tolerance, and `InduceExact` adds the literal-congruence group-by on the code values.

### Certificate formats (Table 1, §1.7, verbatim rows) **[assigned to milestones]**

| Claim | Certificate | Replay |
|---|---|---|
| Current or update failure | Pair, query or action, the two values, codes or class masses | Evaluate both sides. |
| Literal-congruence failure (`InduceExact`) | `CongruenceWitness`: pair with equal code value, action, two successor code values (a code value and two masses for laws; two code sets for nondeterminism) | Apply the encoding to both successors and compare the values literally; the code tolerance is not consulted. |
| Exact value (`Precision 0`) | A lower and an upper certificate | Replay both and require equal values; a distance computed by any algorithm enters only this way. Trace-event and policy-tree tests count as lower certificates at discount one only (at discount $1/2$ the one-step event test of U04 would exceed the distance). Over all finite words at discount one the only registered lower certificates are tests, so when no test reaches the upper bound the result is Unknown with the interval (claim U01). |
| Derived result (`Then`, lift, safety transfer, rebuild, gate) | Premise digests with their bindings | Validate every premise's binding against the objects the operation names (InvalidInput on a mismatch); recompute the union of the premises' assumptions; a Conditional premise makes the result Conditional, and an Estimated premise makes it Conditional on `(EstimatedPremise result-digest delta)`. |
| Backend verdict without a replayed proof | `(TrustedBackend solver version logic obligation-digest)`, and `agreed_by` entries | Nothing to replay: check that the obligation digest is the generator's output for the admitted source, record the assumption and the agreeing backends, and assign Conditional. |

### Algorithms (§1.9, verbatim) **[assigned to milestones]**

- *Crisp current and update checks*, those of a representation whose code tolerance is the discrete equality, are functional-dependency tests—does the code determine each query, does it determine each successor's code—implemented as hash group-bys with exact comparison, linear in $n$ plus $m$. Under a two-valued metric code tolerance the same group-bys run on the classes of the tolerance, and `InduceExact` adds the literal-congruence group-by on the code values.
- *Behavioral partition*: Hopcroft or Paige–Tarjan refinement in $O(m\log n)$ [hopcroft,paigetarjan]; for deterministic machines, a splitting tree with minimal separating sequences [smetsers]; for other functors, characteristic formulas in shared form [explaining].
- *Crisp behavioral check*: compute $\Pbeh$, then test the dependency ``code determines behavioral class''. A failing group yields a witness pair, separated by the test at their lowest common ancestor. The pair-graph search of the specification's definitions is the reference engine only; it needs $\Theta(n^2)$ memory.
- *Graded distances*: for deterministic machines, shortest paths in the pair graph restricted to the pairs a request needs; for labelled Markov chains with one transition function, exact polynomial-time computation, with policy iteration or on-the-fly algorithms in practice [chenvbw,tangvb,bacci]; for several actions, exact value iteration for lower bounds and couplings for upper bounds, reported as an interval with no complexity claim.
- *Closure*: max–Łukasiewicz Floyd–Warshall in $O(n^3)$.
- *Frontier search*: exhaustive over partitions for small carriers; heuristic otherwise, with optimality reported Unknown.
