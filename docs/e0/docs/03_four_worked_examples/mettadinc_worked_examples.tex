\begin{abstract}
\noindent
A language specification says what programs mean. It does not show what it is like to write one
for a problem someone cares about, which requests that person would send, what the answers look
like, or which parts of the language turn out to be missing. This document works through four
MeTTaDinC programs in full. The first compacts the belief memory of an agent with two consumers,
a reasoner that reads truth values and a controller that reads a status, and finds that the
choice of decay rule decides whether any compact summary can be trusted; it separates three
meanings of ``store it in fewer bits'' into three claims with different numbers. The second
audits an administrative access-control policy on forty-bit configurations without enumerating
them: two authoring mistakes are found with short canonical witnesses, the corrected policy is
proved safe with $80$ small proofs whose obligations are generated from the module itself and checked
by a verified checker, and a true property comes back Unknown until a stronger invariant is
supplied. The third shares navigation skills between three robots whose
cameras see the same bay in different frames; a transfer learned from recorded behavior is
correct only up to the task's symmetries, and whether the skill library is coherent depends on
the gauge declared at each robot. The fourth follows a market maker through a toxic-flow shift
and a one-sided-flow shift: the first changes every value and no decision, the second breaks the
desk's state compression and its policy, a toxicity signal is priced correctly and incorrectly,
a leak of news is shown to be invisible to a desk that only quotes wide, and monitors are shown
to be provably blind to one shift each. Every number is recomputed by an exact oracle, and each
example ends with implementation notes and the registry additions it needs.
\end{abstract}

\section{Introduction}\label{sec:intro}

\subsection{Why worked examples}

The MeTTaDinC specification defines what a program means: carriers, observers and actions; the
defects that measure what an encoding loses; the claims that say which notion of sameness has
been established; the certificates that let a second program check the first. It supports those
definitions with fixtures, and the fixtures are small on purpose. Each isolates one phenomenon --
an eight-state machine for the crisp core, a forty-bit machine that cannot be enumerated, a
seven-state chain on which behavioral, trace and linear answers disagree -- so that an
implementation either reproduces the phenomenon or visibly fails to.

Fixtures do not show what it is like to use the language. Someone with a real problem has to
decide which machine to declare, which consumer the interface serves, which requests to send in
which order, what a refutation is telling them about their design, and what to do when the
language cannot yet express the next question. Those decisions are where a language succeeds or
fails in practice, and they only become visible on problems large enough to have structure and
small enough to be checked exactly. The four examples in this document were chosen with that in
mind. Each is a problem that comes up in the systems this work is meant to support -- the memory
of an Omega agent, the access policy of an organization, a group of robots sharing skills, a
trading desk facing a market that changes under it -- and each forces the language to say
something the fixtures do not.

The examples serve two readers. An implementer gets a set of conformance targets that exercise
many requests together, with every expected status, witness and number stated and recomputed by
an independent oracle, and with notes on the algorithms that produce them. A prospective user gets
a picture of how MeTTaDinC programs are written and read, and of the kind of design advice the
answers carry: a decay rule that silently ruins every summary of a memory, a policy rule that reads
a session where it should read an assignment, a learned transfer that is correct only up to a
mirror, a market shift that a fill-rate dashboard can never see.

\subsection{The four examples}

\emph{Example 1, belief memory} (Section~\ref{sec:ex1}). An agent keeps two evidence counts per
proposition and serves two consumers: a reasoner that reads a truth value and a controller that
reads a three-way status. Under memory pressure the designer wants dormant beliefs stored in fewer
bits. The example finds that neither consumer has a useful exact compaction, that the original
decay rule makes every compact summary worthless, that a gentler rule bounds the error of a
twenty-one-code summary at $1/5$, and that ``fewer bits'' means three different things --- an index,
a cold store that is rehydrated, and a memory that runs on its codes --- with three different
claims and three different answers. It extends to six beliefs ($2^{48}$ states) by a product rule
and to a ledger of evidence receipts whose forks must be merged, and whose oldest receipts can be
compacted to counts only under a delivery protocol that keeps them from arriving again.

\emph{Example 2, access policy} (Section~\ref{sec:ex2}). An administrative role-based access
control policy over four users and five roles has forty bits of state. The audit finds two
authoring mistakes with two- and three-step witnesses, proves the corrected policy safe with
$80$ small proofs whose obligations are generated from the module and which pass through the
specification's pinned proof-checking pipeline, shows that restoring either mistake in the source
changes the verdict, shows a true property returning Unknown until a stronger invariant is
supplied, and finds that a targeted monitor needs seventeen bits where a vendor proposed ten.

\emph{Example 3, skill sharing} (Section~\ref{sec:ex3}). Three warehouse robots see the same bay
through cameras in three frames and share a library of navigation skills. A transfer learned from
recorded behavior is one of four equally exact candidates, and going around the cycle of transfers
returns every cell as its mirror image, so that a skill comes back earning at each cell what it
earned at the mirrored cell. Whether that is acceptable depends on the gauge declared
at each robot; a gauge copied between robots instead of transported is caught by the intertwining
check. A docking requirement breaks a symmetry and exposes the stale transfer, and a pallet makes
transfers into one bay approximate.

\emph{Example 4, market making} (Section~\ref{sec:ex4}). A market maker's quoting problem is a
discounted decision process in four markets. In calm markets the desk can run on three risk
buckets with no loss; toxic flow lowers every value by more than half and changes no decision;
one-sided flow breaks the compression and the policy, and the broken symmetry survives as an exact
transfer between two markets. A toxicity signal is priced correctly and incorrectly, a news leak
is shown to be invisible to a desk that only quotes wide, and each of two monitors is shown to be
blind to one of the shifts.

\subsection{How each example is organized}

Each example section has the same parts. It opens with the problem in its own terms and the
background needed to follow it. It then gives the program: excerpts of the modules with the
reasons for each declaration, and pointers to the full file in Appendix~\ref{app:sources}. The
results follow, grouped by the question they answer, each with its status, its canonical witness
when it is refuted, and its certificate when it is checked. A table of expected results collects
them for conformance testing. Notes for implementers describe the algorithms that produced the
results and the pitfalls the oracle uncovered, and a final subsection lists the registry additions
the example proposes.

Proposed additions are marked in the modules with the comment \code{PROPOSED}. None of them changes
the meaning of an existing request on the inputs that request already accepts; several extend a
request to new inputs (Example~4 extends four requests of the Decisions library from one-step
decision models to decision processes), and one proposes a change to a status rule (Example~1
allows the optimality of a frontier to be Checked by a replayed lower-bound certificate without
exhaustive enumeration). Section~\ref{sec:synthesis} collects all of them.

\section{Conventions shared by the examples}\label{sec:conventions}

\subsection{Statuses and claims}\label{sec:statuses}

Every request returns a result in the specification's envelope (\spec{5.5}), with one of seven
statuses (\spec{2.2}). The examples use all seven, under one policy for what each status requires.
\begin{itemize}
\item A result is \emph{Checked} when the claim holds within its scope and is established either by
an exact method that the checker runs on the module's machine (finite enumeration, exact rational
arithmetic, partition refinement, decision diagrams) or by a certificate that the checker replays:
a witness, a coupling, a clique, a table of values, an exact dual solution of a linear program, or a
proof of unsatisfiability in the DRAT format that drat-trim converts to LRAT and the verified checker
\code{cake\_lpr} accepts, for an obligation that the obligation generator built from the admitted
source.
\item A result is \emph{Conditional} when the claim holds under named assumptions that the checker
has not discharged. The answer of an external solver that has not been replayed, such as a
satisfiability solver's ``unsatisfiable'' without a checked proof, is Conditional, and its
assumption names the solver, its version, the logic and the digest of the obligation, as in
\code{(TrustedBackend cadical 1.5.3 SAT sha256:...)}. A second solver or a second encoding that
agrees is recorded as evidence, in the field \code{agreed\_by}; it does not discharge the
assumption.
\item A result is \emph{Refuted} when a counterexample, the \emph{witness}, or a lower-bound
certificate shows that the claim fails and the checker replays it by evaluating the admitted source.
A witness found by a solver counts once it has been replayed.
\item A result is \emph{Unknown} when the claim is unresolved, because a budget ended or a
certified interval straddles the bound. The result carries what was learned in its
\code{Resources} field.
\item A result is \emph{Estimated} when a statistical procedure supports a conclusion about a data
source, with its estimand, protocol, sample and guarantee stated. Estimated results appear only in
Example~4.
\item A result is \emph{InvalidInput} when a declaration or request violates the admitted language,
for example a transfer whose state pullback is not total, and \emph{Unsupported} when the request
lies outside the capability manifest of the running release.
\end{itemize}
A result derived from other results, such as a claim about six beliefs lifted from one belief by the
product rule of Example~1, carries the union of their assumptions, so a derivation from a
Conditional premise is Conditional. A consumer declares which results it accepts:
\code{(Accepts Checked)} accepts only Checked results, and
\code{(Accepts Checked (Conditional (TrustedBackend cadical)))} also accepts results whose only open
assumptions are trusted-backend assumptions for CaDiCaL. A Conditional result that a consumer does
not accept counts, for that consumer, as a claim not yet covered.

Only Examples~1 and~2 call a solver. Their bundles keep every unsatisfiable obligation together with
its DRAT proof, and their oracles replay the proofs when drat-trim and \code{cake\_lpr} are
installed. The results that rest on the proofs are then Checked; without the two checkers the
oracles report them as Conditional, with the assumption above. Every other result in the four
examples is an exact computation or a replayed certificate.

The specification separates measuring a defect from checking a bound (\spec{2.4}). A request named
\code{Measure...} returns a certified interval and is Checked when the interval is no wider than the
requested \code{Precision} (zero by default, which asks for the exact value). A request named
\code{Check...} with \code{(Within b)} is Checked when the upper end of the interval is at most $b$,
Refuted when the lower end exceeds $b$ (with a witness), and Unknown otherwise. Without
\code{Within}, a check asks for defect zero.

\subsection{Defects in one page}\label{sec:defects}

An interface is a machine: a carrier $X$ of states, observers $o_j$ with value tolerances
$\beta_j$, and actions $T_a$ that are deterministic maps, stochastic kernels or nondeterministic
relations. A representation is a map $q$ from states to codes, and it is meant to be used in place
of the state by some consumer. The specification measures what $q$ loses with four defects
(\spec{4.2}).
\begin{itemize}
\item The \emph{current defect} $\dnow(q)$ is the largest observation distance $1-\beta_j$ between
two states with the same code. It is zero when every observer can be read off the code.
\item The \emph{update defect} $\dupd(q)$ is the largest distance between the codes of the
successors of two states with the same code. For crisp codes and deterministic actions it is zero
or one: either every action can be carried out on codes, or some pair of same-code states is sent
to different codes. For stochastic actions it is the largest total-variation distance between
the laws the two states push onto the codes; defect zero is \emph{strong lumpability}.
\item The \emph{behavioral defect} $\dbd(q)$ is the largest behavioral distance between two
states with the same code. For a deterministic machine the behavioral distance at discount
$\gamma$ is
\[
\dbeh^\gamma(x,y)=\max_{w}\ \gamma^{|w|}\,\max_j\bigl(1-\beta_j(o_jT_wx,\ o_jT_wy)\bigr),
\]
the largest discounted observation difference that any finite word of actions can produce; through
horizon $h$ the maximum ranges over words of length at most $h$. For stochastic machines the
behavioral distance is the Kantorovich bisimulation pseudometric, which replaces the single
successor by a coupling of the two successor laws (\spec{4.1}).
\item The \emph{trace defect} compares the laws of observation sequences only. For deterministic
machines it equals the behavioral defect; for stochastic machines it can be strictly smaller
(\spec{4.3}).
\end{itemize}
When the current and update defects are both zero, the representation is an exact quotient:
\code{InduceExact} returns the abstract machine on the codes and a checked quotient arrow. When they
are not, \code{InduceApprox} builds a machine from chosen representatives and reports its
\emph{radius}, the largest distance from a state to the representative of its class, and its
\emph{arrow defect}, the largest distance between a state and its code in the disjoint union of
the concrete and abstract machines (\spec{4.6}).

\plain A code is a promise that two states are interchangeable for a particular consumer. The
current defect says how far the consumer's present readings can differ between states with the
same code, the update defect says whether the code can be kept up to date without the state, and
the behavioral defect says how far apart the consumer's future readings can drift. These are three
different promises, and the examples show each of them failing while the others hold.

\subsection{Canonical witnesses}\label{sec:canonical}

A replay checker accepts any witness that replays. Conformance testing needs more: two correct
implementations must report the same witness, so that a manifest can record it. The specification
fixes a canonical witness, the least one in a declared order: shortest word first, then pairs of
states in the lexicographic order of carrier declaration, then actions and queries in declaration
order, then words in numeric order (\spec{4.4} and the registry's \code{witness\_order}). A
\code{Product} carrier enumerates in declared component order with the last component varying
fastest, which fixes the order of pairs. Each example adds the ordering rules its own claims need:
the least moved cell for a holonomy, the least state and first improving action for a policy
optimality check, the least observation sequence for a trace event.

Producing canonical witnesses is mostly a matter of search order. Breadth-first searches expand
actions in declaration order; solver models are minimized before they are reported, because a
satisfiability solver returns an arbitrary model; and tables are scanned in declaration order.

\subsection{Registry patches and the two-pass check}\label{sec:patches}

MeTTaDinC is registry driven: every declaration head, field, request, argument and result type that
a module may use is listed in a machine-readable registry, and the checker of the validation
package rejects anything else. The examples need forms the registry does not have yet. Each example
therefore ships a JSON patch that declares exactly those forms --- libraries with their primitives,
new declarations, new fields on existing declarations, new requests and result types --- and a
checker, \fpath{ex_check.py}, that runs two passes. The first pass applies the patches in memory
and checks every form of the module files; it must report no errors. The second pass checks the same
files against the unpatched registry and lists every diagnostic, which makes the forms that depend
on the patch explicit. The patches compose: Example~3 uses the \code{NatArith} library of
Example~1, and Example~4 uses \code{NatArith} and the \code{Families} library of Example~2.

\subsection{Oracles}\label{sec:oracles}

Every number in this document was recomputed by an oracle written in Python with exact rationals.
Floating point appears only where a section says so: as a first stage that finds the structure of
a fixed point before an exact solve, and in the decimals of a few statistical quantities that are
not part of any Checked claim.

The oracles compute from the module files. Each bundle also ships a Python model written from the
problem statement, and each oracle first establishes that the module and the model define the same
objects, so that the claims are computed on the machines the module declares.
\begin{itemize}
\item In Examples~1, 3 and~4 a small reference evaluator, the same file in the three bundles,
evaluates the maps of the module, and the oracle compares them with the model cell by cell: the
observations, actions and encodings of Example~1 on all $256$ states and the receipt maps on all
$64$ receipt sets; the responses, free cells, transfers, symmetries and skills of Example~3 at every
cell and command; and the kernels and reward laws of Example~4 on every state-quote cell. Example~1
builds its distance tables, and hence every frontier obligation, from the successor arrays that the
module defines.
\item Example~2 cannot enumerate its states, so its oracle builds everything from the source. A
reader elaborates \fpath{access_policy.metta} into a typed intermediate form, Boolean terms over the
bits of a word, and the evaluator, the Boolean encoding and the decision diagrams all consume that
form; every obligation, witness and reachable set of the oracle comes from it. On a two-user
instance of the same source, a direct interpreter of the source terms, the intermediate form and the
generated CNF agree on every word, action, query and closure obligation. Two mutations of the source
that restore the example's authoring mistakes must change the verdicts they affect. The bundle's
independent model, a hand-written Python policy and encoder that do not read the module, remains as
a differential check (Section~\ref{sec:ex2notes}).
\end{itemize}
Examples~1 and~2 also use a satisfiability solver, CaDiCaL $1.5.3$ through python-sat. With drat-trim
and \code{cake\_lpr} installed, the two oracles convert every DRAT proof to LRAT and check it;
without them, they skip the checks that read the checker's verdicts and report the results that
rest on the proofs as Conditional. \Cref{tab:oracles} gives the number of checks with the
checkers installed.

\subsection{Release scope}

The first capability manifest covers deterministic dynamics, crisp and \L{}ukasiewicz values,
enumerated and symbolic carriers, the core requests, the \code{GradedKernels} library and the
\code{BitVectors} and \code{FiniteSets} primitives (\spec{16.1}). Example~2 lies entirely within
it: its patch adds syntax, a few fields and one primitive, but no new kind of claim. Example~1 uses the
graded deterministic core of the first release together with proposed extensions and, for its
receipt ledger, the \code{Contracts} library of a later release. Example~3 needs the
\code{Transfers} and \code{Hives} libraries, and Example~4 the stochastic profile with the
\code{Decisions} and \code{Linear} libraries; both are conformance targets for the releases that add
those capabilities (milestones M6 and M4 of the guide). A first-release implementation answers
their requests with Unsupported.

\subsection{Reproducing the results}

The four bundles are collected in one package, described in Appendix~\ref{app:repro}. Each bundle
runs on its own: \code{python3 exN\_oracle.py} recomputes and checks every number and writes a
results file, and \fpath{ex_check.py}, pointed at the specification's validation package, checks
the modules against the registry and the patches. The bundles of Examples~1 and~2 add
\fpath{replay_proofs.py}, which replays their shipped proofs with drat-trim and \code{cake\_lpr}
alone.
\section{Example 1: compacting an agent's belief memory}\label{sec:ex1}

\subsection{The problem}

An Omega agent records, for each proposition it tracks, how many observations have supported it
and how many have gone against it. These are the counts $p$ and $n$ of the evidence form of a PLN
truth value \cite{pln}. With $t=p+n$, the \emph{strength} is $s=p/t$, or $1/2$ when there is no
evidence, and the \emph{confidence} is $c=t/(t+4)$; the constant $4$ plays the role of PLN's
lookahead parameter and is chosen small here. Each count saturates at $15$, so a belief occupies
eight bits. Evidence arrives as \code{pos} and \code{neg} events, each adding one to a count. A
periodic \code{decay} event halves both counts, so that old evidence weighs less than new; in the
memory as first designed, halving rounds down.

Two consumers read the memory.
\begin{itemize}
\item Reasoning processes read the truth value $(s,c)$. Two truth values are compared coordinate
by coordinate, with tolerance $1-|x-x'|$, so the distance between two readings is the larger of
the differences in strength and in confidence.
\item The action-selection controller reads a three-way status. A belief is \emph{Believed} when
$t\ge4$ and $p\ge2n$, \emph{Disbelieved} when $t\ge4$ and $n\ge2p$, and \emph{Uncertain}
otherwise.
\end{itemize}
Under memory pressure the designer wants dormant beliefs --- those no process is currently
reasoning about --- stored in fewer bits, and asks which smaller encodings can be trusted, by which
consumer, and with what certified error. A belief has $256$ states: small enough that every claim
can be checked exactly by enumeration, large enough that the answers are not obvious. The example
then extends to six beliefs held together ($2^{48}$ states, which must not be enumerated) and to
a ledger of evidence receipts whose forks have to be merged, the setting of the specification's
evidence-packet laboratory (\spec{12.4}).

The findings, in brief:
\begin{itemize}
\item Neither consumer has a useful exact compaction. The controller's exact quotient saves a
fifth of a bit per belief, and the reasoner's saves nothing.
\item The original decay rule makes every compact summary of the truth value worthless: two
beliefs that differ by a single observation can, after a few decays and evidence events, report
opposite truth values. The defect of every candidate summary is $1$, the largest possible.
\item A gentler decay rule repairs this, and the checker certifies the repair. Under it, a
twenty-one-code summary has defect at most $1/5$, and no lossy encoding can do better than $6/35$.
\item ``Store it in fewer bits'' means three different things. As an index or summary the
twenty-one codes are needed; as a cold store that is restored to a representative when evidence
arrives, ten codes suffice; a memory that discards the counts and runs on its codes fails at this
error level, because the error compounds with every update.
\item Memories that keep only counts cannot be merged without double counting, and cannot tell a
receipt that arrives a second time from a new one. Receipts, the identities of the evidence, can be
compacted to counts below the oldest open fork only under a delivery protocol that keeps those
receipts from arriving again.
\end{itemize}

\subsection{Background: what compaction means here}

The memory is a deterministic machine with $256$ states and three actions, and each consumer
sees it through an interface: \code{Decide} observes the status, and \code{Report} observes
strength and confidence. An encoding of the memory is a representation $q$ in the sense of
Section~\ref{sec:defects}: the memory would store $q(p,n)$ instead of $(p,n)$.

An \emph{exact} compaction keeps exactly what the consumer can ever observe. It is computed by
partition refinement (\spec{4.5}): start from the classes of the current observation, split every
class whose members are sent by some action into different classes, and repeat until nothing
splits. The stable partition is behavioral equivalence for that consumer, and its quotient is the
smallest memory that answers every question the consumer could ask, now or after any sequence of
events. The savings of a partition are measured in bits, $\log_2$ of the number of classes, and in
\emph{weakness}, the probability that two independent uniformly drawn beliefs fall in the same
class (\spec{4.7}); refinement lowers weakness round by round, and the specification records that
fall as a ledger.

When exact compaction saves too little, the question becomes graded: how far apart can two
beliefs with the same code drift? For a deterministic machine the behavioral distance between two
states is the largest observation difference that any word of actions produces from them, with
each step of the word discounted by $\gamma$ (Section~\ref{sec:defects}); at $\gamma=1$ nothing is
discounted. The behavioral defect of an encoding is the largest distance between two states with
the same code. Through a horizon $h$ only words of length at most $h$ count, which corresponds to
a consumer that looks at most $h$ events ahead. For the reasoner's interface the distance before
any event is
\[
d_0\bigl((p,n),(p',n')\bigr)=\max\bigl(|s-s'|,\ |c-c'|\bigr).
\]
All of these are computed on the pair graph, whose nodes are the $65536$ ordered pairs of states and
whose edges follow the three actions in both components at once.

The core module declares the memory, its two interfaces and the candidate encodings. The excerpt

A few choices in this module recur throughout the examples. Every map is unary, so functions of
two counts take a tuple and destructure it in a \code{Cases} pattern. The strength map divides
by $t$ only in the branch where $t\ne0$; this relies on \code{If} evaluating only the branch it
selects, which the proposed \code{NatArith} library states explicitly, because a strict
evaluation of both branches would divide by zero. The encoding \code{tv-grid-20} rounds strength and
confidence to the nearest twentieth with integer arithmetic: $\lfloor(40p+t)/2t\rfloor$ is
$20s$ rounded to the nearest integer, and $\lfloor(41t+4)/(2t+8)\rfloor$ is $20c$ rounded. The two
other grid encodings of the file, \code{tv-grid-10} and \code{tv-grid-10-7}, round to tenths, and
to tenths in strength and sevenths in confidence. \code{Buckets7} keeps each count only up to one
of the buckets $[0],[1],[2],[3],[4,5],[6,9],[10,15]$, and \code{Capped7} caps both counts at seven.

\subsection{Exact compaction for the controller}

\code{DecisionQuotient} is Checked with $225$ classes after six refinement rounds. The number of
classes grows as $3, 17, 68, 144, 206, 220, 225$, and the weakness ledger falls from
$11931/32768$ for the three status classes to $81/16384$ for the quotient. The only states the
quotient identifies are at saturation: $(k,14)$ with $(k,15)$ and $(14,k)$ with $(15,k)$ for
$k\le13$, and the four states with both counts at least $14$. Counts $14$ and $15$ halve to the
same $7$ and saturate alike, so the controller can never tell them apart. The quotient takes
$7.81$ bits instead of $8$, which is not worth having.

The status alone cannot be maintained: \code{CheckUpdates StatusOnly} is Refuted with the pair
$((0,0),(0,3))$ and the action \code{pos}. Both beliefs are Uncertain, but \code{pos} turns the
second into $(1,3)$, which is Disbelieved, and the first into $(1,0)$, which is still Uncertain.

A planner that looks $h$ events ahead needs only the \emph{staged} partition $P_h$, agreement
through horizon $h$, which has $17$, $68$ and $144$ classes for $h=1,2,3$. These partitions are
snapshot summaries rather than machines. \code{Staged2Machine} is Refuted on the update obligation
with the pair $((0,0),(0,1))$ and the action \code{pos}: the two beliefs agree on every status
through two events, but \code{pos} sends them to $(1,0)$ and $(1,1)$, and two more \code{pos} events
give $(3,0)$, Uncertain, against $(3,1)$, Believed. The specification's warning that a
bounded-horizon certificate supports a staged interface and not an abstract machine
(\spec{4.5}) applies here with a concrete witness.

everything.

\subsection{Three uses, three claims}\label{sec:ex1uses}

``Store the belief in fewer bits'' can mean three different things, and MeTTaDinC has a separate claim
for each.
\begin{enumerate}
\item \emph{An index or summary.} The code serves as a key --- for example, to share planning
results across beliefs --- while the counts stay available. The criterion is the behavioral
defect of the representation: two states with the same code have futures within the bound.
\item \emph{Cold storage with rehydration.} A dormant belief is replaced by its code and restored
to a fixed representative of its class when evidence next arrives. The error is the
\emph{radius}, the largest distance from a state to the representative of its class
(\code{InduceApprox}, \spec{4.6}). Each compression cycle adds at most one radius, because at
discount one the behavioral distance of two states is never smaller than that of their
successors: the words available from the successors are suffixes of words available from the
states. Decays missed while the belief was stored are handled by recording a decay epoch with the
code and replaying the missed decays on restore; the same bound covers them.
\item \emph{A compact memory that runs on its codes.} The counts are discarded and updates go
through the induced abstract machine. The criterion is the arrow defect of the induced machine,
and errors compound with every update.
\end{enumerate}
At the bound $1/5$ under the gentle rule the three uses give different answers. A summary needs
$21$ codes ($4.39$ bits). A cold store needs $10$ codes ($3.32$ bits). Running on codes fails at
this level: \code{RoundedTV20} has radius $6/35$, but its induced machine drifts to an arrow defect
of $20/63$. The drift is $3/22$, $3/22$, $3/20$ and $6/35$ at horizons one to four and reaches
$20/63$ only at horizon $33$. \code{Grid10x7}, with the same radius, drifts to $29/55$, and among the
$1600$ rounding grids of the \code{TVGrids} family none runs on its codes, with center
representatives, within $1/4$; the best of them drifts to $4/15$.

\plain A belief that is put away and later restored loses at most a radius each time it is put away.
A belief that is kept only as a code and updated as a code loses a little at every update, and
the losses add up. The same encoding can be good for the first use and bad for the second, and the
language makes the user say which use is meant.

\subsection{The frontier and its certificates}\label{sec:ex1frontier}

With the codes objective, the frontier is a graph coloring problem. Call two states in
\emph{conflict} when their behavioral distance exceeds the bound. An encoding whose defect is within
the bound is exactly a coloring of the conflict graph, colors being codes, so the fewest codes is
the chromatic number of that graph. Coloring is NP-hard in general, and the specification's status
discipline applies (\spec{4.7}): the defect of a returned partition is always certified, and its
optimality is Checked only with a certificate. Two certificates make an answer exact. The coloring
itself is one; its defect is recomputed from the distance table. A lower bound is the other: either
a clique of pairwise conflicting states, each conflict replayable as a word, or a refutation of the
problem with one code fewer.

The refutation is a satisfiability obligation in conjunctive normal form: one variable for each
state and code, a clause saying that each state receives a code, a clause for each conflicting pair
and code, and unit clauses that give the states of a largest clique the first codes, which rules out
no coloring up to a renaming of the codes. CaDiCaL finds the obligation unsatisfiable and writes a
DRAT proof, the list of clauses it derived in order, each of which a much simpler program can
confirm; drat-trim converts the proof to the LRAT format and the verified checker \code{cake\_lpr}
checks it. This is the specification's pinned pipeline (guide, Section~1.8). The obligations are
built from the distance table of the module's own machine (Section~\ref{sec:oracles}); the one for
twenty codes at $1/5$ has $5120$ variables and $501{,}856$ clauses. The bundle keeps every refuted
CNF with its DRAT proof, every coloring and every clique. With drat-trim and \code{cake\_lpr}
installed, the oracle replays the nine refutations of this section, four for codes and five for
centers, and every optimum below is Checked. Without them, the optima whose lower bound is a
refutation are Conditional on \code{(TrustedBackend cadical 1.5.3 SAT sha256:...)}, the digest
naming the refuted obligation, while the optima certified by a clique stay Checked.

Under the original rule the frontier is flat over most of its range. Below $1/58$ no two distinct

except that one may share a code; the four states with both counts at least $14$ then need two codes,

needs $225$, the classes of the exact quotient. Every other pair is at least $1/2$ apart, so below
$1/2$ the fewest codes is a sum over the small groups of states that may share codes, and in each case
the lower bound is a clique, of $256$, $226$ or $225$ states, replayed pair by pair. At $1/2$ a summary
needs $17$ codes, again with a clique. With discount $9/10$ the gentle rule needs $256$ codes at
$1/20$, $54$ at $1/10$, $26$ at $3/20$ and $15$ at $1/5$, while the original rule needs $225$ for
each of these bounds; all eight values are certified by cliques.

heavily against the unrestricted $21$. The registered weakness objective with greedy search gives

\subsection{Six beliefs}

The agent holds many beliefs, and the specification's product rule lets claims about one belief
carry over to several without enumerating the product. \code{Beliefs6} has $2^{48}$ states.

\begin{proposition}[Product rule]\label{prop:product}
Let $M_1,\dots,M_k$ be deterministic machines and let $M$ be their parallel composition, in which
every action either acts on all components at once or on exactly one of them, and the observation
distance of $M$ is the maximum of the components' observation distances. Then for every discount
and every horizon,
\[
\dbeh^M\bigl((x_i)_i,(y_i)_i\bigr)=\max_i\ \dbeh^{M_i}(x_i,y_i).
\]
Consequently a product encoding has the current, behavioral and radius defects of its component
encodings, its number of codes is the product of theirs, and its weakness under the product law is
the product of their weaknesses.
\end{proposition}

\begin{proof}
A word of $M$ acts on component $i$ through its projection, the subsequence of actions that reach
$i$, which is never longer than the word; discounting by length therefore gives at most the
component's own value, so the left side is at most the right. Conversely every word of $M_i$ lifts
to a word of $M$ of the same length, by replacing each component action with the corresponding
local or global action, and the lifted word produces the same observation difference in component
$i$. The supremum over words therefore commutes with the maximum over components. The same argument
applies word length by word length, which gives the horizon form.
\end{proof}

The oracle confirms the proposition on two copies of a sixteen-state memory, for both decay rules
and both discounts, over all $65536$ pairs. \code{CheckBehavioral Grid6 (Within 1/5)} is therefore
Checked from the component certificate, an exact computation that carries no assumptions. \Cref{tab:ex1bits} gives the cost of six beliefs.

\subsection{Forks and merges}

Agents fork: two processes take copies of a memory, hear different evidence, and later merge. The
receipt ledger models this with six receipts and union as the merge.
\begin{itemize}
\item \code{CheckNow Counts} is Checked: the counts determine the truth value.
\item \code{CheckUpdates Counts} is Refuted with the pair $(\{u_1\},\{u_2\})$ and the action
\code{hear-u1}, giving tallies $(1,0)$ against $(2,0)$. Hearing a receipt twice is harmless only if
one knows it is the same receipt.
\item \code{MeasureBehavioral Counts} is Checked with defect $1/3$, attained at
$(\{u_1,v_1\},\{u_2,v_2\})$.
\end{itemize}
A memory that kept only counts can still try to merge two forks, and the contracts measure how
badly each attempt fails.
\begin{itemize}
\item Adding the tallies has worst error $6/35$. \code{CheckImplementation AddMerge (Grade 1 1/6)}
is Refuted at $(\{u_1,u_2,u_3\},\{u_1,u_2,u_3\})$, which gives $(6,0)$ instead of $(3,0)$.
\item Taking the maximum also has worst error $6/35$; the witness is
$(\{u_1,u_2,v_1\},\{u_3,u_4,v_2\})$, which gives $(2,1)$ instead of $(4,2)$.
\item No rule on counts does better. If both forks hold the tally $(2,1)$, the true union may be
any of six tallies from $(2,1)$ to $(4,2)$, and no single tally lies within less than $6/35$ of all of
them.
\item A three-way merge from the fork base, which adds what each fork heard since the base, is
Refuted over all forks with worst error $6/35$; the least witness is the empty base with both forks
$\{u_1\}$, with error $2/15$. Restricted to forks whose new receipts are disjoint
(\code{CleanForks}) it is Checked with error $0$.
\end{itemize}
Forgetting an identity is safe only relative to what can happen next. A natural design keeps the
identities of receipts newer than the oldest open fork and compacts older receipts to counts. The
fork horizon takes care of merges: two forks opened after the compaction share the compacted part,
and merging them adds only newer receipts, which still carry their identities. It does not take care
of an old receipt that arrives again, through a delayed delivery, a retransmission, or a later
operation that names it. The ledger module declares such a compaction, with $u_1$ and $u_2$ below
the horizon, and a machine whose actions are those of a delivery protocol that never delivers them
again:
\begin{lstlisting}
  (Map compact (From Receipts) (To Compact)
    (Body ($r) (Tuple (PopCount (Slice $r 0 1)) (Slice $r 2 5))))
  (Representation Compacted (Of Ledger) (Encode compact))   ; every hear action allowed
  (Machine SettledLedger (States Receipts)                   ; u1 and u2 never arrive again
    (Observe strength ledger-strength (Values Dist01))
    (Observe confidence ledger-confidence (Values Dist01))
    (Action hear-u3 hear-u3) (Action hear-u4 hear-u4)
    (Action hear-v1 hear-v1) (Action hear-v2 hear-v2))
  (Representation CompactedSettled (Of SettledLedger) (Encode compact))
\end{lstlisting}
\begin{itemize}
\item On the ledger, where every hear action remains available, \code{CheckUpdates Compacted} is
Refuted with the pair $(\{u_1\},\{u_2\})$ and the action \code{hear-u1}. Both sets compact to one old
receipt and no newer ones. \code{hear-u1} leaves the first at one receipt and takes the second to two,
so the confidence becomes $1/5$ in one run and $1/3$ in the other, and no update on the compacted
codes can produce both. \code{CheckBehavioral Compacted (Within 1/10)} is Refuted with the same pair
and the same one-action word, a gap of $2/15$, and \code{MeasureBehavioral Compacted} is Checked with
defect $1/6$.
\item \code{SettledLedger} has exactly the operations of a protocol in which $u_1$ and $u_2$ are never
delivered again, for instance a delivery watermark at $u_2$ below which redeliveries are dropped,
with forks opened from the compacted state. On it \code{CheckUpdates CompactedSettled} is Checked and
\code{MeasureBehavioral CompactedSettled} is Checked with defect $0$.
\item A merge of two compacted forks that reads only their codes, taking the old count of the first
and the union of the newer identities (\code{CompactMerge}), is Refuted over all fork pairs, with worst
error $2/3$ and least witness $(\emptyset,\{u_1\})$ at error $1/2$. Restricted to forks that share the
compacted part (\code{CompactMergeSettled}) it is Checked with error $0$.
\end{itemize}
The design rule is therefore a statement about a protocol. Receipts older than the oldest open fork
may be compacted to counts when the protocol also ensures that none of them is delivered or named
again: a closed receipt namespace whose old receipts have all been delivered, a delivery watermark
that drops redeliveries below it, deduplication tombstones that keep the old identities in a cheaper
form, or the exclusion of old hear operations after compaction. The fork horizon is one part of such
a protocol, and the certificate holds for the operations declared: \code{compact} is exact on
\code{SettledLedger} and fails on \code{Ledger}.

\plain A count cannot tell a receipt that arrives a second time from a new one. Dropping the
identities of old evidence is safe only when the rest of the system promises that old evidence will
not arrive again, and the check has to be made against the operations that promise leaves open.

\subsection{Notes for implementers}

\paragraph{Undiscounted distances.} For a deterministic machine, the undiscounted distance of a
pair is the largest observation distance over the pairs reachable from it in the pair graph. A
strongly-connected-component pass over the pair graph computes it in linear time ($65536$ nodes and
$3\times65536$ edges here). Plain iteration also converges, after $15$ rounds under the original rule
and $23$ under the gentle one, but the number of rounds has no useful general bound.

\paragraph{Discounted and horizon distances.} Iterate from the observation distances until nothing
changes; with discount $9/10$ the iteration stops exactly after $12$ rounds here. Horizon $h$ is
exactly $h$ rounds.

\paragraph{Exact arithmetic.} Store distances as ranks into the sorted list of distinct values ---
$50$ values under the original rule and $1445$ under the gentle one --- and convert to rationals only
for results. Comparisons, maxima and the fixed point then run on small integers.

\paragraph{Certificates for a defect.} The upper bound is the distance table itself: one pass
confirms that each entry is at least the observation distance and at least the entry of each
successor pair. The lower bound is a replayed word.

\paragraph{Canonical witnesses.} A backward breadth-first search from the violating pairs gives the
shortest violating length of every pair in one pass. A forward search from the least pair at that
length, expanding actions in declaration order, then gives the canonical word.

\paragraph{Frontiers.} A satisfiability solver with clique-based symmetry breaking (the clique's
states fixed to distinct colors) solves each coloring instance here in under a second, and drat-trim
and \code{cake\_lpr} check each of the nine refutations in under a second as well. Under the
original rule no solver is needed below $1/2$: the pairs that may share a code fall into small groups,
every state of one group conflicts with every state of another, and the fewest codes and the largest
clique are sums over the groups. Partitions returned by an optimizer are not canonical, so the
manifest should record their properties --- the number of codes, the defect within the bound, the
kind of optimality certificate --- rather than the partition itself. A budget that ends before a
certificate is found yields Unknown, with the best clique bound in \code{Resources}; a refutation
whose proof is not replayed yields Conditional, with the solver's trusted-backend assumption.

\paragraph{Merges.} A merge reduces to translations. For a union merge, translation by single
receipts suffices, and those translations are exactly the \code{hear} actions: six checks instead
of sixty-four. A compaction that forgets identities must be checked on the machine of the declared
delivery protocol, whose actions are the operations still possible after compaction; checked on the
full ledger it fails.

\paragraph{Behaviors the fixtures pin down.} \code{If} evaluates only its chosen branch, and the
$t=0$ guards depend on it. \code{Quot} is floor division. The \code{Center} selector breaks ties by
declaration order. \code{Product} varies the last component fastest, which fixes the order of pairs
in witnesses. Codes are crisp by default, so update defects are $0$ or $1$.

\begin{itemize}
\item A \code{NatArith} library with \code{Le}, \code{Lt}, \code{Min}, \code{Max}, \code{Quot} and

\section{Example 2: auditing an access policy without enumeration}\label{sec:ex2}

\subsection{The problem}

Many organizations control access with roles. Users are assigned roles, roles carry permissions,
and a user exercises a permission by activating one of their roles in a session. In
\emph{administrative} role-based access control the assignments themselves are governed by rules:
an administrator may assign a role to a user only when preconditions hold, and revoking one role
may revoke others that depend on it \cite{rbac,arbac}. Separation of duty is the usual safety
requirement: no single person may both approve payments and audit them. Policies of this kind are
written by hand, grow by accretion, and are hard to audit. Each rule may look sensible on its own
while some sequence of individually legitimate administrative steps still reaches a configuration
that violates the requirement, and finding such a sequence by inspection is slow and unreliable. Analysis tools for
such policies exist \cite{stoller}; the example shows how the same questions are posed and
answered in MeTTaDinC, with certificates.

The organization has four users (alice, bob, carol, dave) and five roles (staff, clerk, approver,
auditor, admin). A user may hold a role (it is \emph{assigned}) and may have it \emph{active} in a
session. Permissions come only from active roles: read from staff, clerk, approver or auditor;
write from clerk or approver; approve from approver; audit from auditor; configure from admin.
The administrative rules are these.
\begin{itemize}
\item Two-person rule: assigning or revoking any role for user $u$ requires some \emph{other}
user with admin active.
\item Preconditions: clerk requires staff; approver requires clerk and not auditor; auditor requires
staff and not approver; admin requires staff.
\item Cascades: revoking staff removes every role of the user; revoking clerk also removes
approver.
\item Sessions: a role can be activated only if it is assigned, and approver and auditor are never
active together.
\end{itemize}
The state is a forty-bit word, ten bits per user: five assigned bits followed by five active bits,
bit $10u+r$ for ``$u$ holds role $r$'' and bit $10u+5+r$ for ``$u$ has $r$ active''. That gives about
$1.1\times10^{12}$ configurations, $80$ actions (four kinds, four users, five roles) and $20$
access observers (five permissions for four users).

The policy as written contains two plausible authoring mistakes. The approver rule checks whether
the user has auditor \emph{active} rather than \emph{assigned}, and revoking clerk forgets to remove
approver. The start configuration is the word $34672145$: alice holds staff and admin, with admin
active; bob holds staff and clerk, with clerk active; carol holds staff, active; dave holds nothing.

The findings, in brief:
\begin{itemize}
\item The policy as written has two holes, found by canonical witnesses of two and three steps.
\item The corrected policy is proved safe without enumeration. It reaches $38{,}418{,}640$
configurations, and $80$ small proofs cover them all; nothing near $2^{40}$ is ever listed.
\item The proof obligations are generated from the module itself, so the audit is about the policy
the module declares. Restoring either mistake in the source turns the corresponding proof into a
refutation, with the witness found for the policy as written.
\item A true property can come back Unknown, when its proof needs a stronger invariant than the
property itself. A counterexample to induction is not a refutation.
\item For a targeted question, slicing does most of the compaction: the state relevant to ``can bob
approve'' shrinks from forty bits to seventeen, and a vendor's ten-bit slice is refuted.
\item The full access interface has no exact compaction at all: forty short tests read off every
bit. The only exact saving is restriction to the reachable configurations, about $25.2$ bits'
worth.
\end{itemize}

\subsection{Background: proofs about a space that cannot be listed}

On a symbolic carrier (\spec{5.3}) states are bit vectors and maps are terms over registered
primitives such as bit access, Boolean connectives and bit setting. The checker never enumerates the
carrier; it turns each claim into proof obligations over the terms and discharges them with a
satisfiability solver or with binary decision diagrams.

\emph{Safety as a partition.} The audit states each safety requirement as a one-block
\code{BlockPartition} on the reachable scope \code{(Reach Policy (From start))}: the block is the set
of safe configurations, and the coverage obligation says that every reachable configuration lies in
it. \code{CheckBlockPartition} is a first-release request (\spec{16.1}).

\emph{Inductive invariants.} The reachable set is not known in advance, so coverage is proved by
induction. A set $I$ that contains the start configuration and is closed under every action is an
\emph{inductive invariant}; it contains every reachable configuration, and if it lies inside the
block, coverage holds. Each closure obligation, ``if $x\in I$ then $T_a x\in I$'', becomes one
satisfiability query: the solver is asked for an $x$ in $I$ whose successor leaves $I$. An
unsatisfiable answer, with a proof, discharges the obligation. A satisfiable answer is a
\emph{counterexample to induction}: a configuration from which one step leaves the set. It may be
unreachable, so it does not refute the claim (\spec{5.3}); a refutation needs a word from the start
configuration.

\emph{Proofs that a second program can check.} The obligations are encoded in conjunctive normal
form by the Tseitin transformation \cite{tseitin}, solved with CaDiCaL, and every unsatisfiability
proof is emitted in the DRAT format, converted to LRAT by drat-trim \cite{dratrim} and checked by
\code{cake\_lpr}, a proof checker verified in CakeML \cite{cakelpr}. This is the specification's
pinned pipeline (\spec{15.3}; guide, Section~1.8); trust rests on the verified checker, not on the
solver. A proof certifies the formula it was produced for, so the formula has to be generated from
the admitted module by the obligation generator, which the specification places inside the trusted
boundary; Section~\ref{sec:ex2notes} describes how the example's oracle generates the obligations
and tests the generator. A result whose proofs have not been replayed is Conditional on the solver
(Section~\ref{sec:statuses}).

\emph{Exact reachable sets.} For counting the scope exactly, binary decision diagrams
\cite{bryant} compute the reachable set as a fixed point of image computations. The image of a set
$R$ under a guarded update that sets bit $b$ to $v$ when the guard $g$ holds is
$(R\wedge\neg g)\vee((\exists b.\,R\wedge g)\wedge b=v)$, provided the guard does not read the bits it
writes.

\plain A proof by induction says that the policy never leaves the safe region because no single
step can leave it. When some single step can leave it, from some configuration, the proof has
failed, but the policy may still be safe: that configuration might never occur. Only a concrete
sequence of steps from the actual starting configuration shows that the policy is unsafe.

\subsection{The program}

The module uses the proposed \code{Families} library of indexed declarations. \code{Parameters}
on a map declares a family of maps indexed by elements of enumerated carriers; \code{(For \$v C)}
on an \code{Observe} or \code{Action} entry declares one entry per element; \code{Switch} selects on a
parameter, and \code{Exists} and \code{ForAll} range over an enumerated carrier. All of these are
expanded, and bit indices constant-folded, before checking. The order of the \code{For} clauses
fixes the canonical order of the $80$ actions: kind first, then user, then role. An excerpt of the
policy as written:

        (staff    True)

        (admin    (holds $u staff $x)))))

    (Body ($x) (If (And (other-admin $u $x) (may-receive $u $r $x))

          (Switch $r
            (staff    (drop $u staff (drop $u clerk (drop $u approver
                        (drop $u auditor (drop $u admin $x))))))

            (auditor  (drop $u auditor $x))
            (admin    (drop $u admin $x)))

    (Observe (read $u) (may-read $u) (For $u User))   ; write, approve, ... alike

    (Action (deactivate $u $r) (deactivate $u $r) (For $u User) (For $r Role)))
  (Const start Word 34672145)
  (Carrier Live (Of (BitVector 40)) (Reach Policy (From start)))
  (Machine SoDWatch (States Live) (Observe breach sod-breach)       ; PROPOSED field
    (ActionsOf Policy))
  (BlockPartition NoBreach (On Live)
    (Block Quiet (Body ($x) (Not (sod-breach $x))) start)
    (Successor Any Quiet Quiet))                                   ; PROPOSED Any
  ;; ClerksOnly and WellFormed alike
  ...)

The three safety requirements are separation of duty (\code{sod-breach}: some user holds both
approver and auditor), no approval without clerk (\code{clerkless-approval}: some user has approver
active without holding clerk), and well-formedness (\code{consistent}: every active role is
assigned, the role dependencies hold, and nobody holds approver and auditor together).
\code{SoDWatch} observes only its alarm and borrows the $80$ actions of the policy through the
proposed \code{ActionsOf} field, and the block partition says that the alarm is constant (off) on
the reachable scope, with every action keeping the block in itself.

\subsection{The corrected policy}

\emph{NoBreach is Checked.} The block is inductive on its own. The proof consists of $80$ closure

\subsection{Compaction}

\emph{The whole interface.} Whether some part of the configuration can be dropped without changing
any access decision is a quotient question.
\begin{itemize}
\item \code{CheckNow AssignmentsOnly} is Refuted with the pair $(0,32)$: the word $32$ has alice's
staff session active, so she can read, and the word $0$ does not, although both have no assignments.
\item \code{WholeInterface} is Checked, and the quotient is discrete: no two of the $2^{40}$ words
behave alike. The certificate is a set of forty tests, one per bit. Each is a word of at most five
actions followed by one query, whose answer equals that bit for every word. For instance,
\code{(deactivate alice auditor) (deactivate alice approver) (activate alice approver)} followed by
\code{approve(alice)} reads alice's approver assignment. Each test is proved by one satisfiability
query, generated from the module, whose proof is replayed.
\item \code{LiveInterface} is discrete as well, with $38{,}418{,}640$ classes, one per reachable
configuration.
\end{itemize}
So the only exact saving is the scope. Storing each user as an index into their $79$ well-formed
configurations takes seven bits per user, $28$ in all, and loses nothing.

\emph{A targeted monitor.} A monitor that only answers ``can bob approve'' needs much less.
\begin{itemize}
\item The cone of influence of \code{approve(bob)} has seventeen bits: bob's five assigned bits and
his approver, auditor and admin sessions, together with every other user's staff assignment, admin
assignment and admin session. The two-person rule is what makes the other users' admin state
matter for bob. The cone is the same under both policies. It is computed from the supports of the
elaborated update terms, and it is exactly the set of bits that the module's encoding
\code{bob-cone} gathers.
\item \code{BobSlice} is Checked: every update term of a cone bit reads only cone bits, an exact
computation on the elaborated terms. The sliced machine has $2^{17}$ states; $34$ of the $80$ actions
act on it and the others act as the identity. As a second certificate, all $80$ two-copy
obligations, which say that two words agreeing on the cone have successors agreeing on the cone, are
unsatisfiable (the largest has $178$ variables and $312$ clauses), and their proofs are replayed.
\item The vendor's slice \code{BobOnly}, bob's own ten bits, fails. Its defects are $0$ now, $1$
for updates and $1$ behaviorally. \code{InduceExact} is Refuted on the update obligation with the
pair $(0,512)$, where $512$ is alice's admin session, and the action \code{(assign bob staff)}: bob's

\subsection{Notes for implementers}\label{sec:ex2notes}

\paragraph{Build every obligation from the source.} The oracle reads \fpath{access_policy.metta} with
a small reader, resolves the imports (a name is looked up in the module that declares the map being
elaborated), expands the \code{Families} forms, folds the bit indices, and elaborates every map into
\code{Bool} or \code{Word} into a typed intermediate form: Boolean terms over the bits of one word,
with the declared \code{From} and \code{To} types checked, and for each action its normal form ``if
$g$ then set these bits''. The CNF encoder, the evaluator that finds and replays witnesses, and the
decision diagrams all read this one form, so a change to the module reaches all three.

\paragraph{Validate the encoding point by point.} On the two-user instance of the same source, with
the \code{User} carrier restricted to alice and bob and twenty bits of state, a direct interpreter
of the source terms, the intermediate form and the generated CNF agree on every one of the $2^{20}$
words, for each of the $80$ actions of the two modules, $26$ queries and alarms, and $240$ closure
obligations. The CNF side is evaluated by propagating the inputs through the recorded gates, after a
structural check that the gate clauses admit exactly one extension of every input assignment, so
that whether an obligation is satisfiable from a given word can be read off directly. At forty bits
the interpreter and the intermediate form agree on a sample of $50{,}119$ words, which includes every
configuration within two steps of \code{start}, and the closure obligations of \code{NoBreach} and
\code{ClerksOnlyProved} agree with them on $20{,}000$ of those words.

\paragraph{Mutate the source.} Restoring the first mistake in the corrected module, so that the
approver rule reads the auditor session again, turns \code{NoBreach} from Checked into Refuted, with
the witness \code{(assign bob auditor) (assign bob approver)} and the state $34684433$ replayed on
the mutated source; the closure obligations that change are exactly the four approver assignments.
Restoring the second, so that revoking clerk keeps approver, refutes \code{ClerksOnlyProved} with the
three-step witness of the policy as written and leaves \code{NoBreach} Checked. A separate model of
the policy would notice neither mutation, because it does not read the module.

\paragraph{Keep an independent model as a differential check.} The bundle's hand-written Python
policy and encoder do not read the module. They agree with the source on every word of the two-user
instance and on the forty-bit sample, the hand-written closure obligations of the corrected policy
are unsatisfiable as well, their decision diagrams give the same reachable sets, and their
obligations agree with enumeration: all $240$ closure obligations at twenty bits and all $2400$
two-copy obligations at ten bits. Under either mutation the comparison fails at the first
affected word, for instance at word $524298$ under the first, where alice holds clerk and auditor and
bob has admin active.

\paragraph{Expand families first.} Four action schemas give $80$ actions and five observer schemas
give $20$ observers. The obligation generator only ever sees expanded, constant-folded terms.

\paragraph{Closure obligations are independent and small.} None has more than $104$ variables, so
they can run in parallel. Hash shared structure, and emit byte-identical conjunctive normal form for
identical obligations, so that certificates are reproducible.

\paragraph{Report a failed induction step with care.} A satisfiable induction step goes in
\code{Resources}, as a counterexample to induction, and never in \code{Witness}. Refute only with a
reachable word found by a search in canonical order.

\paragraph{Minimize solver models before reporting them.} Solvers return arbitrary models; for the
written policy the first counterexample to induction came back as a thirteen-digit word. Fix bits from
the most significant down, which costs at most forty extra calls, to obtain the least model; for
\code{NoBreach} on the policy as written it is the word $10752$ with \code{(assign bob approver)}.

\paragraph{Images for guarded updates.} The image formula for guarded set and clear updates holds
only when the guard does not read the bits it writes, so check that condition when expanding the
terms.

\paragraph{Say which evidence backs each number.} Scope sizes come from recomputing the decision
diagrams. The satisfiability path proves only that the scope lies inside the invariant, so the
result should state which kind of evidence supports each number it reports, and its assurance:
\code{Exact} for the decision diagrams, \code{Replayed} for replayed proofs, \code{Witness} for
replayed refutations, \code{TrustedBackend} for a solver answer taken on trust.

\paragraph{Cones of influence.} Take the support of each update term and close it under all actions;
the result is sound and cheap to compute. Guard bits count as reads, and that is exactly what the
vendor's slice missed.

\paragraph{Minimizing an interface on $2^{40}$ words.} Take the cone, enumerate the $2^{17}$-state
slice, refine it, and lift the blocks back as predicates over the cone bits. Coverage and
disjointness of the lifted blocks then hold by construction.

\paragraph{The proof pipeline needs one setting.} The default heap and stack of \code{cake\_lpr}
($4096$ MiB each) could not be allocated on a seven-gigabyte machine; the flags
\code{--CML\_HEAP\_SIZE=1024 --CML\_STACK\_SIZE=512} work, and the guide's pipeline command should
include them. The proofs are a few hundred bytes of DRAT each, and all $619$ were checked in about
twenty-five seconds. The solver here is CaDiCaL $1.5.3$ through python-sat rather than the pinned
binary; since only the obligation generator and \code{cake\_lpr} are trusted, the solver's version
appears only in the trusted-backend assumption of a result whose proofs were not replayed.

\section{Example 3: sharing skills between robots with different camera frames}\label{sec:ex3}

\subsection{The problem}

Robots that share skills rarely share a body. Their cameras are mounted differently, their
grippers differ, and a command that means ``forward'' for one means ``left'' for another. A skill
learned by one robot can be used by another only through a translation of states and commands,
and a library of such translations becomes a network: some are calibrated, some are learned from
recorded behavior, and composing them around a loop should bring a skill back unchanged, or at
least changed in a way nobody minds. The specification's skill-transfer laboratory states the
claims for this setting (\spec{13.3}); this example works them out on a problem with enough
geometry to be instructive.

Three warehouse robots work in identical $5\times5$ bays. The goal is at the center, cell $(2,2)$,
counting rows from the top and columns from the left, and pillars stand in rows $1$ and $3$ of the
two outer columns. Each robot sees the bay through its own camera and issues the commands
\emph{up}, \emph{right}, \emph{down} and \emph{left} in its own image frame. Robot A's camera is
aligned with the bay, robot B's is turned a quarter turn clockwise, and robot C's sees the bay
transposed. A move earns $1$ if it brings the robot closer to the goal, $1/2$ if the distance is
unchanged (a wall or a pillar blocks the move), and $0$ if it moves away. Each robot has $21$ free
cells.

The shared library has three transfers. AB and BC come from camera calibration. CA was learned by
matching recorded responses: the matcher took the first frame change under which every translated
command earned the recorded reward.

The findings, in brief:
\begin{itemize}
\item A learned transfer is fixed only up to the task's symmetries. The learned CA is one of four
candidates that are all exactly right, and going around the cycle A, B, C, A returns every cell as
its up-down mirror image.
\item Whether that is acceptable depends on the declared gauge, the group of response symmetries
each robot is allowed to absorb. With no gauge the library is refuted; with the task's symmetry
group it is coherent.
\item A gauge copied unchanged from one robot to the next is wrong; it must be transported into
each robot's frame. The checker catches the copied gauge on the intertwining condition.
\item A skill sent around the loop earns, at each cell, what the original earns at the mirrored
cell. A's greedy skill comes back changed at $5$ of its $21$ cells and earns the same reward at
every cell, because its rewards are symmetric under the mirror; the skill that always moves up comes
back as the skill that always moves down, and its reward changes at $12$ cells.
\item A new requirement that breaks a symmetry exposes the stale transfer, with a one-move witness,
and re-learning repairs the library up to a smaller gauge.
\item A pallet in one bay makes transfers into that bay approximate, and makes the transfer out of
it ill-typed. No hive claim covers that case yet.
\end{itemize}

\subsection{Background: transfers, symmetries, holonomy and gauges}\label{sec:ex3background}

A \emph{method system} has states, methods (here, commands) and a response $r(x,m)$, the reward
of method $m$ in state $x$. A \emph{transfer} from system $i$ to system $j$ has two parts: a
\emph{state pullback} $\varphi$, which maps each state of $j$ to the state of $i$ that it
corresponds to, and a \emph{method pushforward} $\iota$, which maps each method of $i$ to a method of
$j$. The transfer is exact when the target, given the translated command, earns what the source
earns at the corresponding state:
\[
r_j\bigl(y,\iota(m)\bigr)=r_i\bigl(\varphi(y),m\bigr)\quad\text{for every target state $y$ and source method $m$.}
\]
Otherwise its defect is the largest difference over all pairs, measured as the total-variation
distance between reward laws (\code{RewardLawTV}, the default) or as the difference of expected
rewards (\code{ExpectedReward}). With these directions a transfer is a morphism of polynomial
functors (\spec{10.2}; \cite{poly}), and composition follows that structure: pullbacks compose in
the reverse order of the transfers and pushforwards in the same order.

A \emph{symmetry} of a method system is a pair of permutations $(g_S,g_M)$ of states and methods
with $r(g_Sx,g_Mm)=r(x,m)$ for every state and method. The symmetries of a system form a group.

Composing the transfers around a cycle that starts and ends at one member gives a transfer from that
member to itself, the \emph{holonomy} of the cycle. If the holonomy is the identity, a skill comes
back unchanged. If it is a symmetry $(g_S,g_M)$, a skill $\pi$, which chooses a method $\pi(x)$ in
each state, comes back as $\pi'(x)=g_M^{-1}\pi(g_Sx)$, and the symmetry condition gives
\[
r\bigl(x,\pi'(x)\bigr)=r\bigl(g_Sx,\pi(g_Sx)\bigr)\quad\text{for every state $x$:}
\]
the returned skill earns at $x$ what the original earns at the corresponding state $g_Sx$. This is
what the \code{TransportSkill} request certifies, equality at the pulled-back state. It does not give
$r(x,\pi'(x))=r(x,\pi(x))$. Three statements have to be kept apart. Performance at correspondingly
transformed states is kept by every transported skill. Performance at the same state is kept by a
skill whose reward profile $x\mapsto r(x,\pi(x))$ is invariant under the gauge. Expected performance
from a start law that the gauge leaves unchanged is kept by every skill, because such a law gives
$x$ and $g_Sx$ the same weight. A \emph{gauge} declares, for each member, a group of symmetries that the library is allowed to absorb,
and a \emph{transfer hive} is coherent up to its gauge when every edge is exact, every declared
gauge element is a symmetry, the gauges agree along the edges, and every holonomy lies in the gauge
of its base member (\spec{10.4}). Agreement along an edge is the \emph{intertwining} condition:
conjugating the target's gauge by the edge must give the source's gauge,
$\iota^{-1}G_j\,\iota=G_i$ on methods and likewise on states. A gauge is a statement about a frame,
so the same symmetry looks different in different frames, and a gauge declared in one robot's frame
has to be carried into the others.

Kernel hives are the second kind of hive (\spec{10.4}). Each member carries a tolerance on its
states, here the response tolerance that identifies cells with identical rows of rewards, and the
transfers induce cross kernels between members. The hive is coherent when the combined kernel on the
disjoint union of the members' states is transitive in the \L{}ukasiewicz sense; the
\emph{consensus cost} measures how much closing it under transitivity would identify. A derived
kernel hive can be \emph{saturated} by the gauge, which first identifies states related by gauge
symmetries. The two kinds of hive make different claims: a transfer hive identifies states, a
kernel hive identifies response classes.

\plain A transfer is a dictionary between two robots' points of view. Going around a loop of
dictionaries can return a word with a different meaning; the question is whether the difference is
one the task cannot see. The gauge is the list of differences each robot has agreed not to care
about, and that list has to be written in each robot's own terms. A skill that comes back through
such a loop does at each position what the original did at the mirrored position; that is the same
as what the original did at the same position only for a skill that looks the same in the mirror.

\subsection{The dihedral picture}

The eight symmetries of the square --- the identity, three rotations, and four mirrors --- act on
cells and on directions. Write $r_{90}$ for a clockwise quarter turn on the screen,
$(r,c)\mapsto(c,4-r)$, and $m_v$, $m_h$, $m_d$, $m_a$ for the left-right mirror, the up-down mirror,
the transpose and the anti-transpose. The progress task is invariant under four of them,
\[
K=\{\mathrm{id},\ r_{180},\ m_v,\ m_h\},
\]
because the bay itself has exactly these symmetries: the goal is central and the pillars are placed
symmetrically about both axes, but not about the diagonals. $K$ is a subgroup of index two, hence
normal, so it is the same set of transformations in every robot's frame. Its two single-mirror
subgroups are not frame independent: a quarter turn exchanges the left-right and the up-down mirror.

\emph{The candidates for CA.} The exact transfers from C to A are exactly the calibrated transfer
composed with an element of $K$, so there are four:
\begin{itemize}
\item $m_d$, the calibrated transfer;
\item $r_{90}$, the learned one, which equals the calibrated pullback composed with A's up-down
mirror: $m_d\circ m_h=r_{90}$;
\item $r_{270}$ and $m_a$, the other two.
\end{itemize}
\emph{The holonomy.} Composing the transfers A to B to C to A gives the identity with the calibrated
CA, and the up-down mirror on both cells and commands with the learned CA.

\subsection{A skill around the loop}

A's greedy skill takes the first improving command in the order \emph{up}, \emph{right},
\emph{down}, \emph{left}. Sent from A to B to C and back to A, it returns changed at $5$ of its $21$

Section~\ref{sec:ex3background}: at every cell $x$ of A, the returned skill earns what the greedy
skill earns at the mirrored cell $m_h(x)$. The greedy skill earns the same at a cell and at its
mirror image, since its reward profile is symmetric under the up-down mirror, so for it the returned
skill also earns the same reward at every cell.

That second property is a property of the greedy skill. The skill that always moves up,
\code{always-up} in the module, comes back as the skill that always moves down; \code{UpRoundTrip} is
Checked and reports the skill changed at all $21$ cells. At $(3,2)$, just below the goal, the
original earns $1$ and the returned skill $0$; at $(1,2)$, just above it, the reverse; in all, the
reward at the same cell changes at $12$ of the $21$ cells. The certified identity holds all the
same: at $(3,2)$ the returned skill earns what \code{always-up} earns at $(1,2)$. Averaged over the
$21$ cells with equal weight, a law that the mirror leaves unchanged, both skills earn $1/2$ per move;
started from $(3,2)$ alone, they earn $1$ and $0$. ``Coherent up to the gauge'' therefore means that
the skills that come back are the originals composed with a symmetry of the task: as good as the
originals under any start law the symmetry preserves, and cell by cell only when the original's
rewards are themselves symmetric.

\subsection{Notes for implementers}

\paragraph{Group elements.} Store each element as a pair of permutations, of states and of commands.
Generate a gauge by closure from its declared generators, and check the symmetry condition on the
generators only.

\paragraph{Obligation order and witnesses.} Check, in this order: edge exactness, edges in
declaration order, with the least target state and then the source command; the gauge generators,
with the least state and then the command; intertwining, edge by edge, reporting the first target
generator whose conjugate leaves the source gauge; and the holonomy, reporting the least moved state.

\paragraph{Holonomy composition order.} Follow the polynomial-functor composition order of the
specification: around the cycle, pullbacks compose right to left ($AB\circ BC\circ CA$) and
pushforwards left to right. The membership test is $(\varphi,\iota^{-1})\in G_{\mathrm{base}}$, with
$\varphi$ the composite pullback and $\iota$ the composite pushforward.

\paragraph{Intertwining for small and large groups.} For small groups, compare the conjugated method
groups as sets. For large ones, compare generating sets with a membership test such as
Schreier--Sims.

\paragraph{Report both holonomy witnesses, typed.} The transfer-hive witness $(0,0)\mapsto(4,0)$ and
the kernel-hive witness $(0,1)\mapsto(4,1)$ belong to different claims and must not be confused.

\paragraph{Saturation.} Compute the saturated kernel $\alpha\circ c\circ\alpha$ through equivalence
classes rather than by the naive four-fold loop. The $63$-node closure runs in exact
\L{}ukasiewicz arithmetic.

\paragraph{Interface digests.} Key every transfer and hive certificate by the digest of its response
map, so that the docking module can never reuse a progress certificate.

\paragraph{Pullback totality is an admission check.} It belongs to the subset carrier, so the pallet
bay's reverse transfer is InvalidInput before any response is compared.

\paragraph{Composing across metrics.} \code{ComposeTransfers} needs a single metric. An exact transfer
has defect $0$ under every metric, and for rewards in $[0,1]$ the expected-reward defect is at most the
total-variation defect; that conversion should be registered.

\paragraph{Say what a transported skill keeps.} \code{TransportSkill} certifies equality at the
pulled-back state. A report that a returned skill earns the same at the same state is a separate
claim: the invariance of the skill's reward profile under the holonomy, checked state by state. The
greedy skill has it and \code{always-up} does not.

\paragraph{Learned transfers.} Report every exact candidate. Choosing among them consistently around a
cycle is gauge fixing; here, choosing $m_d$ for CA makes the holonomy trivial.

\subsection{Proposed registry additions}

\begin{itemize}
\item \code{FindTransfers}: all exact transfers within a declared family of candidates, with their

\item \code{TransportSkill}: moves a skill table along a checked transfer, certifies that the

\section{Example 4: a market maker across regime shifts}\label{sec:ex4}

\subsection{The problem}

A market maker posts a price at which it will buy (the bid) and a price at which it will sell (the
ask), and earns the difference when both sides trade. Two forces work against it. Every fill changes
its inventory, and inventory is risk: a desk that has bought more than it sold is exposed to the
price falling. And some of the traders who take its quotes know more than it does, so that the
price tends to move against the desk right after it trades --- adverse selection, the subject of
the classical models of Glosten and Milgrom \cite{glosten} and of Kyle \cite{kyle}. A quoting policy
balances spread against both, and the balance depends on the market: how often each side trades,
how informed the flow is, whether one side dominates. Markets change regime often, and a policy and
its forecasts tuned in one regime are routinely carried into another. After a shift the desk needs
to know what changed, whether its policy still holds, what its own data can and cannot reveal, and
how to detect shifts without crying wolf. The specification's regime laboratory poses these
questions on a two-state example (\spec{13.4}); the market-making application treats typed regime
changes, certified transfer and selective repair at length \cite{marketmaking}. This example makes
them concrete on a model small enough to solve exactly.

\emph{The desk.} The desk holds at most two lots either way, so its inventory $q$ lies in
$\{-2,\dots,2\}$. Each step it posts one of three quotes:
\begin{itemize}
\item \emph{tight}: one tick from the mid on both sides;
\item \emph{wide}: two ticks on both sides;
\item \emph{lean}: one tick on the side that reduces the position and two on the side that grows it;
when flat, lean is the same as tight.
\end{itemize}
At $\pm2$ lots the side that would grow the position is withdrawn, so at the limits lean is also the
same as tight. Each step, a buyer lifts the ask and a seller hits the bid, independently of each
other. A fill earns its offset in ticks minus the adverse-selection cost $\theta$ of the market, the
expected move against the desk after the fill. Holding $q'$ lots after the step costs $|q'|/4$ tick,
and the desk maximizes expected discounted profit and loss (P\&L) with discount $9/10$.

\emph{The markets.} In a calm market a one-tick quote fills with probability $1/2$ and a two-tick
quote with probability $1/8$, on each side, and fills carry no information. Fill probabilities that fall
geometrically with the distance from the mid are the usual simplification in models of limit-order
fills \cite{avellaneda}. \Cref{tab:ex4markets}
lists the four markets of the example.

The toxic market is also given in a finer form: each step independently carries an informed trader

The findings, in brief:
\begin{itemize}
\item In calm markets the desk can run on three risk buckets --- flat, one lot, two lots ---
because the bucket map is an exact quotient of the decision process, and the optimal policy works on
it at no loss.
\item Toxic flow cuts every value by more than half and changes no decision: the calm policy is
certified optimal in the toxic market. A monitor of fill rates is provably blind to this change.
\item One-sided buying breaks the compression on both of its obligations, each with a one-line
witness, and refutes the calm policy when the desk is one lot long. The broken symmetry survives as
an exact transfer between the buyers' and the sellers' markets.
\item Knowing which steps carry informed flow is worth about one tick of discounted P\&L. A signal that
is right nine times in ten, at $1/20$ tick per step, nets about a third of a tick, and evaluating it
as if the signal were the truth overstates it by $0.22$.
\item A desk that only quotes wide cannot tell from its own tape whether news has leaked: the two
models are trace equivalent but not bisimilar. A tight quote makes the leak visible, with a
two-step witness.
\item Each of two monitors is blind to one of the two shifts, and the blindness is an exact claim.
Detections on data are Estimated results with guarantees that hold however often the stream is
examined.
\end{itemize}

\subsection{Background: decision processes and their quotients}

A finite discounted decision process has states, actions, a transition kernel $P(x'\mid x,a)$, a
reward law for each state and action, and a discount $\gamma<1$. A stationary policy $\pi$ picks one
action per state, and its value solves the linear system
\[
V^\pi(x)=r\bigl(x,\pi(x)\bigr)+\gamma\sum_{x'}P\bigl(x'\mid x,\pi(x)\bigr)\,V^\pi(x'),
\]
where $r$ is the expected reward. With rational data the system can be solved exactly. Policy
iteration \cite{howardpi} alternates exact evaluation with improvement --- in each state, switch to an
action with a larger $Q(x,a)=r(x,a)+\gamma\sum_{x'}P(x'\mid x,a)V^\pi(x')$ --- and stops at an optimal
policy, which is certified by the values together with the table of $Q$-values: the policy is optimal
exactly when no $Q(x,a)$ exceeds $Q(x,\pi(x))$.

The registry's \code{Decisions} library has one-step decision models only. The example proposes a
\code{DecisionProcess} declaration and gives it a second reading: a decision process \emph{is} a
stochastic machine whose observations are the expected rewards of its actions, one query per action.
With that reading the core requests apply unchanged. \code{InduceExact} on a representation of a
decision process checks that states with the same code have equal expected rewards for every action
and push equal probability onto every code; that is the definition of a stochastic bisimulation of
the process \cite{givan}, or a homomorphism onto the quotient \cite{ravindran}, and such a quotient
preserves optimal values and optimal policies. \code{CheckAbstractionMap} between two processes
checks a homomorphism, and \code{MeasureBehavioral} measures the Kantorovich behavioral distance of
the reward interface, the stochastic version of the distance of Section~\ref{sec:defects}
\cite{desharnais,vbw,ferns}.

\begin{proposition}[Policies pull back along homomorphisms]\label{prop:pullback}
Let $h$ map the states of a decision process $M$ onto those of a process $N$ with the same actions,
so that $r_M(x,a)=r_N(hx,a)$ and $\sum_{x':hx'=y}P_M(x'\mid x,a)=P_N(y\mid hx,a)$ for every $x$, $a$ and
$y$. Then for every stationary policy $\pi$ of $N$, $V_M^{\pi\circ h}=V_N^\pi\circ h$; moreover
$V_M^*=V_N^*\circ h$, and $\pi\circ h$ is optimal for $M$ whenever $\pi$ is optimal for $N$.
\end{proposition}

\begin{proof}
Put $W=V_N^\pi\circ h$. For every $x$, with $a=\pi(hx)$,
\[
r_M(x,a)+\gamma\sum_{x'}P_M(x'\mid x,a)\,W(x')=r_N(hx,a)+\gamma\sum_yP_N(y\mid hx,a)\,V_N^\pi(y)=V_N^\pi(hx)=W(x),
\]
grouping the successors $x'$ by $y=hx'$. So $W$ solves the evaluation equation of $\pi\circ h$ in $M$,
whose solution is unique for $\gamma<1$. The same computation with a maximum over actions shows that
$V_N^*\circ h$ solves the Bellman optimality equation of $M$, so it equals $V_M^*$, and $\pi\circ h$
attains it when $\pi$ attains $V_N^*$.
\end{proof}

\begin{proposition}[Averaging a fresh hidden factor]\label{prop:fresh}
Let a decision process have states $(x,h)$, and suppose that in every transition the hidden component
of the successor is drawn from a fixed law $\mu$, independently of the visible component of the
successor and of the current state and action, and that the start law also has $h\sim\mu$ independent
of $x$. Let $\bar P(x'\mid x,a)=\sum_h\mu(h)P(x'\mid(x,h),a)$ and $\bar r(x,a)=\sum_h\mu(h)r((x,h),a)$.
Then for every policy that chooses actions from the visible history:
\begin{enumerate}
\item the visible states and actions $(x_0,a_0,x_1,a_1,\dots)$ have the same joint law in the process
and in the averaged process $(\bar P,\bar r)$;
\item given the visible history $(x_0,a_0,\dots,x_t)$ and the action $a_t$, the conditional mean of the
reward at time $t$ is $\bar r(x_t,a_t)$ in both processes;
\item hence the expected reward at every time, and the expected discounted return, are the same in
both.
\end{enumerate}
In particular the best coarse policy is the optimum of the averaged process, and memoryless coarse
policies lose nothing. The law of the full-state expected reward $r((x_t,h_t),a_t)$ is not
preserved: it depends on $h_t$, which the averaged process replaces by its mean.
\end{proposition}

\begin{proof}
By induction on time, the hidden component $h_t$ is independent of the visible history
$(x_0,a_0,\dots,x_t)$ and has law $\mu$: at $t=0$ by the start law, and afterwards because it is
redrawn independently at each transition. The action $a_t$ depends only on the visible history, so
$h_t$ is independent of that history and $a_t$ together. Given both, the conditional mean of the
reward is $\sum_h\mu(h)r((x_t,h),a_t)=\bar r(x_t,a_t)$, which is the second statement, and the law of
$x_{t+1}$ is $\sum_h\mu(h)P(\cdot\mid(x_t,h),a_t)=\bar P(\cdot\mid x_t,a_t)$. By induction the visible
process is the averaged chain under the same policy, which is the first statement. The third follows
by taking expectations of the second, which depend only on the law of $(x_t,a_t)$, and summing with
the discount. The optimum of the averaged process over history-dependent policies is attained by a
stationary policy, which is a memoryless coarse policy. Finally, given the visible history the
expected reward $r((x_t,h_t),a_t)$ is a function of $h_t$ whose law is the image of $\mu$, while the
averaged process has the single value $\bar r(x_t,a_t)$; the two laws agree only when
$r((x_t,h),a_t)$ is the same for every $h$ in the support of $\mu$.
\end{proof}

In the example the hidden factor is the flow type, with $\mu$ the law \code{Half}. At the state $-2$
with a tight quote, the expected reward is $1/8$ with noise traders and $-3/8$ with an informed trader,
each with probability $1/2$, while the averaged model has the constant $-1/8$: the means agree and the
laws do not. The oracle checks the three statements exactly, for the calm policy and for a policy that
quotes wide whenever the inventory has just moved: the joint laws of the visible states and actions
through three steps coincide, the conditional mean of the reward given every visible history is the
averaged reward, and the expected discounted return of the calm policy from flat is $2181/704$ in
both processes.

Without freshness the proposition fails: if the hidden factor persists, the visible history carries
information about it, and memory or randomization can beat every memoryless coarse policy
\cite{singhpomdp}. The proposed \code{AverageModel} on processes therefore checks freshness, by
enumeration, before it answers.

\emph{Averaging.} \code{CheckEqual} applied to \code{(AverageModel Split (Through Coarse) (Under Half))}
and \code{ToxicDesk}, with \code{(Compare Means)}, is Checked: the averaged process has exactly the

\subsection{Did the news leak?}

\paragraph{Background.} For a stochastic machine, behavioral equivalence and trace equivalence are
different claims (\spec{4.3} and~7.2). Two states are \emph{trace equivalent} when every sequence of
observations has the same probability from both, under every sequence of actions; equivalently, under
every policy that chooses actions from what it has observed. They are \emph{bisimilar} when, in
addition, their futures branch alike: a test that reads a predicted probability and reacts to it --- a
\emph{modal test} --- cannot separate them. A consumer that acts only on its own observations can
tell apart trace classes and nothing finer. Trace equivalence is decided by linear algebra: the functions $x\mapsto
P_x(y_0a_1y_1\cdots a_ky_k)$ span a space whose dimension is the size of the minimal linear realization,
the predictive-state dimension of the process \cite{schutzenberger,tzeng,psr,oom}. The specification's
mandatory seven-state chain has two states that are trace equivalent but not bisimilar, a trace
partition of six classes and a minimal linear realization of dimension five.

\paragraph{The model.} \code{NewsLeak} is a tape of nine states. In \code{leak} an informed trader
already knows the direction of an imminent move; in \code{embargo} nobody knows it yet. The informed
trader picks off a tight quote just before the move, and the desk reports \code{hit-up} or
\code{hit-down}; a wide quote is left alone. An embargoed release moves the price with no informed trade.

a parameter its data cannot fix. Quoting tight is a probe whose price is getting picked off. The
interface identity of a trace certificate includes the action set, so the wide-only certificate says
nothing about the desk that may also quote tight.

\subsection{Monitoring the shift}

\paragraph{Background.} A monitor watches a stream and should raise an alarm when the stream stops
looking like the null law, here the calm market, while keeping false alarms rare however long and
however often it looks. Fixed-sample tests do not have that property; anytime-valid procedures do
\cite{ramdas,howardcs}. The simplest is the likelihood-ratio e-process: multiply, observation by
observation, the probability of what was seen under a declared alternative divided by its probability
under the null. Under the null this product is a nonnegative martingale with initial value one, and
Ville's inequality \cite{ville} bounds the probability that it \emph{ever} reaches $1/\delta$ by
$\delta$. Several monitors run at once combine by a union bound, each with threshold $k/\delta$ for $k$
monitors, unless a joint procedure is declared (\spec{7.4}).

\begin{proposition}[Monitors are valid under any quoting policy]\label{prop:monitor}
Let each observation $o_t$ be drawn, given the past, from the law $N(c_t)$, where the context $c_t$ ---
for instance the posted quote --- is fixed before $o_t$ is drawn, by any rule depending on the past. Let
$E_T=\prod_{t\le T}A(c_t)(o_t)/N(c_t)(o_t)$ for a family of alternative laws $A(c)$. Then $E_T$ is a
nonnegative supermartingale with $E_0=1$, a martingale when each $A(c)$ is absolutely continuous with
respect to $N(c)$, and $\Pr\bigl(\sup_TE_T\ge1/\delta\bigr)\le\delta$.
\end{proposition}

\begin{proof}
Given the past and $c_{T+1}$, the expected value of the next factor is
\[
\sum_{o:\,N(c)(o)>0}N(c)(o)\,\frac{A(c)(o)}{N(c)(o)},
\]
the mass of $A(c)$ on the support of $N(c)$, which is at most one and equal to one under absolute
continuity. Ville's maximal inequality for nonnegative supermartingales gives the bound.
\end{proof}

The proposition explains the role of the context: each factor must use the law given the quote that
was standing when the outcome occurred. A monitor that used, say, the average fill law of the desk's usual
quotes would not be a martingale under an adaptive quoting policy.

\subsection{Notes for implementers}

\paragraph{Laws are exact finite maps} from canonical values to rationals, with zero masses dropped when
they are built. \code{Image} adds the masses of equal values and \code{Indep} multiplies supports. Carrier
closure is checked on supports: when the desk is two lots long the bid's law is \code{Coin 0}, so the
out-of-range inventory $3$ is never produced.

\paragraph{Decision processes reuse the machine checks.} The machine view's queries are the expected
rewards, one per action, with the declared value tolerance. Quotient checks are then MDP homomorphism
checks with no new algorithm. Equality of reward laws is a separate and stronger claim
(\code{Compare Laws}).

\paragraph{Policy iteration.} Evaluate exactly by Gaussian elimination over the rationals. Improve by
keeping the current action on ties and otherwise taking the first best action in declaration order,
which makes the reported policy canonical. The certificate is the vector of values and the table of
$Q$-values; replay checks $|S|$ linear equations and $|S||A|$ inequalities. The canonical witness of
\code{CheckOptimal} is the least state, the policy's action there, the first action in declaration order
with a larger $Q$-value, and both $Q$-values.

\paragraph{Policies through a representation.} \code{OptimizePolicy} enumerates the deterministic code
policies ($27$ for the buckets, $243$ for \code{Coarse}) and evaluates each in the full process. For larger
families it should report the best policy found and leave optimality Unknown unless the search was
exhaustive. Memoryless code policies are all the coarse policies there are only when the hidden part is
fresh; in general the problem is partially observable, memory and randomization can do better, and the
result must name its policy class.

\paragraph{Kantorovich distances in three stages.} A floating-point value iteration, with one small
linear program per pair and action, identifies for each pair the term that sets the distance and the
optimal couplings. An exact linear solve gives the candidate distances, and the couplings are
re-optimized exactly until they stop changing. Verification then solves an exact transport problem for
every pair and action (upper bounds) and an exact dual problem for every pair whose distance comes from a
future step (lower bounds). For a discount below one the verified fixed point is the distance. Supports
here have at most three points, so a rational simplex with Bland's rule \cite{bland} is enough.

\paragraph{The behavioral distance does not bound values.} The specification's operator combines the
present observation and the future with a maximum. It certifies equal values at distance zero, but no
constant $c$ gives $|V^*(x)-V^*(y)|\le c\,\dbeh(x,y)$ in general. Consider two chains whose reward gaps
are $\delta,\delta/\gamma,\delta/\gamma^2,\dots$ for $K+1$ steps, with $\delta/\gamma^K\le1$, and equal
afterwards: the distance stays at $\delta$, while the value gap is $(K+1)\delta$, and $K$ can be as large
as $\log(1/\delta)/\log(1/\gamma)$. A desk that needs a guarantee on value loss should check values
directly, as this example does, or use an additive metric, $d=\max_a(|\Delta r_a|+\gamma W_d)$, which
bounds value differences \cite{ferns}. The registry does not have one yet.

\paragraph{Sensors on processes.} Compute values on the hidden states, with a fresh reading drawn each
step. When the hidden part is fresh, optimize over policies on the code and the reading using the
posteriors given each reading. Never substitute the reading for the hidden state.

\paragraph{Trace claims.} Compute trace spaces by Krylov iteration over the operators
$M_{a,y}=M_a\,\mathrm{diag}([o=y])$ with exact rationals. The canonical trace-event witness is the
shortest word, words ordered by action declaration, and then the least sequence of observations in the
declaration order of the reports. A trace certificate is keyed by its interface, action set included.

\paragraph{Monitors.} Fix the context before the observation. Validity, blindness and chi-square are exact
results; the KL rate is irrational and stays outside every Checked claim. \code{Union} gives each of $k$
monitors the threshold $k$ divided by the level, and \code{Mixture} thresholds the average of the
e-values. Store the stream rather than the seed: random generators differ between implementations, and
the module pins the stream by its digest. The e-value at a crossing is an exact rational. A null with
unknown parameters, such as a calm market with estimated fill rates, needs a different procedure, for
example a mixture e-process, which the proposed library does not cover.

\paragraph{Interface identity.} Certificates are keyed by the digest of the process --- kernel, reward
law, discount and value tolerance. The calm policy is optimal in \code{CalmDesk} and in \code{ToxicDesk} by
two separate certificates.

The additions that extend what can be claimed are few. \code{WeakestWithin} with a codes objective and

that are vectors of values and tables of $Q$-values. \code{Detect} is the first request whose only status
is Estimated, and its result names the data source by digest. Each of these comes with an exact
algorithm on the scale of the examples and a replayable certificate, which is the standard every
registered claim must meet.

\subsection{Lessons for implementers}

Some lessons recur across the examples, often in different forms.

\emph{Claims that look alike are different claims.} Example~1 separates a summary, a cold store and a
memory that runs on its codes, with three different answers for the same encoding, and a compaction
that is exact for the operations a delivery protocol allows from one that is exact for every
operation. Example~2 separates
a failed induction step from a refutation. Example~3 separates a value pullback from a transfer, a
transfer hive from a kernel hive, with different witnesses for the same cycle, and what a returned
skill earns at the mirrored state from what it earns at the same state. Example~4 separates
averaging from quotienting, equal means from equal laws, and trace equivalence from bisimulation. In
every case the cheaper claim is true and the stronger one false, or the reverse, on the same input. An
implementation that lets one request stand in for another produces confident wrong answers, and the
registry's job is to keep the requests and their result types distinct.

\emph{Every certificate has two halves.} An upper bound and a lower bound, a coloring and a clique or a
refutation, couplings and potentials, values and a table of $Q$-values, a proof of closure and a
reachable word: each Checked or Refuted result in the examples rests on a pair of objects that a second
program can check, with arithmetic or, for a refutation or a proof of closure, with a verified proof
checker. Producing them is the hard part; replaying them is cheap, and it is what lets the trusted base
stay small. A result whose second half has not been replayed is Conditional, and its assumptions name
the solver that was trusted.

\emph{Canonical witnesses take deliberate work.} They come from breadth-first searches that expand
actions in declaration order, from minimizing solver models before reporting them, and from fixed
orders on pairs, classes and observation sequences. None of this is automatic, and every implementation
that wants to pass a manifest has to do it the same way.

\emph{Unknown is an answer.} A budget that ends, a property whose proof needs a stronger invariant, a
greedy search without a lower bound: each of these returns Unknown with what was learned in
\code{Resources}. Example~2's counterexample to induction is the clearest case, and its result is more
useful to the auditor than a false refutation or a silent failure would be.

\emph{Interface identity keys every certificate.} The docking response of Example~3, each market of
Example~4, and the action set of the news-leak desk all change the interface, and certificates for one
interface must never be consulted for another. Digests of the response maps, the kernels and the action
sets are the mechanism. Example~2 adds the source itself: its obligations are generated from the
module, each result records the module's digest, and a mutation of one rule changes exactly the
obligations of that rule.

\emph{Admission does real work.} A non-total state pullback (Example~3), a hidden factor that is not
fresh (Example~4), and a guard that reads the bits it writes (Example~2) are all caught before any claim
is evaluated. Checks of this kind are cheap and turn a wrong answer into an InvalidInput.

\emph{Avoid enumeration by structure, not by luck.} The product rule (Example~1), cones of influence and
symbolic proofs (Example~2), and freshness (Example~4) each replace an enumeration that would be
impossible or expensive by an argument with a certificate. A request whose structure falls outside such a
rule should return Unknown with a diagnostic rather than attempt the enumeration.

\emph{Data enters frozen.} The streams of Example~4 are stored with digests, and the Estimated results
name them. Exact claims are about models and Estimated claims about data, and the result envelope keeps
the two apart.

\subsection{Open questions the examples raise}

\begin{itemize}
\item A frontier for memories that run on their codes, where each candidate costs the fixed point of an
induced machine (Example~1).
\item Joint encodings outside the product rule, such as codebooks shared across beliefs (Example~1).
\item Graded transfer hives, for libraries whose transfers are only approximately exact, and a
gauge-fixing completion that chooses among exact candidates so that holonomies become trivial
(Example~3).
\item An additive behavioral metric for decision processes, whose distances bound differences of optimal
value (Example~4).
\item Declared policy classes for processes whose hidden state persists, where memory and randomization
matter (Example~4).
\item Monitors for nulls with unknown parameters, and confidence sequences for estimated rates
(Example~4).
\item Risk-sensitive objectives, for which equality of reward laws, and not only of means, becomes the
relevant check (Example~4).
\item Declarations of delivery protocols for memories that forget identities, so that the operations
a compaction is certified against are declared once instead of being written out as a restricted
machine (Example~1).
\item A verified obligation generator, which would turn the translation validation of Example~2 into
a proof that the generated formulas express the module's obligations (Example~2).
\end{itemize}

\section{Conclusion}\label{sec:conclusion}

The four examples began as tests of a specification and turned into something closer to design
reviews. In each of them the most useful output was not a number but a distinction the designer had been
collapsing without noticing --- between a summary of a memory and a cold store for it, between a
property that is false and one whose proof needs more than the property itself, between a skill
library that is wrong and one that is right only up to a mirror, between a market whose averages have
changed and one in which the things being averaged have changed. Keeping such distinctions apart, in a
form that a second program can check, is a modest job for a language. It is also a job that a great deal
of practical reasoning in AI systems currently does without, and the examples suggest that doing it
explicitly costs less than one might fear: every claim here was settled exactly or by a certificate that a
verified checker replays, most of them in seconds.

The examples are small on purpose, and they show nothing yet about deployed memories, policies, robots or
markets. Each would have to be scaled up, connected to real data through frozen snapshots and streams,
and run against a running system before it said anything about one. What they do show is how MeTTaDinC
programs are written and read, what their answers look like, and where the language runs out. The
registry additions they propose are the first concrete evidence about which parts are missing, and the
list of open questions is the first concrete evidence about which parts are hard.

The hope, in the end, is that the next person to write a MeTTaDinC program starts from one of these four
rather than from the fixtures, and finds that the language says what they need it to say --- or, failing
that, finds out quickly and precisely what it cannot say yet.

        (If (And (Le 4 (Add $p $n)) (Le (Mul 2 $p) $n)) Disbelieved Uncertain)))))

  ;; how it changes: evidence saturates at 15, decay halves and rounds down
  (Map add-pos (From Belief) (To Belief) (Cases ((Tuple $p $n) (Tuple (Min (Add $p 1) 15) $n))))
  (Map add-neg (From Belief) (To Belief) (Cases ((Tuple $p $n) (Tuple $p (Min (Add $n 1) 15)))))
  (Map halve   (From Belief) (To Belief) (Cases ((Tuple $p $n) (Tuple (Quot $p 2) (Quot $n 2)))))

  (Tolerance Dist01 (On Rational01) (OneMinusAbsoluteDifference))
  (Machine Decide (States Belief)                   ; the action-selection interface
    (Observe status status)
    (Action pos add-pos) (Action neg add-neg) (Action decay halve))
  (Machine Report (States Belief)                   ; the reasoning interface
    (Observe strength strength (Values Dist01))
    (Observe confidence confidence (Values Dist01))
    (Action pos add-pos) (Action neg add-neg) (Action decay halve))

  ;; candidate encodings: grid indices of the rounded truth value, count buckets, caps
  (Map tv-grid-20 (From Belief) (To (Tuple Nat Nat))
    (Cases ((Tuple $p $n)
      (Tuple (If (Eq (Add $p $n) 0) 10 (Quot (Add (Mul 40 $p) (Add $p $n)) (Mul 2 (Add $p $n))))
             (Quot (Add (Mul 41 (Add $p $n)) 4) (Add (Mul 2 (Add $p $n)) 8))))))
  (Map tv-grid-10 (From Belief) (To (Tuple Nat Nat))
    (Cases ((Tuple $p $n)
      (Tuple (If (Eq (Add $p $n) 0) 5 (Quot (Add (Mul 20 $p) (Add $p $n)) (Mul 2 (Add $p $n))))
             (Quot (Add (Mul 21 (Add $p $n)) 4) (Add (Mul 2 (Add $p $n)) 8))))))
  (Map tv-grid-10-7 (From Belief) (To (Tuple Nat Nat))
    (Cases ((Tuple $p $n)
      (Tuple (If (Eq (Add $p $n) 0) 5 (Quot (Add (Mul 20 $p) (Add $p $n)) (Mul 2 (Add $p $n))))
             (Quot (Add (Mul 15 (Add $p $n)) 4) (Add (Mul 2 (Add $p $n)) 8))))))
  (Map bucket7 (From Count) (To Nat)
    (Table (0 0) (1 1) (2 2) (3 3) (4 4) (5 4) (6 5) (7 5) (8 5) (9 5)
           (10 6) (11 6) (12 6) (13 6) (14 6) (15 6)))
  (Map buckets7 (From Belief) (To (Tuple Nat Nat))
    (Cases ((Tuple $p $n) (Tuple (bucket7 $p) (bucket7 $n)))))
  (Map cap7 (From Belief) (To (Tuple Nat Nat))
    (Cases ((Tuple $p $n) (Tuple (Min $p 7) (Min $n 7)))))

  (Representation StatusOnly  (Of Decide) (Encode status))
  (Representation RoundedTV20 (Of Report) (Encode tv-grid-20))
  (Representation RoundedTV10 (Of Report) (Encode tv-grid-10))
  (Representation Grid10x7    (Of Report) (Encode tv-grid-10-7))
  (Representation Buckets7    (Of Report) (Encode buckets7))
  (Representation Capped7     (Of Report) (Encode cap7))
  (Measure Uniform (On Belief) (Uniform))

  (Derive StatusRepair (Refine StatusOnly (Preserve Encoding) (Until Stable) (Under Uniform)))
  (Derive Staged2 (Refine StatusOnly (Preserve Encoding) (Until (Steps 2))))      ; PROPOSED Until form

(DC.Module ReceiptLedger
  (Profile Graded)
  (Use BitVectors Contracts NatArith)
  ;; bit i records receipt i: u1 u2 u3 u4 support the proposition, v1 v2 oppose it
  (Carrier Receipts (Of (BitVector 6)) (All))
  (Carrier Upto8 (Of Nat) (Enum 0 1 2 3 4 5 6 7 8))
  (Carrier Upto4 (Of Nat) (Enum 0 1 2 3 4))
  (Carrier Tally (Of (Tuple Nat Nat)) (Product Upto8 Upto4))
  (Map counts (From Receipts) (To Tally)
    (Body ($r) (Tuple (PopCount (Slice $r 0 3)) (PopCount (Slice $r 4 5)))))   ; PROPOSED PopCount
  (Map tally-strength (From Tally) (To Rational01)
    (Cases ((Tuple $p $n) (If (Eq (Add $p $n) 0) (Rat 1 2) (Div $p (Add $p $n))))))
  (Map tally-confidence (From Tally) (To Rational01)
    (Cases ((Tuple $p $n) (Div (Add $p $n) (Add (Add $p $n) 4)))))
  (Map ledger-strength   (From Receipts) (To Rational01) (Body ($r) (tally-strength (counts $r))))
  (Map ledger-confidence (From Receipts) (To Rational01) (Body ($r) (tally-confidence (counts $r))))
  (Map hear-u1 (From Receipts) (To Receipts) (Body ($r) (SetBit $r 0 1)))
  (Map hear-u2 (From Receipts) (To Receipts) (Body ($r) (SetBit $r 1 1)))
  (Map hear-u3 (From Receipts) (To Receipts) (Body ($r) (SetBit $r 2 1)))
  (Map hear-u4 (From Receipts) (To Receipts) (Body ($r) (SetBit $r 3 1)))
  (Map hear-v1 (From Receipts) (To Receipts) (Body ($r) (SetBit $r 4 1)))
  (Map hear-v2 (From Receipts) (To Receipts) (Body ($r) (SetBit $r 5 1)))
  (Map union (From (Product Receipts Receipts)) (To Receipts)
    (Body ($pair) (BitOr (GetTuple $pair 0) (GetTuple $pair 1))))               ; PROPOSED BitOr
  (Tolerance Dist01 (On Rational01) (OneMinusAbsoluteDifference))
  (Machine Ledger (States Receipts)
    (Observe strength ledger-strength (Values Dist01))
    (Observe confidence ledger-confidence (Values Dist01))
    (Action hear-u1 hear-u1) (Action hear-u2 hear-u2) (Action hear-u3 hear-u3)
    (Action hear-u4 hear-u4) (Action hear-v1 hear-v1) (Action hear-v2 hear-v2)
    (Merge merge union))
  (Representation Counts (Of Ledger) (Encode counts))

  ;; merging two forks that kept only counts
  (Carrier ForkPair (Of (Tuple (BitVector 6) (BitVector 6))) (Product Receipts Receipts))
  (Map merged-tally (From ForkPair) (To Tally) (Body ($pair) (counts (union $pair))))
  (Map add-tallies (From ForkPair) (To Tally)
    (Body ($pair) (Tuple (Add (GetTuple (counts (GetTuple $pair 0)) 0) (GetTuple (counts (GetTuple $pair 1)) 0))
                         (Add (GetTuple (counts (GetTuple $pair 0)) 1) (GetTuple (counts (GetTuple $pair 1)) 1)))))
  (Map max-tallies (From ForkPair) (To Tally)
    (Body ($pair) (Tuple (Max (GetTuple (counts (GetTuple $pair 0)) 0) (GetTuple (counts (GetTuple $pair 1)) 0))
                         (Max (GetTuple (counts (GetTuple $pair 0)) 1) (GetTuple (counts (GetTuple $pair 1)) 1)))))
  (Tolerance SameInput (On ForkPair) (Discrete))
  (Tolerance TallyDistance (On Tally)
    (Meet (Pullback tally-strength Dist01) (Pullback tally-confidence Dist01)))   ; PROPOSED Meet
  (Implementation AddMerge (Ideal merged-tally) (Actual add-tallies)
    (Audit ForkPair) (InputDistance SameInput) (OutputDistance TallyDistance))
  (Implementation MaxMerge (Ideal merged-tally) (Actual max-tallies)
    (Audit ForkPair) (InputDistance SameInput) (OutputDistance TallyDistance))

  ;; three-way merge from the fork base: exact only when the forks heard different receipts
  (Carrier Triple (Of (Tuple (BitVector 6) (BitVector 6) (BitVector 6))) (Product Receipts Receipts Receipts))
  (Map based (From Triple) (To Bool)
    (Body ($t) (And (Eq (BitAnd (GetTuple $t 0) (GetTuple $t 1)) (GetTuple $t 0))
                    (Eq (BitAnd (GetTuple $t 0) (GetTuple $t 2)) (GetTuple $t 0)))))
  (Carrier Forks (Of (Tuple (BitVector 6) (BitVector 6) (BitVector 6))) (Subset Triple based))
  (Map fresh-news (From Forks) (To Bool)
    (Body ($t) (IsZero (BitAnd (BitXor (GetTuple $t 1) (GetTuple $t 0))
                               (BitXor (GetTuple $t 2) (GetTuple $t 0))))))
  (Carrier CleanForks (Of (Tuple (BitVector 6) (BitVector 6) (BitVector 6))) (Subset Forks fresh-news))
  (Map fork-union (From Forks) (To Tally)
    (Body ($t) (counts (BitOr (GetTuple $t 1) (GetTuple $t 2)))))
  (Map three-way (From Forks) (To Tally)
    (Body ($t) (Tuple (Sub (Add (GetTuple (counts (GetTuple $t 1)) 0) (GetTuple (counts (GetTuple $t 2)) 0))
                           (GetTuple (counts (GetTuple $t 0)) 0))
                      (Sub (Add (GetTuple (counts (GetTuple $t 1)) 1) (GetTuple (counts (GetTuple $t 2)) 1))
                           (GetTuple (counts (GetTuple $t 0)) 1)))))
  (Tolerance SameTriple (On Forks) (Discrete))
  (Implementation ThreeWay (Ideal fork-union) (Actual three-way)
    (Audit Forks) (InputDistance SameTriple) (OutputDistance TallyDistance))
  (Implementation ThreeWayClean (Ideal fork-union) (Actual three-way)
    (Audit CleanForks) (InputDistance SameTriple) (OutputDistance TallyDistance))

  ;; compaction below a fork horizon: u1 and u2 are older than the oldest open fork, so only
  ;; their number is kept; the identities of u3, u4, v1 and v2 are kept
  (Carrier Upto2 (Of Nat) (Enum 0 1 2))
  (Carrier Recent (Of (BitVector 4)) (All))
  (Carrier Compact (Of (Tuple Nat (BitVector 4))) (Product Upto2 Recent))
  (Map compact (From Receipts) (To Compact)
    (Body ($r) (Tuple (PopCount (Slice $r 0 1)) (Slice $r 2 5))))
  (Representation Compacted (Of Ledger) (Encode compact))   ; every hear action still allowed
  ;; the delivery protocol after compaction: u1 and u2 are never delivered again (a delivery
  ;; watermark at u2 that drops redeliveries), and forks are opened from the compacted state, so
  ;; a merge adds only newer receipts; the machine has exactly the operations the protocol allows
  (Machine SettledLedger (States Receipts)
    (Observe strength ledger-strength (Values Dist01))
    (Observe confidence ledger-confidence (Values Dist01))
    (Action hear-u3 hear-u3) (Action hear-u4 hear-u4)
    (Action hear-v1 hear-v1) (Action hear-v2 hear-v2))
  (Representation CompactedSettled (Of SettledLedger) (Encode compact))
  ;; merging two forks from their compacted codes: the old count of the first, the union of the
  ;; newer identities; exact only for forks that share the compacted part
  (Map compact-merge (From ForkPair) (To Tally)
    (Body ($pair)
      (Tuple (Add (PopCount (Slice (GetTuple $pair 0) 0 1))
                  (PopCount (BitOr (Slice (GetTuple $pair 0) 2 3) (Slice (GetTuple $pair 1) 2 3))))
             (PopCount (BitOr (Slice (GetTuple $pair 0) 4 5) (Slice (GetTuple $pair 1) 4 5))))))
  (Map same-old (From ForkPair) (To Bool)
    (Body ($pair) (Eq (Slice (GetTuple $pair 0) 0 1) (Slice (GetTuple $pair 1) 0 1))))
  (Carrier SettledForks (Of (Tuple (BitVector 6) (BitVector 6))) (Subset ForkPair same-old))
  (Tolerance SameSettled (On SettledForks) (Discrete))
  (Implementation CompactMerge (Ideal merged-tally) (Actual compact-merge)
    (Audit ForkPair) (InputDistance SameInput) (OutputDistance TallyDistance))
  (Implementation CompactMergeSettled (Ideal merged-tally) (Actual compact-merge)
    (Audit SettledForks) (InputDistance SameSettled) (OutputDistance TallyDistance)))
;; @end

;; Example 2: auditing an administrative access-control policy on forty-bit words.
;; Two modules: the policy as written, and the corrected policy with the audit's
;; certificates, slices and quotients.  Forms marked PROPOSED need ex2_registry_patch.json.

;; @excerpt access-policy
(DC.Module AccessPolicy
  (Profile (Dynamics Deterministic) (Values Crisp) (Carriers Symbolic))
  (Use BitVectors Families)                         ; PROPOSED library: Parameters, For, Switch, Exists
  (Carrier Word (Of (BitVector 40)) (All))
  (Carrier User (Of Symbol) (Enum alice bob carol dave))
  (Carrier Role (Of Symbol) (Enum staff clerk approver auditor admin))
  (Map slot (From User) (To Nat) (Table (alice 0) (bob 10) (carol 20) (dave 30)))
  (Map rank (From Role) (To Nat) (Table (staff 0) (clerk 1) (approver 2) (auditor 3) (admin 4)))

  ;; bit 10u+r says that u is assigned r; bit 10u+5+r says that u has r active
  (Map holds (Parameters ($u User) ($r Role)) (From Word) (To Bool)
    (Body ($x) (Eq (BitAt $x (Add (slot $u) (rank $r))) 1)))
  (Map active (Parameters ($u User) ($r Role)) (From Word) (To Bool)
    (Body ($x) (Eq (BitAt $x (Add (Add (slot $u) 5) (rank $r))) 1)))
  (Map other-admin (Parameters ($u User)) (From Word) (To Bool)
    (Body ($x) (Exists $v User (And (Not (Eq $v $u)) (active $v admin $x)))))

  ;; the can-assign rules; as written, the approver rule reads the auditor session
  (Map may-receive (Parameters ($u User) ($r Role)) (From Word) (To Bool)
    (Body ($x)
      (Switch $r
        (staff    True)
        (clerk    (holds $u staff $x))
        (approver (And (holds $u clerk $x) (Not (active $u auditor $x))))
        (auditor  (And (holds $u staff $x) (Not (holds $u approver $x))))
        (admin    (holds $u staff $x)))))
  (Map grant (Parameters ($u User) ($r Role)) (From Word) (To Word)
    (Body ($x) (SetBit $x (Add (slot $u) (rank $r)) 1)))
  (Map drop (Parameters ($u User) ($r Role)) (From Word) (To Word)
    (Body ($x) (SetBit (SetBit $x (Add (slot $u) (rank $r)) 0) (Add (Add (slot $u) 5) (rank $r)) 0)))
  (Map assign (Parameters ($u User) ($r Role)) (From Word) (To Word)
    (Body ($x) (If (And (other-admin $u $x) (may-receive $u $r $x)) (grant $u $r $x) $x)))
  ;; revocation cascades along role dependencies; as written, revoking clerk keeps approver
  (Map revoke (Parameters ($u User) ($r Role)) (From Word) (To Word)
    (Body ($x)
      (If (other-admin $u $x)
          (Switch $r
            (staff    (drop $u staff (drop $u clerk (drop $u approver (drop $u auditor (drop $u admin $x))))))
            (clerk    (drop $u clerk $x))
            (approver (drop $u approver $x))
            (auditor  (drop $u auditor $x))
            (admin    (drop $u admin $x)))
          $x)))
  ;; sessions: approver and auditor are never active together
  (Map activate (Parameters ($u User) ($r Role)) (From Word) (To Word)
    (Body ($x)
      (If (And (holds $u $r $x)
               (Switch $r
                 (staff True) (clerk True) (admin True)
                 (approver (Not (active $u auditor $x)))
                 (auditor  (Not (active $u approver $x)))))
          (SetBit $x (Add (Add (slot $u) 5) (rank $r)) 1)
          $x)))
  (Map deactivate (Parameters ($u User) ($r Role)) (From Word) (To Word)
    (Body ($x) (SetBit $x (Add (Add (slot $u) 5) (rank $r)) 0)))

  ;; access decisions and the auditor's alarms
  (Map may-read (Parameters ($u User)) (From Word) (To Bool)
    (Body ($x) (Or (Or (active $u staff $x) (active $u clerk $x))
                   (Or (active $u approver $x) (active $u auditor $x)))))
  (Map may-write     (Parameters ($u User)) (From Word) (To Bool)
    (Body ($x) (Or (active $u clerk $x) (active $u approver $x))))
  (Map may-approve   (Parameters ($u User)) (From Word) (To Bool) (Body ($x) (active $u approver $x)))
  (Map may-audit     (Parameters ($u User)) (From Word) (To Bool) (Body ($x) (active $u auditor $x)))
  (Map may-configure (Parameters ($u User)) (From Word) (To Bool) (Body ($x) (active $u admin $x)))
  (Map sod-breach (From Word) (To Bool)
    (Body ($x) (Exists $u User (And (holds $u approver $x) (holds $u auditor $x)))))
  (Map clerkless-approval (From Word) (To Bool)
    (Body ($x) (Exists $u User (And (active $u approver $x) (Not (holds $u clerk $x))))))
  (Map well-formed (Parameters ($u User)) (From Word) (To Bool)
    (Body ($x)
      (And (ForAll $r Role (Or (Not (active $u $r $x)) (holds $u $r $x)))
        (And (Or (Not (holds $u clerk $x)) (holds $u staff $x))
          (And (Or (Not (holds $u approver $x)) (holds $u clerk $x))
            (And (Or (Not (holds $u auditor $x)) (holds $u staff $x))
              (And (Or (Not (holds $u admin $x)) (holds $u staff $x))
                (Not (And (holds $u approver $x) (holds $u auditor $x))))))))))
  (Map consistent (From Word) (To Bool) (Body ($x) (ForAll $u User (well-formed $u $x))))

  (Machine Policy (States Word)
    (Observe (read $u)      (may-read $u)      (For $u User))
    (Observe (write $u)     (may-write $u)     (For $u User))
    (Observe (approve $u)   (may-approve $u)   (For $u User))

\subsection{Example 3: \texorpdfstring{\fpath{skill_share.metta}}{skill\_share.metta}}

\begin{lstlisting}[style=mettafull]
;; Example 3: sharing navigation skills between robots whose cameras see the bay in
;; different frames.  Three modules: the progress task, the docking task, and a bay with
;; an extra pallet.  Forms marked PROPOSED need ex3_registry_patch.json (and NatArith from
;; ex1_registry_patch.json).

;; @excerpt skill-share
(DC.Module SkillShare
  (Profile Crisp)
  (Use Transfers Hives NatArith)
  (Carrier Coord  (Of Nat) (Enum 0 1 2 3 4))
  (Carrier Grid   (Of (Tuple Nat Nat)) (Product Coord Coord))
  (Carrier Dir    (Of Symbol) (Enum up right down left))
  (Carrier Reward (Of Rational) (Enum 0 (Rat 1 2) 1))

  ;; the dihedral group of the square, on cells (row from the top, column from the left)
  ;; and on image directions; r90 is a clockwise quarter turn on the screen
  (Map r90-cell  (From Grid) (To Grid) (Cases ((Tuple $r $c) (Tuple $c (Sub 4 $r)))))
  (Map r270-cell (From Grid) (To Grid) (Cases ((Tuple $r $c) (Tuple (Sub 4 $c) $r))))
  (Map mv-cell   (From Grid) (To Grid) (Cases ((Tuple $r $c) (Tuple $r (Sub 4 $c)))))   ; mirror left-right
  (Map mh-cell   (From Grid) (To Grid) (Cases ((Tuple $r $c) (Tuple (Sub 4 $r) $c))))   ; mirror up-down
  (Map md-cell   (From Grid) (To Grid) (Cases ((Tuple $r $c) (Tuple $c $r))))           ; transpose
  (Map ma-cell   (From Grid) (To Grid) (Cases ((Tuple $r $c) (Tuple (Sub 4 $c) (Sub 4 $r)))))
  (Map r180-cell (From Grid) (To Grid) (Cases ((Tuple $r $c) (Tuple (Sub 4 $r) (Sub 4 $c)))))
  (Map same-cell (From Grid) (To Grid) (Cases ((Tuple $r $c) (Tuple $r $c))))
  (Map r90-dir   (From Dir) (To Dir) (Cases (up right) (right down) (down left) (left up)))
  (Map r270-dir  (From Dir) (To Dir) (Cases (up left) (right up) (down right) (left down)))
  (Map mv-dir    (From Dir) (To Dir) (Cases (up up) (right left) (down down) (left right)))
  (Map mh-dir    (From Dir) (To Dir) (Cases (up down) (right right) (down up) (left left)))
  (Map md-dir    (From Dir) (To Dir) (Cases (up left) (right down) (down right) (left up)))
  (Map ma-dir    (From Dir) (To Dir) (Cases (up right) (right up) (down left) (left down)))
  (Map r180-dir  (From Dir) (To Dir) (Cases (up down) (right left) (down up) (left right)))
  (Map same-dir  (From Dir) (To Dir) (Cases (up up) (right right) (down down) (left left)))

  ;; the bay: goal at the centre, pillars at rows 1 and 3 of the outer columns
  (Map pillar (From Grid) (To Bool)
    (Cases ((Tuple $r $c) (And (Or (Eq $r 1) (Eq $r 3)) (Or (Eq $c 0) (Eq $c 4))))))
  (Map dist (From Grid) (To Nat)
    (Cases ((Tuple $r $c) (Add (If (Le $r 2) (Sub 2 $r) (Sub $r 2)) (If (Le $c 2) (Sub 2 $c) (Sub $c 2))))))
  (Map step (From (Product Grid Dir)) (To Grid)       ; blocked moves stay put
    (Cases
      ((Tuple (Tuple $r $c) up)
        (If (Eq $r 0) (Tuple $r $c)
          (If (pillar (Tuple (Sub $r 1) $c)) (Tuple $r $c) (Tuple (Sub $r 1) $c))))
      ((Tuple (Tuple $r $c) down)
        (If (Eq $r 4) (Tuple $r $c)
          (If (pillar (Tuple (Add $r 1) $c)) (Tuple $r $c) (Tuple (Add $r 1) $c))))
      ((Tuple (Tuple $r $c) left)
        (If (Eq $c 0) (Tuple $r $c)
          (If (pillar (Tuple $r (Sub $c 1))) (Tuple $r $c) (Tuple $r (Sub $c 1)))))
      ((Tuple (Tuple $r $c) right)
        (If (Eq $c 4) (Tuple $r $c)
          (If (pillar (Tuple $r (Add $c 1))) (Tuple $r $c) (Tuple $r (Add $c 1)))))))
  (Map progress (From (Product Grid Dir)) (To Reward)  ; 1 closer, 1/2 no change, 0 farther
    (Body ($xm)
      (If (Lt (dist (step $xm)) (dist (GetTuple $xm 0))) 1
        (If (Eq (dist (step $xm)) (dist (GetTuple $xm 0))) (Rat 1 2) 0))))

  ;; three robots: A's camera is aligned with the bay, B's is turned a quarter turn
  ;; clockwise, C's sees the bay transposed; each commands moves in its own image frame
  (Map free-A (From Grid) (To Bool) (Body ($y) (Not (pillar $y))))
  (Map free-B (From Grid) (To Bool) (Body ($y) (Not (pillar (r270-cell $y)))))
  (Map free-C (From Grid) (To Bool) (Body ($y) (Not (pillar (md-cell $y)))))
  (Carrier FreeA (Of (Tuple Nat Nat)) (Subset Grid free-A))
  (Carrier FreeB (Of (Tuple Nat Nat)) (Subset Grid free-B))
  (Carrier FreeC (Of (Tuple Nat Nat)) (Subset Grid free-C))
  (Map respond-A (From (Product FreeA Dir)) (To Reward) (Body ($ym) (progress $ym)))
  (Map respond-B (From (Product FreeB Dir)) (To Reward)
    (Body ($ym) (progress (Tuple (r270-cell (GetTuple $ym 0)) (r270-dir (GetTuple $ym 1))))))
  (Map respond-C (From (Product FreeC Dir)) (To Reward)
    (Body ($ym) (progress (Tuple (md-cell (GetTuple $ym 0)) (md-dir (GetTuple $ym 1))))))
  (MethodSystem A (States FreeA) (Methods Dir) (Response respond-A))
  (MethodSystem B (States FreeB) (Methods Dir) (Response respond-B))
  (MethodSystem C (States FreeC) (Methods Dir) (Response respond-C))

  ;; the library: AB and BC from camera calibration, CA learned by matching recorded
  ;; responses; a pullback maps target cells to source cells, a pushforward source commands
  ;; to target commands
  (Transfer AB      (Source A) (Target B) (StatePullback r270-cell) (MethodPushforward r90-dir))
  (Transfer BC      (Source B) (Target C) (StatePullback mv-cell)   (MethodPushforward mv-dir))
  (Transfer CA      (Source C) (Target A) (StatePullback r90-cell)  (MethodPushforward r270-dir))
  (Transfer CAcal   (Source C) (Target A) (StatePullback md-cell)   (MethodPushforward md-dir))
  (Transfer NaiveAB (Source A) (Target B) (StatePullback r270-cell) (MethodPushforward same-dir))
  ;; every exact C-to-A transfer among the eight frame changes (pullback, pushforward)
  (Derive CandidatesCA
    (FindTransfers C A                                                                  ; PROPOSED
      (Candidates (same-cell same-dir) (r90-cell r270-dir) (r180-cell r180-dir) (r270-cell r90-dir)
                  (mv-cell mv-dir) (mh-cell mh-dir) (md-cell md-dir) (ma-cell ma-dir))))
  (Derive ABchecked (CheckTransfer AB))
  (Derive BCchecked (CheckTransfer BC))
  (Derive CAchecked (CheckTransfer CA))
  (Derive RoundTrip (ComposeTransfers (Output ABchecked Transfer) (Output BCchecked Transfer)
                                      (Output CAchecked Transfer)))

  ;; response symmetries, each in its robot's own frame
  (Symmetry FlipUD-A (Of A) (States mh-cell) (Methods mh-dir))
  (Symmetry FlipLR-A (Of A) (States mv-cell) (Methods mv-dir))
  (Symmetry FlipUD-B (Of B) (States mh-cell) (Methods mh-dir))
  (Symmetry FlipLR-B (Of B) (States mv-cell) (Methods mv-dir))
  (Symmetry FlipUD-C (Of C) (States mh-cell) (Methods mh-dir))
  (Symmetry FlipLR-C (Of C) (States mv-cell) (Methods mv-dir))
  (TransferHive Strict (Member A) (Member B) (Member C)
    (Edge AB) (Edge BC) (Edge CA) (Cycle A B C))
  (TransferHive FullGauge (Member A) (Member B) (Member C)
    (Edge AB) (Edge BC) (Edge CA) (Cycle A B C)
    (Gauge A FlipUD-A FlipLR-A) (Gauge B FlipUD-B FlipLR-B) (Gauge C FlipUD-C FlipLR-C))
  (TransferHive Copied (Member A) (Member B) (Member C)
    (Edge AB) (Edge BC) (Edge CA) (Cycle A B C)
    (Gauge A FlipUD-A) (Gauge B FlipUD-B) (Gauge C FlipUD-C))
  (TransferHive Transported (Member A) (Member B) (Member C)
    (Edge AB) (Edge BC) (Edge CA) (Cycle A B C)
    (Gauge A FlipUD-A) (Gauge B FlipLR-B) (Gauge C FlipLR-C))
  (TransferHive FromBase (Member A) (Member B) (Member C)                             ; PROPOSED
    (Edge AB) (Edge BC) (Edge CA) (Cycle A B C) (GaugeFrom A FlipUD-A))
  (Derive Unsaturated (KernelOf Strict))
  (Derive SaturatedFull (KernelOf FullGauge (Saturate Gauge)))
  (Derive SaturatedCopied (KernelOf Copied (Saturate Gauge)))
  (Derive SaturatedTransported (KernelOf Transported (Saturate Gauge)))

  ;; a skill: the greedy move, ties broken by command order (as a frozen table)
  (Map greedy-A (From FreeA) (To Dir)
    (Table ((Tuple 0 0) right) ((Tuple 0 1) right) ((Tuple 0 2) down) ((Tuple 0 3) down) ((Tuple 0 4) left)
           ((Tuple 1 1) right) ((Tuple 1 2) down) ((Tuple 1 3) down)
           ((Tuple 2 0) right) ((Tuple 2 1) right) ((Tuple 2 2) up) ((Tuple 2 3) left) ((Tuple 2 4) left)
           ((Tuple 3 1) up) ((Tuple 3 2) up) ((Tuple 3 3) up)
           ((Tuple 4 0) right) ((Tuple 4 1) up) ((Tuple 4 2) up) ((Tuple 4 3) up) ((Tuple 4 4) left)))
  (Derive SkillRoundTrip (TransportSkill (Output RoundTrip Transfer) greedy-A))        ; PROPOSED
  ;; a skill whose rewards are not mirror-symmetric: always move up
  (Map always-up (From FreeA) (To Dir) (Body ($x) up))
  (Derive UpRoundTrip (TransportSkill (Output RoundTrip Transfer) always-up)))
;; @end

;;                  mirror between the two one-sided regimes, optimality of the calm policy
;;   InformedFlow   toxic flow as a hidden distinction: averages, coarse and refined policies,
;;                  a noisy toxicity signal with a price
;;   NewsLeak       did the news leak?  trace and behavioral claims about the desk's own tape
;;   ShiftMonitors  likelihood-ratio monitors: exact validity and blindness, Estimated detections
;;
;; Forms marked PROPOSED need ex4_registry_patch.json; NatArith comes from Example 1 and
;; Families (Parameters, Switch, Like) from Example 2.

;; ---------------------------------------------------------------------------- the desk
(DC.Module MarketDesk
  (Profile Stochastic)
  (Use Decisions Laws Families NatArith)            ; Laws, DecisionProcess: PROPOSED
  (Carrier Inv    (Of Int)    (Enum -2 -1 0 1 2))     ; inventory in lots
  (Carrier Quote  (Of Symbol) (Enum tight wide lean))
  (Carrier Market (Of Symbol) (Enum calm toxic buyers sellers informed))
  (Carrier Bit    (Of Nat)    (Enum 0 1))
  (Carrier Offset (Of Nat)    (Enum 0 1 2))           ; ticks from the mid; 0: side not shown
  (Carrier Bucket (Of Nat)    (Enum 0 1 2))           ; lots held, on either side
  (Carrier One    (Of Nat)    (Enum 0))
  (Tolerance Ticks (On Rational) (OneMinusAbsoluteDifference))
  (Measure Flat (On Inv) (Masses (0 1)))

  ;; the quoting rule: lean is tight on the side that reduces the position; at the limits
  ;; the side that would grow the position is withdrawn
  (Map ask-offset (From (Product Inv Quote)) (To Offset)
    (Cases ((Tuple $q tight) (If (Eq $q -2) 0 1))
           ((Tuple $q wide)  (If (Eq $q -2) 0 2))
           ((Tuple $q lean)  (If (Eq $q -2) 0 (If (Lt $q 0) 2 1)))))
  (Map bid-offset (From (Product Inv Quote)) (To Offset)
    (Cases ((Tuple $q tight) (If (Eq $q 2) 0 1))
           ((Tuple $q wide)  (If (Eq $q 2) 0 2))
           ((Tuple $q lean)  (If (Eq $q 2) 0 (If (Lt 0 $q) 2 1)))))

  ;; a market is a fill probability per side and offset, and an adverse-selection cost per
  ;; fill (the expected move against the maker after the fill, in ticks)
  (Map ask-fill (Parameters ($m Market)) (From Offset) (To Rational)
    (Cases (0 0)
           (1 (Switch $m (calm (Rat 1 2)) (toxic (Rat 1 2)) (buyers (Rat 3 4)) (sellers (Rat 1 4))
                         (informed (Rat 1 2))))
           (2 (Switch $m (calm (Rat 1 8)) (toxic (Rat 1 8)) (buyers (Rat 3 16)) (sellers (Rat 1 16))
                         (informed (Rat 1 8))))))
  (Map bid-fill (Parameters ($m Market)) (From Offset) (To Rational)
    (Cases (0 0)
           (1 (Switch $m (calm (Rat 1 2)) (toxic (Rat 1 2)) (buyers (Rat 1 4)) (sellers (Rat 3 4))
                         (informed (Rat 1 2))))
           (2 (Switch $m (calm (Rat 1 8)) (toxic (Rat 1 8)) (buyers (Rat 1 16)) (sellers (Rat 3 16))
                         (informed (Rat 1 8))))))
  (Map theta (Parameters ($m Market)) (From One) (To Rational)
    (Body ($u) (Switch $m (calm 0) (toxic (Rat 1 2)) (buyers 0) (sellers 0) (informed 1))))
  (Map edge (Parameters ($m Market)) (From Offset) (To Rational)
    (Body ($o) (Sub $o (theta $m 0))))

  ;; one step: a buyer lifts the ask and a seller hits the bid, independently
  (Map fills (Parameters ($m Market)) (From (Product Inv Quote)) (To (Law (Tuple Bit Bit)))
    (Body ($xa) (Indep (Coin (ask-fill $m (ask-offset $xa))) (Coin (bid-fill $m (bid-offset $xa))))))
  (Map after (From (Product Inv Bit Bit)) (To Int)
    (Body ($t) (Add (Sub (GetTuple $t 0) (GetTuple $t 1)) (GetTuple $t 2))))
  (Map held (From (Product Inv Bit Bit)) (To Nat)
    (Body ($t) (Max (after $t) (Sub 0 (after $t)))))
  (Map step (Parameters ($m Market)) (From (Product Inv Quote)) (To (Law Inv))
    (Body ($xa)
      (Image $f (after (Tuple (GetTuple $xa 0) (GetTuple $f 0) (GetTuple $f 1)))
        (fills $m $xa))))
  (Map pnl (Parameters ($m Market)) (From (Product Inv Quote)) (To (Law Rational))
    (Body ($xa)
      (Image $f
        (Sub (Add (Mul (GetTuple $f 0) (edge $m (ask-offset $xa)))
                  (Mul (GetTuple $f 1) (edge $m (bid-offset $xa))))
             (Mul (Rat 1 4) (held (Tuple (GetTuple $xa 0) (GetTuple $f 0) (GetTuple $f 1)))))
        (fills $m $xa))))

  ;; four regimes as decision processes (each is also a machine observing expected rewards)
  (DecisionProcess CalmDesk    (States Inv) (Actions Quote) (Kernel (step calm))    (RewardLaw (pnl calm))
    (Discount (Rat 9 10)) (Values Ticks))
  (DecisionProcess ToxicDesk   (States Inv) (Actions Quote) (Kernel (step toxic))   (RewardLaw (pnl toxic))
    (Discount (Rat 9 10)) (Values Ticks))
  (DecisionProcess BuyersDesk  (States Inv) (Actions Quote) (Kernel (step buyers))  (RewardLaw (pnl buyers))
    (Discount (Rat 9 10)) (Values Ticks))
  (DecisionProcess SellersDesk (States Inv) (Actions Quote) (Kernel (step sellers)) (RewardLaw (pnl sellers))
    (Discount (Rat 9 10)) (Values Ticks))

  ;; the risk-bucket compression and the mirror
  (Map bucket (From Inv) (To Bucket) (Body ($q) (Max $q (Sub 0 $q))))
  (Map mirror (From Inv) (To Inv) (Body ($q) (Sub 0 $q)))
  (Representation Risk       (Of CalmDesk)   (Encode bucket))
  (Representation RiskToxic  (Of ToxicDesk)  (Encode bucket))
  (Representation RiskBuyers (Of BuyersDesk) (Encode bucket))
  (AbstractionMap CalmMirror (Source CalmDesk)   (Target CalmDesk)    (Map mirror))
  (AbstractionMap Flip       (Source BuyersDesk) (Target SellersDesk) (Map mirror))

  ;; policies the desk has on file
  (Map calm-policy    (From Inv) (To Quote) (Table (-2 tight) (-1 lean)  (0 tight) (1 lean)  (2 tight)))
  (Map sellers-policy (From Inv) (To Quote) (Table (-2 tight) (-1 tight) (0 tight) (1 lean)  (2 tight)))

  (Derive CalmQuotient (InduceExact Risk))
  (Derive FlipChecked  (CheckAbstractionMap Flip)))

;; calm: the risk buckets are an exact quotient, and the optimum lives on them
!(dc.run MarketDesk CalmQuotient)
!(dc.run MarketDesk (CheckAbstractionMap CalmMirror))
!(dc.run MarketDesk (OptimizePolicy CalmDesk (Under Flat)))
!(dc.run MarketDesk (OptimizePolicy CalmDesk (Through Risk) (Under Flat)))
;; toxic flow: every value moves, no decision does
!(dc.run MarketDesk (InduceExact RiskToxic))
!(dc.run MarketDesk (CheckOptimal ToxicDesk (Policy calm-policy)))
!(dc.run MarketDesk (EvaluatePolicy ToxicDesk (Policy calm-policy) (Under Flat)))
;; one-sided flow: the compression breaks, and so does the policy
!(dc.run MarketDesk (InduceExact RiskBuyers))
!(dc.run MarketDesk (CheckUpdates RiskBuyers))
!(dc.run MarketDesk (MeasureBehavioral RiskBuyers (Discount (Rat 9 10))))
!(dc.run MarketDesk (CheckOptimal BuyersDesk (Policy calm-policy)))
!(dc.run MarketDesk (OptimizePolicy BuyersDesk (Under Flat)))
!(dc.run MarketDesk (OptimizePolicy BuyersDesk (Through RiskBuyers) (Under Flat)))
;; the broken symmetry survives as a transfer between the two one-sided markets
!(dc.run MarketDesk FlipChecked)
!(dc.run MarketDesk (PullbackPolicy Flip (Policy sellers-policy)))

;; ---------------------------------------------------------------------------- informed flow
(DC.Module InformedFlow
  (Profile Stochastic)
  (Use Decisions Laws Families NatArith)
  (Import MarketDesk (Only Inv Quote Market Bit Ticks step pnl ToxicDesk))
  (Carrier Flow    (Of Symbol) (Enum noise informed))
  (Carrier Book    (Of (Tuple Int Symbol)) (Product Inv Flow))
  (Carrier Reading (Of Symbol) (Enum says-noise says-informed))
  (Measure Half     (On Flow) (Masses (noise (Rat 1 2)) (informed (Rat 1 2))))
  (Measure FlatHalf (On Book) (Masses ((Tuple 0 noise) (Rat 1 2)) ((Tuple 0 informed) (Rat 1 2))))

  ;; each step is informed with probability 1/2, independently of everything else: an
  ;; informed fill is followed by a one-tick move against the maker; fills are as in calm
  (Map visible (From Book) (To Inv) (Body ($x) (GetTuple $x 0)))
  (Map flow-of (From Book) (To Flow) (Body ($x) (GetTuple $x 1)))
  (Map visible-move (From (Product Book Quote)) (To (Product Inv Quote))
    (Body ($xa) (Tuple (visible (GetTuple $xa 0)) (GetTuple $xa 1))))
  (Map split-step (From (Product Book Quote)) (To (Law Book))
    (Body ($xa) (Indep (step calm (visible-move $xa)) (LawOf Half))))
  (Map split-pnl (From (Product Book Quote)) (To (Law Rational))
    (Body ($xa) (If (Eq (flow-of (GetTuple $xa 0)) informed)
                    (pnl informed (visible-move $xa))
                    (pnl calm (visible-move $xa)))))
  (DecisionProcess Split (States Book) (Actions Quote) (Kernel split-step) (RewardLaw split-pnl)
    (Discount (Rat 9 10)) (Values Ticks))
  (Representation Coarse (Of Split) (Encode visible))

  ;; a toxicity signal that is wrong one time in ten and costs 1/20 tick per step
  (TransitionKernel FlowSignal (From Flow) (To Reading)
    (Row noise    (Mass says-noise (Rat 9 10)) (Mass says-informed (Rat 1 10)))
    (Row informed (Mass says-noise (Rat 1 10)) (Mass says-informed (Rat 9 10))))
  (ObservationMethod Signal (Channel FlowSignal) (Cost (Rat 1 20))))

!(dc.run InformedFlow (CheckEqual (AverageModel Split (Through Coarse) (Under Half)) ToxicDesk (Compare Means)))
!(dc.run InformedFlow (CheckEqual (AverageModel Split (Through Coarse) (Under Half)) ToxicDesk))
!(dc.run InformedFlow (InduceExact Coarse))
!(dc.run InformedFlow (OptimizePolicy Split (Through Coarse) (Under FlatHalf)))
!(dc.run InformedFlow (OptimizePolicy Split (Under FlatHalf)))
!(dc.run InformedFlow (EvaluatePolicy Split (With Signal) (Through Coarse) (Under FlatHalf)))

;; ---------------------------------------------------------------------------- did the news leak?
(DC.Module NewsLeak
  (Profile Stochastic)
  (Use Linear)                                          ; the Like field: PROPOSED with Example 2
  (Carrier Tape   (Of Symbol)
    (Enum leak embargo knows-up knows-down pending moved-up moved-down picked-up picked-down))
  (Carrier Report (Of Symbol) (Enum quiet up down hit-up hit-down))
  (Map report (From Tape) (To Report)
    (Cases (leak quiet) (embargo quiet) (knows-up quiet) (knows-down quiet) (pending quiet)
           (moved-up up) (moved-down down) (picked-up hit-up) (picked-down hit-down)))
  ;; leak: an informed trader already knows the direction; embargo: nobody does yet.
  ;; The informed trader picks off a tight quote just before the move and leaves a wide one.
  (TransitionKernel QuoteTight (From Tape) (To Tape)
    (Row leak (Mass knows-up (Rat 1 2)) (Mass knows-down (Rat 1 2)))
    (Row embargo (Mass pending 1))
    (Row knows-up (Mass picked-up 1))
    (Row knows-down (Mass picked-down 1))
    (Row pending (Mass moved-up (Rat 1 2)) (Mass moved-down (Rat 1 2)))
    (Row moved-up (Mass moved-up 1)) (Row moved-down (Mass moved-down 1))
    (Row picked-up (Mass picked-up 1)) (Row picked-down (Mass picked-down 1)))
  (TransitionKernel QuoteWide (From Tape) (To Tape)
    (Row leak (Mass knows-up (Rat 1 2)) (Mass knows-down (Rat 1 2)))
    (Row embargo (Mass pending 1))
    (Row knows-up (Mass moved-up 1))
    (Row knows-down (Mass moved-down 1))
    (Row pending (Mass moved-up (Rat 1 2)) (Mass moved-down (Rat 1 2)))
    (Row moved-up (Mass moved-up 1)) (Row moved-down (Mass moved-down 1))
    (Row picked-up (Mass picked-up 1)) (Row picked-down (Mass picked-down 1)))
  (Machine Desk     (States Tape) (Observe report report) (Action tight QuoteTight) (Action wide QuoteWide))
  (Machine WideDesk (States Tape) (Observe report report) (Action wide QuoteWide))
  (Carrier Seen (Of Symbol) (Reach WideDesk (From leak embargo)))
  (Machine WideSeen (States Seen) (Like WideDesk))        ; the desk that only ever quotes wide
  (Map merge-leak (From Tape) (To Tape)
    (Cases (leak leak) (embargo leak) (knows-up knows-up) (knows-down knows-down) (pending pending)
           (moved-up moved-up) (moved-down moved-down) (picked-up picked-up) (picked-down picked-down)))
  (Map merge-leak-seen (From Seen) (To Seen)
    (Cases (leak leak) (embargo leak) (knows-up knows-up) (knows-down knows-down) (pending pending)
           (moved-up moved-up) (moved-down moved-down)))
  (Representation MergeLeak     (Of Desk)     (Encode merge-leak))
  (Representation MergeLeakWide (Of WideSeen) (Encode merge-leak-seen))
  (Derive WideLinear (MinimalLinear WideSeen))
  (Derive DeskLinear (MinimalLinear Desk))
  (Derive WideTraceClasses (TracePartition WideSeen)))

!(dc.run NewsLeak (CheckTrace MergeLeakWide (Policies ObservationBased)))
!(dc.run NewsLeak (CheckBehavioral MergeLeakWide))
!(dc.run NewsLeak (MeasureBehavioral MergeLeakWide (Discount (Rat 9 10))))
!(dc.run NewsLeak WideTraceClasses)
!(dc.run NewsLeak WideLinear)
!(dc.run NewsLeak (CheckTrace MergeLeak))
!(dc.run NewsLeak (CheckBehavioral MergeLeak))
!(dc.run NewsLeak DeskLinear)

\section{Reproducing the results}\label{app:repro}

The four bundles are collected in \fpath{mettadinc_worked_examples_package.zip}, one directory per
example (\fpath{ex1_belief_memory}, \fpath{ex2_access_policy}, \fpath{ex3_skill_share} and
\fpath{ex4_market_maker}) under a top-level README. Each bundle contains its module file, its registry
patch (and the patches of earlier examples that it reuses), the static checker \fpath{ex_check.py},
the Python model, the oracle and the oracle's results. The bundles of Examples~1, 3 and~4 add the
reference evaluator \fpath{metta_eval.py}, and those of Examples~1 and~2 their proof obligations and a
replay script. Python~3.11 or later is assumed.

\paragraph{Running an oracle.} In a bundle directory, \code{python3 exN\_oracle.py} recomputes every
number of the example from the module file, prints one line per check, writes \fpath{exN_results.json},
and exits with a nonzero status if any check fails. \Cref{tab:oracles} gives the running times and
dependencies. The oracles of Examples~1 and~2 write every unsatisfiable obligation, with its CNF and its
DRAT proof, to \fpath{obligations/}, and check the proofs when the environment variable
\fpath{MDINC_TOOLS} names a directory holding \fpath{drat-trim/drat-trim} and \fpath{cake_lpr/cake_lpr}.
Without the tools they skip the checks that read the proof checker's verdicts and report the results
that rest on the proofs as Conditional, with a trusted-backend assumption. The pinned versions are
drat-trim at commit \fpath{2e3b2dc} and \code{cake\_lpr} at commit \fpath{033aad5}, run as
\begin{lstlisting}
drat-trim obligation.cnf obligation.drat -L obligation.lrat
cake_lpr --CML_HEAP_SIZE=1024 --CML_STACK_SIZE=512 obligation.cnf obligation.lrat
\end{lstlisting}

\paragraph{Replaying the shipped proofs.} \fpath{ex1_obligations.tar.xz} and
\fpath{ex2_obligations.tar.xz} hold the obligations of the runs that wrote the shipped results: the CNF
and DRAT proof of every unsatisfiable obligation, the colorings, cliques and center sets of Example~1,
and an index of names, claims, CNF digests and the digest of the module file. \fpath{replay_proofs.py}
needs neither python-sat nor the oracle. It extracts an archive, compares the module digest with the
module file it is given and every CNF with its digest, and runs the two commands above on every proof:
\begin{lstlisting}
MDINC_TOOLS=/path/to/tools python3 replay_proofs.py ex2_obligations.tar.xz access_policy.metta
\end{lstlisting}

\paragraph{Checking the modules.} The checker needs the specification's validation package, which
contains the registry and the base checker:
\begin{lstlisting}
MDINC_PACKAGE=/path/to/mettadinc_validation_package python3 ex_check.py \
    ex1_registry_patch.json ex2_registry_patch.json ex4_registry_patch.json \
    -- market_maker.metta
\end{lstlisting}
The patches before \code{--} are applied in order. The first pass must report that all forms conform to
the registry with the proposed patches; the second pass lists the diagnostics against the unpatched
registry, which are exactly the forms that depend on the patches. The commands for the other examples
take the patch lists of \cref{tab:repro}.

\paragraph{The reference evaluator.} \fpath{metta_eval.py}, the same file in the bundles of
Examples~1, 3 and~4, reads a module file with its own small reader, resolves imports, and evaluates the
maps of the module: \code{Cases}, \code{Body} and \code{Table} bodies, parameterized maps, the
arithmetic and bit-vector primitives used in the files, and the proposed law primitives. The oracles use
it to compare each module with its Python model cell by cell. It is a test aid for these examples and
not an implementation of MeTTaDinC.

\paragraph{The source route of Example 2.} \fpath{policy_ir.py} reads \fpath{access_policy.metta} into
the typed intermediate form of Section~\ref{sec:ex2notes}, and \fpath{obligations.py},
\fpath{bdd_reach.py} and the oracle build every obligation, reachable set and witness from it;
\fpath{validate_small_lib.py} holds the point-by-point validation on the two-user instance.
\fpath{rbac.py}, \fpath{circuits.py} and \fpath{sat_obligations.py} are the independent model, kept as
a differential check. The oracle also applies the two source mutations of \cref{tab:ex2results} and
requires the verdicts they affect to change.

\paragraph{The streams of Example 4.} The three streams in \fpath{streams/} were generated once by
\fpath{monitors.simulate} with seed $1$ and are stored as data; the module pins each by its SHA-256
digest. Reproducing a detection means replaying the stored stream, not rerunning the generator, whose
output depends on the random number generator of the language it runs in.
