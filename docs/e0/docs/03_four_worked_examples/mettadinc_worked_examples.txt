Scope. Four complete MeTTaDinC programs, each worked out from the problem statement to the
expected result of every request: the model, the modules, the statuses, the witnesses and certificates,
the algorithms that produce them, the design lessons the results carry, and the registry additions each
program needs. Together the four examples exercise the graded deterministic core, symbolic carriers
with proof-logged obligations, transfers and hives with declared gauges, and the stochastic profile with
decision processes and monitors.
Validation material. Each example ships as a bundle: its modules, a registry patch that declares
every proposed addition, a Python model, an exact-arithmetic oracle that recomputes every number in
this document from the module files, the oracle’s results, and the static checker that tests the modules
against the registry with and without the patch. The bundles of Examples 1 and 2 also carry their
proof obligations and the DRAT proofs of every unsatisfiable one, which the oracles replay through
drat-trim and the verified checker cake_lpr. The four bundles total 305 oracle checks. Where this text
and the bundles differ, the bundles are authoritative. No MeTTaDinC runtime exists yet; the examples
are written to be the first programs one runs.

                                              Abstract
     A language specification says what programs mean. It does not show what it is like to
     write one for a problem someone cares about, which requests that person would send,
     what the answers look like, or which parts of the language turn out to be missing. This
     document works through four MeTTaDinC programs in full. The first compacts the belief
     memory of an agent with two consumers, a reasoner that reads truth values and a controller
     that reads a status, and finds that the choice of decay rule decides whether any compact
     summary can be trusted; it separates three meanings of “store it in fewer bits” into three
     claims with different numbers. The second audits an administrative access-control policy on
     forty-bit configurations without enumerating them: two authoring mistakes are found with
     short canonical witnesses, the corrected policy is proved safe with 80 small proofs whose
     obligations are generated from the module itself and checked by a verified checker, and a
     true property comes back Unknown until a stronger invariant is supplied. The third shares
     navigation skills between three robots whose cameras see the same bay in different frames;
     a transfer learned from recorded behavior is correct only up to the task’s symmetries, and
     whether the skill library is coherent depends on the gauge declared at each robot. The
     fourth follows a market maker through a toxic-flow shift and a one-sided-flow shift: the first
     changes every value and no decision, the second breaks the desk’s state compression and its
     policy, a toxicity signal is priced correctly and incorrectly, a leak of news is shown to be
     invisible to a desk that only quotes wide, and monitors are shown to be provably blind to
     one shift each. Every number is recomputed by an exact oracle, and each example ends
     with implementation notes and the registry additions it needs.

1     Introduction
1.1   Why worked examples
The MeTTaDinC specification defines what a program means: carriers, observers and actions;
the defects that measure what an encoding loses; the claims that say which notion of sameness
has been established; the certificates that let a second program check the first. It supports those
definitions with fixtures, and the fixtures are small on purpose. Each isolates one phenomenon –
an eight-state machine for the crisp core, a forty-bit machine that cannot be enumerated, a seven-
state chain on which behavioral, trace and linear answers disagree – so that an implementation
either reproduces the phenomenon or visibly fails to.
    Fixtures do not show what it is like to use the language. Someone with a real problem has
to decide which machine to declare, which consumer the interface serves, which requests to send
in which order, what a refutation is telling them about their design, and what to do when the
language cannot yet express the next question. Those decisions are where a language succeeds
or fails in practice, and they only become visible on problems large enough to have structure
and small enough to be checked exactly. The four examples in this document were chosen with
that in mind. Each is a problem that comes up in the systems this work is meant to support –
the memory of an Omega agent, the access policy of an organization, a group of robots sharing
skills, a trading desk facing a market that changes under it – and each forces the language to
say something the fixtures do not.
    The examples serve two readers. An implementer gets a set of conformance targets that
exercise many requests together, with every expected status, witness and number stated and
recomputed by an independent oracle, and with notes on the algorithms that produce them.
A prospective user gets a picture of how MeTTaDinC programs are written and read, and of
the kind of design advice the answers carry: a decay rule that silently ruins every summary
of a memory, a policy rule that reads a session where it should read an assignment, a learned
transfer that is correct only up to a mirror, a market shift that a fill-rate dashboard can never
see.

1.2   The four examples
Example 1, belief memory (Section 3). An agent keeps two evidence counts per proposition
and serves two consumers: a reasoner that reads a truth value and a controller that reads a
three-way status. Under memory pressure the designer wants dormant beliefs stored in fewer
bits. The example finds that neither consumer has a useful exact compaction, that the original
decay rule makes every compact summary worthless, that a gentler rule bounds the error of
a twenty-one-code summary at 1/5, and that “fewer bits” means three different things — an
index, a cold store that is rehydrated, and a memory that runs on its codes — with three
different claims and three different answers. It extends to six beliefs (248 states) by a product
rule and to a ledger of evidence receipts whose forks must be merged, and whose oldest receipts
can be compacted to counts only under a delivery protocol that keeps them from arriving again.
    Example 2, access policy (Section 4). An administrative role-based access control policy
over four users and five roles has forty bits of state. The audit finds two authoring mistakes
with two- and three-step witnesses, proves the corrected policy safe with 80 small proofs whose
obligations are generated from the module and which pass through the specification’s pinned
proof-checking pipeline, shows that restoring either mistake in the source changes the verdict,
shows a true property returning Unknown until a stronger invariant is supplied, and finds that
a targeted monitor needs seventeen bits where a vendor proposed ten.
    Example 3, skill sharing (Section 5). Three warehouse robots see the same bay through

1.3    How each example is organized
Each example section has the same parts. It opens with the problem in its own terms and the
background needed to follow it. It then gives the program: excerpts of the modules with the
reasons for each declaration, and pointers to the full file in Appendix A. The results follow,
grouped by the question they answer, each with its status, its canonical witness when it is
refuted, and its certificate when it is checked. A table of expected results collects them for
conformance testing. Notes for implementers describe the algorithms that produced the results
and the pitfalls the oracle uncovered, and a final subsection lists the registry additions the
example proposes.
    Proposed additions are marked in the modules with the comment PROPOSED. None of them
changes the meaning of an existing request on the inputs that request already accepts; several
extend a request to new inputs (Example 4 extends four requests of the Decisions library
from one-step decision models to decision processes), and one proposes a change to a status
rule (Example 1 allows the optimality of a frontier to be Checked by a replayed lower-bound
certificate without exhaustive enumeration). Section 7 collects all of them.

2     Conventions shared by the examples
2.1    Statuses and claims
Every request returns a result in the specification’s envelope (specification, Section 5.5), with
one of seven statuses (specification, Section 2.2). The examples use all seven, under one policy
for what each status requires.
    • A result is Checked when the claim holds within its scope and is established either by an
      exact method that the checker runs on the module’s machine (finite enumeration, exact
      rational arithmetic, partition refinement, decision diagrams) or by a certificate that the
      checker replays: a witness, a coupling, a clique, a table of values, an exact dual solution
      of a linear program, or a proof of unsatisfiability in the DRAT format that drat-trim
      converts to LRAT and the verified checker cake_lpr accepts, for an obligation that the
      obligation generator built from the admitted source.
    • A result is Conditional when the claim holds under named assumptions that the checker
      has not discharged. The answer of an external solver that has not been replayed, such
      as a satisfiability solver’s “unsatisfiable” without a checked proof, is Conditional, and
      its assumption names the solver, its version, the logic and the digest of the obligation,
      as in (TrustedBackend cadical 1.5.3 SAT sha256:...). A second solver or a second
      encoding that agrees is recorded as evidence, in the field agreed_by; it does not discharge
      the assumption.
    • A result is Refuted when a counterexample, the witness, or a lower-bound certificate
      shows that the claim fails and the checker replays it by evaluating the admitted source. A
      witness found by a solver counts once it has been replayed.
    • A result is Unknown when the claim is unresolved, because a budget ended or a certified
      interval straddles the bound. The result carries what was learned in its Resources field.
    • A result is Estimated when a statistical procedure supports a conclusion about a data
      source, with its estimand, protocol, sample and guarantee stated. Estimated results
      appear only in Example 4.
    • A result is InvalidInput when a declaration or request violates the admitted language, for
      example a transfer whose state pullback is not total, and Unsupported when the request
      lies outside the capability manifest of the running release.
A result derived from other results, such as a claim about six beliefs lifted from one belief
by the product rule of Example 1, carries the union of their assumptions, so a derivation
from a Conditional premise is Conditional. A consumer declares which results it accepts:
(Accepts Checked) accepts only Checked results, and (Accepts Checked (Conditional
(TrustedBackend cadical))) also accepts results whose only open assumptions are trusted-
backend assumptions for CaDiCaL. A Conditional result that a consumer does not accept
counts, for that consumer, as a claim not yet covered.
    Only Examples 1 and 2 call a solver. Their bundles keep every unsatisfiable obligation
together with its DRAT proof, and their oracles replay the proofs when drat-trim and cake_lpr
are installed. The results that rest on the proofs are then Checked; without the two checkers
the oracles report them as Conditional, with the assumption above. Every other result in the
four examples is an exact computation or a replayed certificate.
    The specification separates measuring a defect from checking a bound (specification, Sec-
tion 2.4). A request named Measure... returns a certified interval and is Checked when the
interval is no wider than the requested Precision (zero by default, which asks for the exact
value). A request named Check... with (Within b) is Checked when the upper end of the

MeTTaDinC                                                       Worked examples, 4 November 2026


interval is at most b, Refuted when the lower end exceeds b (with a witness), and Unknown
otherwise. Without Within, a check asks for defect zero.

2.2   Defects in one page
An interface is a machine: a carrier X of states, observers oj with value tolerances βj , and
actions Ta that are deterministic maps, stochastic kernels or nondeterministic relations. A
representation is a map q from states to codes, and it is meant to be used in place of the state
by some consumer. The specification measures what q loses with four defects (specification,
Section 4.2).
  • The current defect δnow (q) is the largest observation distance 1 − βj between two states
    with the same code. It is zero when every observer can be read off the code.
  • The update defect δupd (q) is the largest distance between the codes of the successors of
    two states with the same code. For crisp codes and deterministic actions it is zero or one:
    either every action can be carried out on codes, or some pair of same-code states is sent
    to different codes. For stochastic actions it is the largest total-variation distance between
    the laws the two states push onto the codes; defect zero is strong lumpability.
  • The behavioral defect δbeh (q) is the largest behavioral distance between two states with
    the same code. For a deterministic machine the behavioral distance at discount γ is

                        dγbeh (x, y) = max γ |w| max 1 − βj (oj Tw x, oj Tw y) ,

      the largest discounted observation difference that any finite word of actions can produce;
      through horizon h the maximum ranges over words of length at most h. For stochastic
      machines the behavioral distance is the Kantorovich bisimulation pseudometric, which
      replaces the single successor by a coupling of the two successor laws (specification,
      Section 4.1).
  • The trace defect compares the laws of observation sequences only. For deterministic
    machines it equals the behavioral defect; for stochastic machines it can be strictly smaller
    (specification, Section 4.3).
When the current and update defects are both zero, the representation is an exact quotient:
InduceExact returns the abstract machine on the codes and a checked quotient arrow. When
they are not, InduceApprox builds a machine from chosen representatives and reports its radius,
the largest distance from a state to the representative of its class, and its arrow defect, the
largest distance between a state and its code in the disjoint union of the concrete and abstract
machines (specification, Section 4.6).

In plain terms. A code is a promise that two states are interchangeable for a particular
consumer. The current defect says how far the consumer’s present readings can differ between
states with the same code, the update defect says whether the code can be kept up to date
without the state, and the behavioral defect says how far apart the consumer’s future readings
can drift. These are three different promises, and the examples show each of them failing while
the others hold.

2.3   Canonical witnesses
A replay checker accepts any witness that replays. Conformance testing needs more: two
correct implementations must report the same witness, so that a manifest can record it. The


                                                7
MeTTaDinC                                                        Worked examples, 4 November 2026


specification fixes a canonical witness, the least one in a declared order: shortest word first,
then pairs of states in the lexicographic order of carrier declaration, then actions and queries
in declaration order, then words in numeric order (specification, Section 4.4 and the registry’s
witness_order). A Product carrier enumerates in declared component order with the last
component varying fastest, which fixes the order of pairs. Each example adds the ordering rules
its own claims need: the least moved cell for a holonomy, the least state and first improving
action for a policy optimality check, the least observation sequence for a trace event.
   Producing canonical witnesses is mostly a matter of search order. Breadth-first searches
expand actions in declaration order; solver models are minimized before they are reported,
because a satisfiability solver returns an arbitrary model; and tables are scanned in declaration
order.

2.4   Registry patches and the two-pass check
MeTTaDinC is registry driven: every declaration head, field, request, argument and result type
that a module may use is listed in a machine-readable registry, and the checker of the validation
package rejects anything else. The examples need forms the registry does not have yet. Each
example therefore ships a JSON patch that declares exactly those forms — libraries with their
primitives, new declarations, new fields on existing declarations, new requests and result types —
and a checker, ex_check.py, that runs two passes. The first pass applies the patches in memory
and checks every form of the module files; it must report no errors. The second pass checks the
same files against the unpatched registry and lists every diagnostic, which makes the forms that
depend on the patch explicit. The patches compose: Example 3 uses the NatArith library of
Example 1, and Example 4 uses NatArith and the Families library of Example 2.

3     Example 1: compacting an agent’s belief memory
3.1   The problem
An Omega agent records, for each proposition it tracks, how many observations have supported
it and how many have gone against it. These are the counts p and n of the evidence form of a
PLN truth value [3]. With t = p + n, the strength is s = p/t, or 1/2 when there is no evidence,
and the confidence is c = t/(t + 4); the constant 4 plays the role of PLN’s lookahead parameter
and is chosen small here. Each count saturates at 15, so a belief occupies eight bits. Evidence
arrives as pos and neg events, each adding one to a count. A periodic decay event halves both

                                                  9
MeTTaDinC                                                        Worked examples, 4 November 2026


counts, so that old evidence weighs less than new; in the memory as first designed, halving
rounds down.
   Two consumers read the memory.
  • Reasoning processes read the truth value (s, c). Two truth values are compared coordinate
    by coordinate, with tolerance 1 − |x − x′ |, so the distance between two readings is the
    larger of the differences in strength and in confidence.
  • The action-selection controller reads a three-way status. A belief is Believed when t ≥ 4
    and p ≥ 2n, Disbelieved when t ≥ 4 and n ≥ 2p, and Uncertain otherwise.
Under memory pressure the designer wants dormant beliefs — those no process is currently
reasoning about — stored in fewer bits, and asks which smaller encodings can be trusted, by
which consumer, and with what certified error. A belief has 256 states: small enough that
every claim can be checked exactly by enumeration, large enough that the answers are not
obvious. The example then extends to six beliefs held together (248 states, which must not be
enumerated) and to a ledger of evidence receipts whose forks have to be merged, the setting of
the specification’s evidence-packet laboratory (specification, Section 12.4).
   The findings, in brief:
  • Neither consumer has a useful exact compaction. The controller’s exact quotient saves a
    fifth of a bit per belief, and the reasoner’s saves nothing.
  • The original decay rule makes every compact summary of the truth value worthless: two
    beliefs that differ by a single observation can, after a few decays and evidence events,
    report opposite truth values. The defect of every candidate summary is 1, the largest
    possible.
  • A gentler decay rule repairs this, and the checker certifies the repair. Under it, a twenty-
    one-code summary has defect at most 1/5, and no lossy encoding can do better than
    6/35.
  • “Store it in fewer bits” means three different things. As an index or summary the twenty-
    one codes are needed; as a cold store that is restored to a representative when evidence
    arrives, ten codes suffice; a memory that discards the counts and runs on its codes fails at
    this error level, because the error compounds with every update.
  • Memories that keep only counts cannot be merged without double counting, and cannot
    tell a receipt that arrives a second time from a new one. Receipts, the identities of the
    evidence, can be compacted to counts below the oldest open fork only under a delivery
    protocol that keeps those receipts from arriving again.

3.2   Background: what compaction means here
The memory is a deterministic machine with 256 states and three actions, and each consumer
sees it through an interface: Decide observes the status, and Report observes strength and
confidence. An encoding of the memory is a representation q in the sense of Section 2.2: the
memory would store q(p, n) instead of (p, n).
    An exact compaction keeps exactly what the consumer can ever observe. It is computed by
partition refinement (specification, Section 4.5): start from the classes of the current observation,
split every class whose members are sent by some action into different classes, and repeat until
nothing splits. The stable partition is behavioral equivalence for that consumer, and its quotient
is the smallest memory that answers every question the consumer could ask, now or after any
sequence of events. The savings of a partition are measured in bits, log2 of the number of
classes, and in weakness, the probability that two independent uniformly drawn beliefs fall in

                                                 10
MeTTaDinC                                                          Worked examples, 4 November 2026


the same class (specification, Section 4.7); refinement lowers weakness round by round, and the
specification records that fall as a ledger.
    When exact compaction saves too little, the question becomes graded: how far apart can two
beliefs with the same code drift? For a deterministic machine the behavioral distance between
two states is the largest observation difference that any word of actions produces from them,
with each step of the word discounted by γ (Section 2.2); at γ = 1 nothing is discounted. The
behavioral defect of an encoding is the largest distance between two states with the same code.
Through a horizon h only words of length at most h count, which corresponds to a consumer
that looks at most h events ahead. For the reasoner’s interface the distance before any event is

                          d0 (p, n), (p′ , n′ ) = max |s − s′ |, |c − c′ | .
                                                                         


All of these are computed on the pair graph, whose nodes are the 65536 ordered pairs of states
and whose edges follow the three actions in both components at once.

3.7   Three uses, three claims
“Store the belief in fewer bits” can mean three different things, and MeTTaDinC has a separate
claim for each.
   1. An index or summary. The code serves as a key — for example, to share planning results
      across beliefs — while the counts stay available. The criterion is the behavioral defect of
      the representation: two states with the same code have futures within the bound.
   2. Cold storage with rehydration. A dormant belief is replaced by its code and restored to a
      fixed representative of its class when evidence next arrives. The error is the radius, the
      largest distance from a state to the representative of its class (InduceApprox, specification,
      Section 4.6). Each compression cycle adds at most one radius, because at discount one
      the behavioral distance of two states is never smaller than that of their successors: the
      words available from the successors are suffixes of words available from the states. Decays
      missed while the belief was stored are handled by recording a decay epoch with the code
      and replaying the missed decays on restore; the same bound covers them.
   3. A compact memory that runs on its codes. The counts are discarded and updates go
      through the induced abstract machine. The criterion is the arrow defect of the induced
      machine, and errors compound with every update.
At the bound 1/5 under the gentle rule the three uses give different answers. A summary needs
21 codes (4.39 bits). A cold store needs 10 codes (3.32 bits). Running on codes fails at this level:
RoundedTV20 has radius 6/35, but its induced machine drifts to an arrow defect of 20/63. The
drift is 3/22, 3/22, 3/20 and 6/35 at horizons one to four and reaches 20/63 only at horizon
33. Grid10x7, with the same radius, drifts to 29/55, and among the 1600 rounding grids of
the TVGrids family none runs on its codes, with center representatives, within 1/4; the best of


                                                15
MeTTaDinC                                                        Worked examples, 4 November 2026


them drifts to 4/15.

In plain terms. A belief that is put away and later restored loses at most a radius each time
it is put away. A belief that is kept only as a code and updated as a code loses a little at every
update, and the losses add up. The same encoding can be good for the first use and bad for the
second, and the language makes the user say which use is meant.

3.8   The frontier and its certificates
With the codes objective, the frontier is a graph coloring problem. Call two states in conflict
when their behavioral distance exceeds the bound. An encoding whose defect is within the
bound is exactly a coloring of the conflict graph, colors being codes, so the fewest codes is
the chromatic number of that graph. Coloring is NP-hard in general, and the specification’s
status discipline applies (specification, Section 4.7): the defect of a returned partition is always
certified, and its optimality is Checked only with a certificate. Two certificates make an answer
exact. The coloring itself is one; its defect is recomputed from the distance table. A lower
bound is the other: either a clique of pairwise conflicting states, each conflict replayable as a
word, or a refutation of the problem with one code fewer.
    The refutation is a satisfiability obligation in conjunctive normal form: one variable for each
state and code, a clause saying that each state receives a code, a clause for each conflicting pair
and code, and unit clauses that give the states of a largest clique the first codes, which rules out
no coloring up to a renaming of the codes. CaDiCaL finds the obligation unsatisfiable and writes
a DRAT proof, the list of clauses it derived in order, each of which a much simpler program can
confirm; drat-trim converts the proof to the LRAT format and the verified checker cake_lpr
checks it. This is the specification’s pinned pipeline (guide, Section 1.8). The obligations are
built from the distance table of the module’s own machine (Section 2.5); the one for twenty
codes at 1/5 has 5120 variables and 501,856 clauses. The bundle keeps every refuted CNF
with its DRAT proof, every coloring and every clique. With drat-trim and cake_lpr installed,
the oracle replays the nine refutations of this section, four for codes and five for centers, and
every optimum below is Checked. Without them, the optima whose lower bound is a refutation
are Conditional on (TrustedBackend cadical 1.5.3 SAT sha256:...), the digest naming
the refuted obligation, while the optima certified by a clique stay Checked. Table 6 gives the
frontier under the gentle rule at discount one.

3.9    Six beliefs
The agent holds many beliefs, and the specification’s product rule lets claims about one belief
carry over to several without enumerating the product. Beliefs6 has 248 states.
Proposition 3.1 (Product rule). Let M1 , . . . , Mk be deterministic machines and let M be their
parallel composition, in which every action either acts on all components at once or on exactly
one of them, and the observation distance of M is the maximum of the components’ observation
distances. Then for every discount and every horizon,
                                                            Mi
                                 beh (xi )i , (yi )i = max dbeh (xi , yi ).
                                dM
                                                 
                                                          i

Consequently a product encoding has the current, behavioral and radius defects of its component
encodings, its number of codes is the product of theirs, and its weakness under the product law
is the product of their weaknesses.

Proof. A word of M acts on component i through its projection, the subsequence of actions that
reach i, which is never longer than the word; discounting by length therefore gives at most the
component’s own value, so the left side is at most the right. Conversely every word of Mi lifts
to a word of M of the same length, by replacing each component action with the corresponding
local or global action, and the lifted word produces the same observation difference in component
i. The supremum over words therefore commutes with the maximum over components. The
same argument applies word length by word length, which gives the horizon form.

    The oracle confirms the proposition on two copies of a sixteen-state memory, for both
decay rules and both discounts, over all 65536 pairs. CheckBehavioral Grid6 (Within 1/5)
is therefore Checked from the component certificate, an exact computation that carries no
assumptions. Table 7 gives the cost of six beliefs.
    A joint encoding, such as a codebook shared across beliefs, falls outside the product rule. A
request about one should return Unknown with a diagnostic that names the rule, rather than
attempt to enumerate 248 states.

3.10    Forks and merges
Agents fork: two processes take copies of a memory, hear different evidence, and later merge.
The receipt ledger models this with six receipts and union as the merge.
  • CheckNow Counts is Checked: the counts determine the truth value.
  • CheckUpdates Counts is Refuted with the pair ({u1 }, {u2 }) and the action hear-u1,
    giving tallies (1, 0) against (2, 0). Hearing a receipt twice is harmless only if one knows it
    is the same receipt.
  • MeasureBehavioral Counts is Checked with defect 1/3, attained at ({u1 , v1 }, {u2 , v2 }).
A memory that kept only counts can still try to merge two forks, and the contracts measure
how badly each attempt fails.
  • Adding the tallies has worst error 6/35. CheckImplementation AddMerge (Grade 1
    1/6) is Refuted at ({u1 , u2 , u3 }, {u1 , u2 , u3 }), which gives (6, 0) instead of (3, 0).
  • Taking the maximum also has worst error 6/35; the witness is ({u1 , u2 , v1 }, {u3 , u4 , v2 }),
    which gives (2, 1) instead of (4, 2).
  • No rule on counts does better. If both forks hold the tally (2, 1), the true union may be
    any of six tallies from (2, 1) to (4, 2), and no single tally lies within less than 6/35 of all of
    them.
  • A three-way merge from the fork base, which adds what each fork heard since the base,
    is Refuted over all forks with worst error 6/35; the least witness is the empty base with
    both forks {u1 }, with error 2/15. Restricted to forks whose new receipts are disjoint
    (CleanForks) it is Checked with error 0.
Forgetting an identity is safe only relative to what can happen next. A natural design keeps the
identities of receipts newer than the oldest open fork and compacts older receipts to counts. The
fork horizon takes care of merges: two forks opened after the compaction share the compacted
part, and merging them adds only newer receipts, which still carry their identities. It does not
take care of an old receipt that arrives again, through a delayed delivery, a retransmission, or
a later operation that names it. The ledger module declares such a compaction, with u1 and
u2 below the horizon, and a machine whose actions are those of a delivery protocol that never
delivers them again:

The design rule is therefore a statement about a protocol. Receipts older than the oldest
open fork may be compacted to counts when the protocol also ensures that none of them is
delivered or named again: a closed receipt namespace whose old receipts have all been delivered,
a delivery watermark that drops redeliveries below it, deduplication tombstones that keep the
old identities in a cheaper form, or the exclusion of old hear operations after compaction. The
fork horizon is one part of such a protocol, and the certificate holds for the operations declared:
compact is exact on SettledLedger and fails on Ledger.

In plain terms. A count cannot tell a receipt that arrives a second time from a new one.
Dropping the identities of old evidence is safe only when the rest of the system promises that
old evidence will not arrive again, and the check has to be made against the operations that
promise leaves open.

3.12   Notes for implementers
Undiscounted distances. For a deterministic machine, the undiscounted distance of a
pair is the largest observation distance over the pairs reachable from it in the pair graph. A
strongly-connected-component pass over the pair graph computes it in linear time (65536 nodes
and 3 × 65536 edges here). Plain iteration also converges, after 15 rounds under the original
rule and 23 under the gentle one, but the number of rounds has no useful general bound.

Discounted and horizon distances. Iterate from the observation distances until nothing
changes; with discount 9/10 the iteration stops exactly after 12 rounds here. Horizon h is
exactly h rounds.

                                             20
MeTTaDinC                                                      Worked examples, 4 November 2026


Exact arithmetic. Store distances as ranks into the sorted list of distinct values — 50 values
under the original rule and 1445 under the gentle one — and convert to rationals only for results.
Comparisons, maxima and the fixed point then run on small integers.

Certificates for a defect. The upper bound is the distance table itself: one pass confirms
that each entry is at least the observation distance and at least the entry of each successor pair.
The lower bound is a replayed word.

Canonical witnesses. A backward breadth-first search from the violating pairs gives the
shortest violating length of every pair in one pass. A forward search from the least pair at that
length, expanding actions in declaration order, then gives the canonical word.

Frontiers. A satisfiability solver with clique-based symmetry breaking (the clique’s states
fixed to distinct colors) solves each coloring instance here in under a second, and drat-trim and
cake_lpr check each of the nine refutations in under a second as well. Under the original rule
no solver is needed below 1/2: the pairs that may share a code fall into small groups, every
state of one group conflicts with every state of another, and the fewest codes and the largest
clique are sums over the groups. Partitions returned by an optimizer are not canonical, so the
manifest should record their properties — the number of codes, the defect within the bound,
the kind of optimality certificate — rather than the partition itself. A budget that ends before
a certificate is found yields Unknown, with the best clique bound in Resources; a refutation
whose proof is not replayed yields Conditional, with the solver’s trusted-backend assumption.

Merges. A merge reduces to translations. For a union merge, translation by single receipts
suffices, and those translations are exactly the hear actions: six checks instead of sixty-four.
A compaction that forgets identities must be checked on the machine of the declared delivery
protocol, whose actions are the operations still possible after compaction; checked on the full
ledger it fails.

Behaviors the fixtures pin down. If evaluates only its chosen branch, and the t = 0
guards depend on it. Quot is floor division. The Center selector breaks ties by declaration
order. Product varies the last component fastest, which fixes the order of pairs in witnesses.
Codes are crisp by default, so update defects are 0 or 1.

4     Example 2: auditing an access policy without enumeration
4.1    The problem
Many organizations control access with roles. Users are assigned roles, roles carry permissions,
and a user exercises a permission by activating one of their roles in a session. In administrative
role-based access control the assignments themselves are governed by rules: an administrator
may assign a role to a user only when preconditions hold, and revoking one role may revoke
others that depend on it [4, 5]. Separation of duty is the usual safety requirement: no single
person may both approve payments and audit them. Policies of this kind are written by hand,
grow by accretion, and are hard to audit. Each rule may look sensible on its own while some
sequence of individually legitimate administrative steps still reaches a configuration that violates
the requirement, and finding such a sequence by inspection is slow and unreliable. Analysis tools
for such policies exist [6]; the example shows how the same questions are posed and answered
in MeTTaDinC, with certificates.
   The organization has four users (alice, bob, carol, dave) and five roles (staff, clerk, approver,
auditor, admin). A user may hold a role (it is assigned) and may have it active in a session.
Permissions come only from active roles: read from staff, clerk, approver or auditor; write
from clerk or approver; approve from approver; audit from auditor; configure from admin. The
administrative rules are these.
    • Two-person rule: assigning or revoking any role for user u requires some other user with
      admin active.
    • Preconditions: clerk requires staff; approver requires clerk and not auditor; auditor requires
      staff and not approver; admin requires staff.
    • Cascades: revoking staff removes every role of the user; revoking clerk also removes
      approver.
    • Sessions: a role can be activated only if it is assigned, and approver and auditor are never
      active together.
The state is a forty-bit word, ten bits per user: five assigned bits followed by five active bits,
bit 10u + r for “u holds role r” and bit 10u + 5 + r for “u has r active”. That gives about
1.1 × 1012 configurations, 80 actions (four kinds, four users, five roles) and 20 access observers
(five permissions for four users).
    The policy as written contains two plausible authoring mistakes. The approver rule checks
whether the user has auditor active rather than assigned, and revoking clerk forgets to remove
approver. The start configuration is the word 34672145: alice holds staff and admin, with admin
active; bob holds staff and clerk, with clerk active; carol holds staff, active; dave holds nothing.
    The findings, in brief:
    • The policy as written has two holes, found by canonical witnesses of two and three steps.
    • The corrected policy is proved safe without enumeration. It reaches 38,418,640 configura-
      tions, and 80 small proofs cover them all; nothing near 240 is ever listed.

MeTTaDinC                                                      Worked examples, 4 November 2026


  • The proof obligations are generated from the module itself, so the audit is about the policy
    the module declares. Restoring either mistake in the source turns the corresponding proof
    into a refutation, with the witness found for the policy as written.
  • A true property can come back Unknown, when its proof needs a stronger invariant than
    the property itself. A counterexample to induction is not a refutation.
  • For a targeted question, slicing does most of the compaction: the state relevant to “can
    bob approve” shrinks from forty bits to seventeen, and a vendor’s ten-bit slice is refuted.
  • The full access interface has no exact compaction at all: forty short tests read off every
    bit. The only exact saving is restriction to the reachable configurations, about 25.2 bits’
    worth.

4.2   Background: proofs about a space that cannot be listed
On a symbolic carrier (specification, Section 5.3) states are bit vectors and maps are terms over
registered primitives such as bit access, Boolean connectives and bit setting. The checker never
enumerates the carrier; it turns each claim into proof obligations over the terms and discharges
them with a satisfiability solver or with binary decision diagrams.
    Safety as a partition.      The audit states each safety requirement as a one-block
BlockPartition on the reachable scope (Reach Policy (From start)): the block is the set
of safe configurations, and the coverage obligation says that every reachable configuration lies
in it. CheckBlockPartition is a first-release request (specification, Section 16.1).
   Inductive invariants. The reachable set is not known in advance, so coverage is proved by
induction. A set I that contains the start configuration and is closed under every action is an
inductive invariant; it contains every reachable configuration, and if it lies inside the block,
coverage holds. Each closure obligation, “if x ∈ I then Ta x ∈ I”, becomes one satisfiability
query: the solver is asked for an x in I whose successor leaves I. An unsatisfiable answer, with
a proof, discharges the obligation. A satisfiable answer is a counterexample to induction: a
configuration from which one step leaves the set. It may be unreachable, so it does not refute
the claim (specification, Section 5.3); a refutation needs a word from the start configuration.
    Proofs that a second program can check. The obligations are encoded in conjunctive normal
form by the Tseitin transformation [7], solved with CaDiCaL, and every unsatisfiability proof is
emitted in the DRAT format, converted to LRAT by drat-trim [9] and checked by cake_lpr, a
proof checker verified in CakeML [10]. This is the specification’s pinned pipeline (specification,
Section 15.3; guide, Section 1.8); trust rests on the verified checker, not on the solver. A proof
certifies the formula it was produced for, so the formula has to be generated from the admitted
module by the obligation generator, which the specification places inside the trusted boundary;
Section 4.8 describes how the example’s oracle generates the obligations and tests the generator.
A result whose proofs have not been replayed is Conditional on the solver (Section 2.1).
    Exact reachable sets. For counting the scope exactly, binary decision diagrams [8] compute
the reachable set as a fixed point of image computations. The image of a set R under a guarded
update that sets bit b to v when the guard g holds is (R ∧ ¬g) ∨ ((∃b. R ∧ g) ∧ b = v), provided
the guard does not read the bits it writes.

In plain terms. A proof by induction says that the policy never leaves the safe region because
no single step can leave it. When some single step can leave it, from some configuration, the
proof has failed, but the policy may still be safe: that configuration might never occur. Only a
concrete sequence of steps from the actual starting configuration shows that the policy is unsafe.

4.8   Notes for implementers
Build every obligation from the source. The oracle reads access_policy.metta with a
small reader, resolves the imports (a name is looked up in the module that declares the map
being elaborated), expands the Families forms, folds the bit indices, and elaborates every map
into Bool or Word into a typed intermediate form: Boolean terms over the bits of one word,
with the declared From and To types checked, and for each action its normal form “if g then set
these bits”. The CNF encoder, the evaluator that finds and replays witnesses, and the decision
diagrams all read this one form, so a change to the module reaches all three.

Validate the encoding point by point. On the two-user instance of the same source, with
the User carrier restricted to alice and bob and twenty bits of state, a direct interpreter of the
source terms, the intermediate form and the generated CNF agree on every one of the 220 words,
for each of the 80 actions of the two modules, 26 queries and alarms, and 240 closure obligations.
The CNF side is evaluated by propagating the inputs through the recorded gates, after a
structural check that the gate clauses admit exactly one extension of every input assignment, so
that whether an obligation is satisfiable from a given word can be read off directly. At forty bits
the interpreter and the intermediate form agree on a sample of 50,119 words, which includes
every configuration within two steps of start, and the closure obligations of NoBreach and
ClerksOnlyProved agree with them on 20,000 of those words.

Mutate the source. Restoring the first mistake in the corrected module, so that the approver
rule reads the auditor session again, turns NoBreach from Checked into Refuted, with the
witness (assign bob auditor) (assign bob approver) and the state 34684433 replayed on
the mutated source; the closure obligations that change are exactly the four approver assignments.
Restoring the second, so that revoking clerk keeps approver, refutes ClerksOnlyProved with
the three-step witness of the policy as written and leaves NoBreach Checked. A separate model
of the policy would notice neither mutation, because it does not read the module.

Keep an independent model as a differential check. The bundle’s hand-written Python
policy and encoder do not read the module. They agree with the source on every word of
the two-user instance and on the forty-bit sample, the hand-written closure obligations of the
corrected policy are unsatisfiable as well, their decision diagrams give the same reachable sets,
and their obligations agree with enumeration: all 240 closure obligations at twenty bits and all
2400 two-copy obligations at ten bits. Under either mutation the comparison fails at the first
affected word, for instance at word 524298 under the first, where alice holds clerk and auditor
and bob has admin active.

Expand families first. Four action schemas give 80 actions and five observer schemas give
20 observers. The obligation generator only ever sees expanded, constant-folded terms.

Closure obligations are independent and small. None has more than 104 variables, so
they can run in parallel. Hash shared structure, and emit byte-identical conjunctive normal
form for identical obligations, so that certificates are reproducible.

Report a failed induction step with care. A satisfiable induction step goes in Resources,
as a counterexample to induction, and never in Witness. Refute only with a reachable word
found by a search in canonical order.

Minimize solver models before reporting them. Solvers return arbitrary models; for the
written policy the first counterexample to induction came back as a thirteen-digit word. Fix bits
from the most significant down, which costs at most forty extra calls, to obtain the least model;

Images for guarded updates. The image formula for guarded set and clear updates holds

the terms.

Say which evidence backs each number. Scope sizes come from recomputing the decision
diagrams. The satisfiability path proves only that the scope lies inside the invariant, so the
result should state which kind of evidence supports each number it reports, and its assurance:

Cones of influence. Take the support of each update term and close it under all actions;
the result is sound and cheap to compute. Guard bits count as reads, and that is exactly what

5     Example 3: sharing skills between robots with different cam-
      era frames
5.1    The problem
Robots that share skills rarely share a body. Their cameras are mounted differently, their
grippers differ, and a command that means “forward” for one means “left” for another. A
skill learned by one robot can be used by another only through a translation of states and
commands, and a library of such translations becomes a network: some are calibrated, some
are learned from recorded behavior, and composing them around a loop should bring a skill
back unchanged, or at least changed in a way nobody minds. The specification’s skill-transfer
laboratory states the claims for this setting (specification, Section 13.3); this example works
them out on a problem with enough geometry to be instructive.
    Three warehouse robots work in identical 5 × 5 bays. The goal is at the center, cell (2, 2),
counting rows from the top and columns from the left, and pillars stand in rows 1 and 3 of the
two outer columns. Each robot sees the bay through its own camera and issues the commands
up, right, down and left in its own image frame. Robot A’s camera is aligned with the bay,
robot B’s is turned a quarter turn clockwise, and robot C’s sees the bay transposed. A move
earns 1 if it brings the robot closer to the goal, 1/2 if the distance is unchanged (a wall or a
pillar blocks the move), and 0 if it moves away. Each robot has 21 free cells.
    The shared library has three transfers. AB and BC come from camera calibration. CA was
learned by matching recorded responses: the matcher took the first frame change under which
every translated command earned the recorded reward.
    The findings, in brief:
    • A learned transfer is fixed only up to the task’s symmetries. The learned CA is one of
      four candidates that are all exactly right, and going around the cycle A, B, C, A returns
      every cell as its up-down mirror image.
    • Whether that is acceptable depends on the declared gauge, the group of response sym-
      metries each robot is allowed to absorb. With no gauge the library is refuted; with the
      task’s symmetry group it is coherent.
    • A gauge copied unchanged from one robot to the next is wrong; it must be transported into
      each robot’s frame. The checker catches the copied gauge on the intertwining condition.
    • A skill sent around the loop earns, at each cell, what the original earns at the mirrored
      cell. A’s greedy skill comes back changed at 5 of its 21 cells and earns the same reward
      at every cell, because its rewards are symmetric under the mirror; the skill that always
      moves up comes back as the skill that always moves down, and its reward changes at 12
      cells.
    • A new requirement that breaks a symmetry exposes the stale transfer, with a one-move
      witness, and re-learning repairs the library up to a smaller gauge.
    • A pallet in one bay makes transfers into that bay approximate, and makes the transfer
      out of it ill-typed. No hive claim covers that case yet.

5.2    Background: transfers, symmetries, holonomy and gauges
A method system has states, methods (here, commands) and a response r(x, m), the reward of
method m in state x. A transfer from system i to system j has two parts: a state pullback φ,
which maps each state of j to the state of i that it corresponds to, and a method pushforward ι,


                                               31
MeTTaDinC                                                            Worked examples, 4 November 2026


which maps each method of i to a method of j. The transfer is exact when the target, given
the translated command, earns what the source earns at the corresponding state:

          rj y, ι(m) = ri φ(y), m          for every target state y and source method m.
                                      


Otherwise its defect is the largest difference over all pairs, measured as the total-variation
distance between reward laws (RewardLawTV, the default) or as the difference of expected
rewards (ExpectedReward). With these directions a transfer is a morphism of polynomial
functors (specification, Section 10.2; [12]), and composition follows that structure: pullbacks
compose in the reverse order of the transfers and pushforwards in the same order.
   A symmetry of a method system is a pair of permutations (gS , gM ) of states and methods
with r(gS x, gM m) = r(x, m) for every state and method. The symmetries of a system form a
group.
   Composing the transfers around a cycle that starts and ends at one member gives a transfer
from that member to itself, the holonomy of the cycle. If the holonomy is the identity, a skill
comes back unchanged. If it is a symmetry (gS , gM ), a skill π, which chooses a method π(x) in
                                     −1
each state, comes back as π ′ (x) = gM  π(gS x), and the symmetry condition gives

                         r x, π ′ (x) = r gS x, π(gS x)       for every state x:
                                                         


the returned skill earns at x what the original earns at the corresponding state gS x. This
is what the TransportSkill request certifies, equality at the pulled-back state. It does
not give r(x, π ′ (x)) = r(x, π(x)). Three statements have to be kept apart. Performance at
correspondingly transformed states is kept by every transported skill. Performance at the
same state is kept by a skill whose reward profile x 7→ r(x, π(x)) is invariant under the gauge.
Expected performance from a start law that the gauge leaves unchanged is kept by every skill,
because such a law gives x and gS x the same weight. A gauge declares, for each member, a
group of symmetries that the library is allowed to absorb, and a transfer hive is coherent up to
its gauge when every edge is exact, every declared gauge element is a symmetry, the gauges
agree along the edges, and every holonomy lies in the gauge of its base member (specification,
Section 10.4). Agreement along an edge is the intertwining condition: conjugating the target’s
gauge by the edge must give the source’s gauge, ι−1 Gj ι = Gi on methods and likewise on states.
A gauge is a statement about a frame, so the same symmetry looks different in different frames,
and a gauge declared in one robot’s frame has to be carried into the others.
    Kernel hives are the second kind of hive (specification, Section 10.4). Each member carries
a tolerance on its states, here the response tolerance that identifies cells with identical rows of
rewards, and the transfers induce cross kernels between members. The hive is coherent when
the combined kernel on the disjoint union of the members’ states is transitive in the Łukasiewicz
sense; the consensus cost measures how much closing it under transitivity would identify. A
derived kernel hive can be saturated by the gauge, which first identifies states related by gauge
symmetries. The two kinds of hive make different claims: a transfer hive identifies states, a
kernel hive identifies response classes.

In plain terms. A transfer is a dictionary between two robots’ points of view. Going around
a loop of dictionaries can return a word with a different meaning; the question is whether the
difference is one the task cannot see. The gauge is the list of differences each robot has agreed
not to care about, and that list has to be written in each robot’s own terms. A skill that comes
back through such a loop does at each position what the original did at the mirrored position;
that is the same as what the original did at the same position only for a skill that looks the
same in the mirror.

5.3   The dihedral picture
The eight symmetries of the square — the identity, three rotations, and four mirrors — act on
cells and on directions. Write r90 for a clockwise quarter turn on the screen, (r, c) 7→ (c, 4 − r),
and mv , mh , md , ma for the left-right mirror, the up-down mirror, the transpose and the
anti-transpose. The progress task is invariant under four of them,

                                     K = {id, r180 , mv , mh },

because the bay itself has exactly these symmetries: the goal is central and the pillars are
placed symmetrically about both axes, but not about the diagonals. K is a subgroup of index
two, hence normal, so it is the same set of transformations in every robot’s frame. Its two
single-mirror subgroups are not frame independent: a quarter turn exchanges the left-right and
the up-down mirror.
   The candidates for CA. The exact transfers from C to A are exactly the calibrated transfer
composed with an element of K, so there are four:
   • md , the calibrated transfer;
   • r90 , the learned one, which equals the calibrated pullback composed with A’s up-down
     mirror: md ◦ mh = r90 ;
   • r270 and ma , the other two.
The holonomy. Composing the transfers A to B to C to A gives the identity with the calibrated
CA, and the up-down mirror on both cells and commands with the learned CA.

5.8    A skill around the loop
A’s greedy skill takes the first improving command in the order up, right, down, left. Sent
from A to B to C and back to A, it returns changed at 5 of its 21 cells, (0, 1), (1, 1), (2, 2),

TransportSkill certifies for the round trip is the identity of Section 5.2: at every cell x of A,
the returned skill earns what the greedy skill earns at the mirrored cell mh (x). The greedy skill
earns the same at a cell and at its mirror image, since its reward profile is symmetric under the
up-down mirror, so for it the returned skill also earns the same reward at every cell.
     That second property is a property of the greedy skill. The skill that always moves up,
always-up in the module, comes back as the skill that always moves down; UpRoundTrip is
Checked and reports the skill changed at all 21 cells. At (3, 2), just below the goal, the original
earns 1 and the returned skill 0; at (1, 2), just above it, the reverse; in all, the reward at the
same cell changes at 12 of the 21 cells. The certified identity holds all the same: at (3, 2) the
returned skill earns what always-up earns at (1, 2). Averaged over the 21 cells with equal
weight, a law that the mirror leaves unchanged, both skills earn 1/2 per move; started from
(3, 2) alone, they earn 1 and 0. “Coherent up to the gauge” therefore means that the skills that
come back are the originals composed with a symmetry of the task: as good as the originals
under any start law the symmetry preserves, and cell by cell only when the original’s rewards
are themselves symmetric.

5.12    Notes for implementers
Group elements. Store each element as a pair of permutations, of states and of commands.
Generate a gauge by closure from its declared generators, and check the symmetry condition on
the generators only.

Obligation order and witnesses. Check, in this order: edge exactness, edges in declaration
order, with the least target state and then the source command; the gauge generators, with
the least state and then the command; intertwining, edge by edge, reporting the first target
generator whose conjugate leaves the source gauge; and the holonomy, reporting the least moved
state.

Holonomy composition order. Follow the polynomial-functor composition order of the
specification: around the cycle, pullbacks compose right to left (AB ◦BC ◦CA) and pushforwards
left to right. The membership test is (φ, ι−1 ) ∈ Gbase , with φ the composite pullback and ι the
composite pushforward.

Intertwining for small and large groups. For small groups, compare the conjugated
method groups as sets. For large ones, compare generating sets with a membership test such as
Schreier–Sims.

Report both holonomy witnesses, typed. The transfer-hive witness (0, 0) 7→ (4, 0) and
the kernel-hive witness (0, 1) 7→ (4, 1) belong to different claims and must not be confused.

Saturation. Compute the saturated kernel α ◦ c ◦ α through equivalence classes rather than
by the naive four-fold loop. The 63-node closure runs in exact Łukasiewicz arithmetic.

Interface digests. Key every transfer and hive certificate by the digest of its response map,
so that the docking module can never reuse a progress certificate.

Pullback totality is an admission check. It belongs to the subset carrier, so the pallet
bay’s reverse transfer is InvalidInput before any response is compared.

Composing across metrics. ComposeTransfers needs a single metric. An exact transfer
has defect 0 under every metric, and for rewards in [0, 1] the expected-reward defect is at most
the total-variation defect; that conversion should be registered.

6      Example 4: a market maker across regime shifts
6.1    The problem
A market maker posts a price at which it will buy (the bid) and a price at which it will sell
(the ask), and earns the difference when both sides trade. Two forces work against it. Every
fill changes its inventory, and inventory is risk: a desk that has bought more than it sold is
exposed to the price falling. And some of the traders who take its quotes know more than it
does, so that the price tends to move against the desk right after it trades — adverse selection,
the subject of the classical models of Glosten and Milgrom [18] and of Kyle [19]. A quoting
policy balances spread against both, and the balance depends on the market: how often each
side trades, how informed the flow is, whether one side dominates. Markets change regime
often, and a policy and its forecasts tuned in one regime are routinely carried into another.
After a shift the desk needs to know what changed, whether its policy still holds, what its own
data can and cannot reveal, and how to detect shifts without crying wolf. The specification’s
regime laboratory poses these questions on a two-state example (specification, Section 13.4); the
market-making application treats typed regime changes, certified transfer and selective repair
at length [21]. This example makes them concrete on a model small enough to solve exactly.
   The desk. The desk holds at most two lots either way, so its inventory q lies in {−2, . . . , 2}.
Each step it posts one of three quotes:
    • tight: one tick from the mid on both sides;
    • wide: two ticks on both sides;
    • lean: one tick on the side that reduces the position and two on the side that grows it;
      when flat, lean is the same as tight.


                                                39
MeTTaDinC                                                             Worked examples, 4 November 2026


At ±2 lots the side that would grow the position is withdrawn, so at the limits lean is also
the same as tight. Each step, a buyer lifts the ask and a seller hits the bid, independently of
each other. A fill earns its offset in ticks minus the adverse-selection cost θ of the market, the
expected move against the desk after the fill. Holding q ′ lots after the step costs |q ′ |/4 tick, and
the desk maximizes expected discounted profit and loss (P&L) with discount 9/10.
    The markets. In a calm market a one-tick quote fills with probability 1/2 and a two-tick
quote with probability 1/8, on each side, and fills carry no information. Fill probabilities that
fall geometrically with the distance from the mid are the usual simplification in models of
limit-order fills [20]. Table 15 lists the four markets of the example.

                 Market      Ask fills (one, two ticks)   Bid fills (one, two ticks)    θ
                 calm               1/2, 1/8                     1/2, 1/8               0
                 toxic              1/2, 1/8                     1/2, 1/8              1/2
                 buyers             3/4, 3/16                    1/4, 1/16              0
                 sellers            1/4, 1/16                    3/4, 3/16              0

Table 15: The four markets. The toxic market has calm fill rates; the one-sided markets are

    The toxic market is also given in a finer form: each step independently carries an informed
trader with probability 1/2, whose fills are followed by a one-tick move against the desk (θ = 1),
and otherwise only noise traders (θ = 0). On average θ = 1/2.
   The findings, in brief:
   • In calm markets the desk can run on three risk buckets — flat, one lot, two lots — because
     the bucket map is an exact quotient of the decision process, and the optimal policy works
     on it at no loss.
   • Toxic flow cuts every value by more than half and changes no decision: the calm policy
     is certified optimal in the toxic market. A monitor of fill rates is provably blind to this
     change.
   • One-sided buying breaks the compression on both of its obligations, each with a one-line
     witness, and refutes the calm policy when the desk is one lot long. The broken symmetry
     survives as an exact transfer between the buyers’ and the sellers’ markets.
   • Knowing which steps carry informed flow is worth about one tick of discounted P&L. A
     signal that is right nine times in ten, at 1/20 tick per step, nets about a third of a tick,
     and evaluating it as if the signal were the truth overstates it by 0.22.
   • A desk that only quotes wide cannot tell from its own tape whether news has leaked: the
     two models are trace equivalent but not bisimilar. A tight quote makes the leak visible,
     with a two-step witness.
   • Each of two monitors is blind to one of the two shifts, and the blindness is an exact claim.
     Detections on data are Estimated results with guarantees that hold however often the
     stream is examined.

needs the sign again — but the market where buyers dominate is the mirror image of the one
where sellers dominate, so a policy worked out for one is a policy for the other.

6.7   Did the news leak?
Background. For a stochastic machine, behavioral equivalence and trace equivalence are
different claims (specification, Section 4.3 and 7.2). Two states are trace equivalent when every
sequence of observations has the same probability from both, under every sequence of actions;


                                                 46
MeTTaDinC                                                        Worked examples, 4 November 2026


equivalently, under every policy that chooses actions from what it has observed. They are
bisimilar when, in addition, their futures branch alike: a test that reads a predicted probability
and reacts to it — a modal test — cannot separate them. A consumer that acts only on its
own observations can tell apart trace classes and nothing finer. Trace equivalence is decided by
linear algebra: the functions x 7→ Px (y0 a1 y1 · · · ak yk ) span a space whose dimension is the size
of the minimal linear realization, the predictive-state dimension of the process [24, 25, 26, 27].
The specification’s mandatory seven-state chain has two states that are trace equivalent but
not bisimilar, a trace partition of six classes and a minimal linear realization of dimension five.

6.8    Monitoring the shift
Background. A monitor watches a stream and should raise an alarm when the stream stops
looking like the null law, here the calm market, while keeping false alarms rare however long and
however often it looks. Fixed-sample tests do not have that property; anytime-valid procedures
do [29, 30]. The simplest is the likelihood-ratio e-process: multiply, observation by observation,
the probability of what was seen under a declared alternative divided by its probability under
the null. Under the null this product is a nonnegative martingale with initial value one, and
Ville’s inequality [28] bounds the probability that it ever reaches 1/δ by δ. Several monitors
run at once combine by a union bound, each with threshold k/δ for k monitors, unless a joint
procedure is declared (specification, Section 7.4).

6.10     Notes for implementers
Laws are exact finite maps from canonical values to rationals, with zero masses dropped
when they are built. Image adds the masses of equal values and Indep multiplies supports.
Carrier closure is checked on supports: when the desk is two lots long the bid’s law is Coin 0,
so the out-of-range inventory 3 is never produced.

Decision processes reuse the machine checks. The machine view’s queries are the
expected rewards, one per action, with the declared value tolerance. Quotient checks are then
MDP homomorphism checks with no new algorithm. Equality of reward laws is a separate and
stronger claim (Compare Laws).

Policy iteration. Evaluate exactly by Gaussian elimination over the rationals. Improve by
keeping the current action on ties and otherwise taking the first best action in declaration order,
which makes the reported policy canonical. The certificate is the vector of values and the table
of Q-values; replay checks |S| linear equations and |S||A| inequalities. The canonical witness of
CheckOptimal is the least state, the policy’s action there, the first action in declaration order
with a larger Q-value, and both Q-values.

Policies through a representation. OptimizePolicy enumerates the deterministic code
policies (27 for the buckets, 243 for Coarse) and evaluates each in the full process. For larger
families it should report the best policy found and leave optimality Unknown unless the search
was exhaustive. Memoryless code policies are all the coarse policies there are only when the
hidden part is fresh; in general the problem is partially observable, memory and randomization
can do better, and the result must name its policy class.

Kantorovich distances in three stages. A floating-point value iteration, with one small
linear program per pair and action, identifies for each pair the term that sets the distance and
the optimal couplings. An exact linear solve gives the candidate distances, and the couplings
are re-optimized exactly until they stop changing. Verification then solves an exact transport
problem for every pair and action (upper bounds) and an exact dual problem for every pair
whose distance comes from a future step (lower bounds). For a discount below one the verified
fixed point is the distance. Supports here have at most three points, so a rational simplex with
Bland’s rule [32] is enough.




                                                51
MeTTaDinC                                                        Worked examples, 4 November 2026


The behavioral distance does not bound values. The specification’s operator combines
the present observation and the future with a maximum. It certifies equal values at distance zero,
but no constant c gives |V ∗ (x) − V ∗ (y)| ≤ c dbeh (x, y) in general. Consider two chains whose
reward gaps are δ, δ/γ, δ/γ 2 , . . . for K + 1 steps, with δ/γ K ≤ 1, and equal afterwards: the
distance stays at δ, while the value gap is (K + 1)δ, and K can be as large as log(1/δ)/ log(1/γ).
A desk that needs a guarantee on value loss should check values directly, as this example does,
or use an additive metric, d = maxa (|∆ra | + γWd ), which bounds value differences [17]. The
registry does not have one yet.

Sensors on processes. Compute values on the hidden states, with a fresh reading drawn
each step. When the hidden part is fresh, optimize over policies on the code and the reading
using the posteriors given each reading. Never substitute the reading for the hidden state.

Trace claims. Compute trace spaces by Krylov iteration over the operators Ma,y =
Ma diag([o = y]) with exact rationals. The canonical trace-event witness is the shortest
word, words ordered by action declaration, and then the least sequence of observations in the
declaration order of the reports. A trace certificate is keyed by its interface, action set included.

Monitors. Fix the context before the observation. Validity, blindness and chi-square are
exact results; the KL rate is irrational and stays outside every Checked claim. Union gives
each of k monitors the threshold k divided by the level, and Mixture thresholds the average
of the e-values. Store the stream rather than the seed: random generators differ between
implementations, and the module pins the stream by its digest. The e-value at a crossing is
an exact rational. A null with unknown parameters, such as a calm market with estimated fill
rates, needs a different procedure, for example a mixture e-process, which the proposed library
does not cover.

Interface identity. Certificates are keyed by the digest of the process — kernel, reward law,
discount and value tolerance. The calm policy is optimal in CalmDesk and in ToxicDesk by
two separate certificates.

    The additions that extend what can be claimed are few. WeakestWithin with a codes
objective and a lower-bound certificate turns frontier optimality from an exhaustive-search
claim into a certified one. FindTransfers turns “the learned transfer is exact” into “these
are all the exact transfers in the family”, which is what makes gauge fixing possible. The
decision-process requests, CheckOptimal and PullbackPolicy, bring policies into the claim
language, with certificates that are vectors of values and tables of Q-values. Detect is the first
request whose only status is Estimated, and its result names the data source by digest. Each of
these comes with an exact algorithm on the scale of the examples and a replayable certificate,
which is the standard every registered claim must meet.

7.2   Lessons for implementers
Some lessons recur across the examples, often in different forms.
    Claims that look alike are different claims. Example 1 separates a summary, a cold store
and a memory that runs on its codes, with three different answers for the same encoding, and a
compaction that is exact for the operations a delivery protocol allows from one that is exact
for every operation. Example 2 separates a failed induction step from a refutation. Example 3
separates a value pullback from a transfer, a transfer hive from a kernel hive, with different
witnesses for the same cycle, and what a returned skill earns at the mirrored state from what it
earns at the same state. Example 4 separates averaging from quotienting, equal means from
equal laws, and trace equivalence from bisimulation. In every case the cheaper claim is true
and the stronger one false, or the reverse, on the same input. An implementation that lets one
request stand in for another produces confident wrong answers, and the registry’s job is to keep
the requests and their result types distinct.
    Every certificate has two halves. An upper bound and a lower bound, a coloring and a clique
or a refutation, couplings and potentials, values and a table of Q-values, a proof of closure and
a reachable word: each Checked or Refuted result in the examples rests on a pair of objects
that a second program can check, with arithmetic or, for a refutation or a proof of closure,
with a verified proof checker. Producing them is the hard part; replaying them is cheap, and it
is what lets the trusted base stay small. A result whose second half has not been replayed is
Conditional, and its assumptions name the solver that was trusted.
    Canonical witnesses take deliberate work. They come from breadth-first searches that expand
actions in declaration order, from minimizing solver models before reporting them, and from
fixed orders on pairs, classes and observation sequences. None of this is automatic, and every
implementation that wants to pass a manifest has to do it the same way.
    Unknown is an answer. A budget that ends, a property whose proof needs a stronger
invariant, a greedy search without a lower bound: each of these returns Unknown with what
was learned in Resources. Example 2’s counterexample to induction is the clearest case, and
its result is more useful to the auditor than a false refutation or a silent failure would be.
   Interface identity keys every certificate. The docking response of Example 3, each market of
Example 4, and the action set of the news-leak desk all change the interface, and certificates for
one interface must never be consulted for another. Digests of the response maps, the kernels
and the action sets are the mechanism. Example 2 adds the source itself: its obligations are
generated from the module, each result records the module’s digest, and a mutation of one rule


                                               54
MeTTaDinC                                                        Worked examples, 4 November 2026


changes exactly the obligations of that rule.
   Admission does real work. A non-total state pullback (Example 3), a hidden factor that is
not fresh (Example 4), and a guard that reads the bits it writes (Example 2) are all caught
before any claim is evaluated. Checks of this kind are cheap and turn a wrong answer into an
InvalidInput.
    Avoid enumeration by structure, not by luck. The product rule (Example 1), cones of influence
and symbolic proofs (Example 2), and freshness (Example 4) each replace an enumeration that
would be impossible or expensive by an argument with a certificate. A request whose structure
falls outside such a rule should return Unknown with a diagnostic rather than attempt the
enumeration.
    Data enters frozen. The streams of Example 4 are stored with digests, and the Estimated
results name them. Exact claims are about models and Estimated claims about data, and the
result envelope keeps the two apart.

7.3    Open questions the examples raise
    • A frontier for memories that run on their codes, where each candidate costs the fixed
      point of an induced machine (Example 1).
    • Joint encodings outside the product rule, such as codebooks shared across beliefs (Exam-
      ple 1).
    • Graded transfer hives, for libraries whose transfers are only approximately exact, and a
      gauge-fixing completion that chooses among exact candidates so that holonomies become
      trivial (Example 3).
    • An additive behavioral metric for decision processes, whose distances bound differences of
      optimal value (Example 4).
    • Declared policy classes for processes whose hidden state persists, where memory and
      randomization matter (Example 4).
    • Monitors for nulls with unknown parameters, and confidence sequences for estimated rates
      (Example 4).
    • Risk-sensitive objectives, for which equality of reward laws, and not only of means, becomes
      the relevant check (Example 4).
    • Declarations of delivery protocols for memories that forget identities, so that the operations
      a compaction is certified against are declared once instead of being written out as a
      restricted machine (Example 1).
    • A verified obligation generator, which would turn the translation validation of Example 2
      into a proof that the generated formulas express the module’s obligations (Example 2).


8     Conclusion
The four examples began as tests of a specification and turned into something closer to design
reviews. In each of them the most useful output was not a number but a distinction the designer
had been collapsing without noticing — between a summary of a memory and a cold store
for it, between a property that is false and one whose proof needs more than the property
itself, between a skill library that is wrong and one that is right only up to a mirror, between a
market whose averages have changed and one in which the things being averaged have changed.
Keeping such distinctions apart, in a form that a second program can check, is a modest job for

                                                 55
MeTTaDinC                                                          Worked examples, 4 November 2026


a language. It is also a job that a great deal of practical reasoning in AI systems currently does
without, and the examples suggest that doing it explicitly costs less than one might fear: every
claim here was settled exactly or by a certificate that a verified checker replays, most of them
in seconds.
    The examples are small on purpose, and they show nothing yet about deployed memories,
policies, robots or markets. Each would have to be scaled up, connected to real data through
frozen snapshots and streams, and run against a running system before it said anything about
one. What they do show is how MeTTaDinC programs are written and read, what their answers
look like, and where the language runs out. The registry additions they propose are the first
concrete evidence about which parts are missing, and the list of open questions is the first
concrete evidence about which parts are hard.
    The hope, in the end, is that the next person to write a MeTTaDinC program starts from
one of these four rather than from the fixtures, and finds that the language says what they need
it to say — or, failing that, finds out quickly and precisely what it cannot say yet.

C     Reproducing the results
The four bundles are collected in mettadinc_worked_examples_package.zip, one directory
per example (ex1_belief_memory, ex2_access_policy, ex3_skill_share and ex4_market_
maker) under a top-level README. Each bundle contains its module file, its registry patch
(and the patches of earlier examples that it reuses), the static checker ex_check.py, the Python
model, the oracle and the oracle’s results. The bundles of Examples 1, 3 and 4 add the reference
evaluator metta_eval.py, and those of Examples 1 and 2 their proof obligations and a replay
script. Python 3.11 or later is assumed.

Running an oracle. In a bundle directory, python3 exN_oracle.py recomputes every
number of the example from the module file, prints one line per check, writes exN_results.json,
and exits with a nonzero status if any check fails. Table 2 gives the running times and
dependencies. The oracles of Examples 1 and 2 write every unsatisfiable obligation, with its
CNF and its DRAT proof, to obligations/, and check the proofs when the environment
variable MDINC_TOOLS names a directory holding drat-trim/drat-trim and cake_lpr/cake_
lpr. Without the tools they skip the checks that read the proof checker’s verdicts and report
the results that rest on the proofs as Conditional, with a trusted-backend assumption. The
pinned versions are drat-trim at commit 2e3b2dc and cake_lpr at commit 033aad5, run as
drat-trim obligation.cnf obligation.drat -L obligation.lrat
cake_lpr --CML_HEAP_SIZE=1024 --CML_STACK_SIZE=512 obligation.cnf obligation.lrat



Replaying the shipped proofs. ex1_obligations.tar.xz and ex2_obligations.tar.xz
hold the obligations of the runs that wrote the shipped results: the CNF and DRAT proof of
every unsatisfiable obligation, the colorings, cliques and center sets of Example 1, and an index

The reference evaluator. metta_eval.py, the same file in the bundles of Examples 1, 3
and 4, reads a module file with its own small reader, resolves imports, and evaluates the maps of
the module: Cases, Body and Table bodies, parameterized maps, the arithmetic and bit-vector
primitives used in the files, and the proposed law primitives. The oracles use it to compare
each module with its Python model cell by cell. It is a test aid for these examples and not an
implementation of MeTTaDinC.

The source route of Example 2. policy_ir.py reads access_policy.metta into the
typed intermediate form of Section 4.8, and obligations.py, bdd_reach.py and the oracle build
every obligation, reachable set and witness from it; validate_small_lib.py holds the point-
by-point validation on the two-user instance. rbac.py, circuits.py and sat_obligations.py
are the independent model, kept as a differential check. The oracle also applies the two source
mutations of Table 10 and requires the verdicts they affect to change.

The streams of Example 4. The three streams in streams/ were generated once by
monitors.simulate with seed 1 and are stored as data; the module pins each by its SHA-256
digest. Reproducing a detection means replaying the stored stream, not rerunning the generator,
whose output depends on the random number generator of the language it runs in.
